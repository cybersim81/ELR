# English Learning Repository (ELR)

## Continuity Package

**Version:** 2.0.0
**Status:** ACTIVE
**Document Type:** Governance and Continuity Document

---

## 1. Purpose

Il Continuity Package permette di ripristinare l'ambiente di lavoro ELR in una
nuova sessione senza dipendere dal contesto conversazionale precedente.

Il Continuity Package:

* definisce lo stato corrente del progetto;
* identifica il punto corrente della Roadmap;
* identifica il corpus documentale autorevole;
* definisce le regole di continuità;
* registra i vincoli operativi rilevanti;
* indica la procedura di ripresa.

Il Continuity Package non sostituisce Architecture Specification, ADR, Matrix,
Roadmap o Specification specialistiche.

Non deve duplicare integralmente le decisioni contenute nei documenti
proprietari.

Il repository è la fonte di verità.

---

## 2. Source of Truth

Lo stato architetturale effettivo deve essere determinato dai documenti
presenti nel repository.

In caso di divergenza tra:

* memoria conversazionale;
* Continuity Package;
* Handoff;
* implementazione;
* documentazione proprietaria;

la verifica deve essere effettuata sul repository e sui documenti
proprietari.

Il Continuity Package non può modificare retroattivamente una decisione
architetturale approvata.

## 3. Architectural Authority

Le autorità documentali sono:

### ELR Architecture Specification

Definisce:

* modello architetturale;
* componenti;
* responsabilità;
* confini;
* relazioni tra sistemi.

### ELR Architecture Decision Log

Definisce:

* decisioni architetturali;
* motivazioni;
* conseguenze;
* evoluzione delle decisioni.

### ELR Architecture Consistency Matrix

Definisce:

* ownership documentale;
* distribuzione delle responsabilità;
* coerenza tra documenti.

### Specialist Specifications

Definiscono il comportamento e la struttura dei singoli componenti secondo
la relativa ownership.

Nessun documento di continuità deve sostituire tali documenti.

## 6. Domain / Process / Persistence Boundary

Durante il lavoro:

* il Domain Model non deve essere inferito dal Persistence Model;
* il Persistence Model non acquisisce autorità semantica per il solo fatto di
  esistere;
* i processi non devono essere introdotti come entità del Domain Model senza
  decisione esplicita;
* le Evidence operative appartengono ai relativi processi e modelli
  proprietari;
* una implementazione esistente non costituisce automaticamente una
  decisione architetturale.

Ogni nuova responsabilità deve essere assegnata al documento proprietario
appropriato.

---

## 7. Decision Workflow

Il processo di lavoro è:

**verifica → problema/discrepanza → analisi documentale → proposta focalizzata →
approvazione esplicita → blocco copiabile → aggiornamento repository →
verifica → prossimo punto**

Una decisione non è considerata definitiva prima dell'approvazione esplicita.

Una modifica documentale non è considerata applicata prima della verifica
del repository.

Non devono essere introdotte simultaneamente più decisioni indipendenti
senza una ragione esplicita.

---

## 8. Repository Verification Rule

Prima di qualsiasi decisione:

1. individuare i documenti rilevanti;
2. recuperarne lo stato effettivo dal repository;
3. verificare versione e status;
4. confrontare le definizioni pertinenti;
5. identificare eventuali contraddizioni.

Dopo ogni aggiornamento:

1. verificare il file nel repository;
2. verificare la sezione modificata;
3. verificare i boundary adiacenti;
4. solo dopo procedere.

La conversazione non costituisce prova dell'avvenuto aggiornamento del
repository.

---

## 9. GitHub Integration Constraint

La connessione GitHub è stata verificata nel corso del lavoro.

### Read

**Disponibile.**

Il connettore può recuperare e verificare file presenti nel repository.

### Write

**Non disponibile nel contesto operativo corrente.**

Le richieste di scrittura diretta al repository hanno restituito:

**HTTP 403 — Forbidden**

Pertanto una richiesta di scrittura non deve essere considerata riuscita
sulla sola base della risposta dello strumento.

### Procedura operativa conseguente

Quando la scrittura diretta restituisce `403`:

1. non dichiarare il documento aggiornato;
2. produrre il blocco copiabile esatto;
3. l'utente applica la modifica al repository;
4. recuperare nuovamente il documento;
5. verificare il contenuto aggiornato;
6. solo allora considerare la modifica effettivamente applicata.

Il `403` è un vincolo operativo dell'integrazione, non una decisione
architetturale ELR.

## 11. Rules for New Sessions

### Una nuova sessione deve:

1. leggere `ELR Session Prompt 1.0.0.txt`;
2. leggere `ELR Continuity Package 2.0.0.txt`;
3. leggere `ELR Roadmap 1.2.0.txt`;
4. leggere `ELR Architectural Work State - Handoff 4.0.0.txt`;
5. leggere `ELR Architecture Specification`, `ELR Architecture Decision Log`
   e `ELR Architecture Consistency Matrix`;
6. verificare lo stato effettivo dei documenti nel repository;
7. identificare la Fase 7 e il relativo stato verificato;
8. iniziare dal controllo repository-wide delle Dependencies;
9. leggere soltanto i documenti specialistici direttamente rilevanti per
   la prima discrepanza;
10. non ricostruire decisioni dalla memoria della conversazione precedente;
11. non riaprire decisioni APPROVED senza una contraddizione documentale
    reale;
12. non assumere che un'attività rimanga aperta soltanto perché lo era in
    una precedente sessione;
13. mantenere il workflow:

**verifica → problema/discrepanza → analisi → proposta → approvazione →
blocco copiabile → aggiornamento repository → verifica → prossimo punto.**

Non deve:

* ricostruire decisioni dalla memoria;
* riaprire automaticamente decisioni APPROVED;
* creare documenti duplicati;
* assumere che un documento sia aggiornato senza verifica;
* assumere che una modifica GitHub sia riuscita dopo un errore `403`.

## 13. Corpus Integrity

Un documento appartiene al corpus ELR quando:

* è presente nel repository ed è riconosciuto dal relativo sistema di
  ownership;
* oppure è esplicitamente previsto come documento futuro dalla Roadmap.

La presenza di un concetto durante l'analisi non implica automaticamente la
necessità di creare una nuova Specification.

Prima di creare un nuovo documento occorre verificare:

1. se la responsabilità appartiene a un documento esistente;
2. se la Consistency Matrix assegna già tale responsabilità;
3. se la creazione modifica l'architettura;
4. se è necessaria una decisione ADR;
5. se è necessario aggiornare la Roadmap.

---

## 14. Continuity Principle

L'ELR deve essere documentariamente autoportante.

La continuità non deve dipendere dalla conversazione precedente.

La continuità è garantita da:

* documenti proprietari;
* decisioni registrate;
* ownership esplicita;
* Roadmap;
* Continuity Package;
* Handoff;
* procedure di verifica del repository.

La memoria conversazionale può facilitare il lavoro, ma non costituisce
autorità architetturale.

---

## 15. End State

Il Continuity Package deve rimanere uno strumento di orientamento e
governance.

Non deve diventare una seconda Architecture Specification.

Quando il contenuto di questo documento diverge da una Specification, ADR,
Matrix o Roadmap verificata nel repository, la divergenza deve essere
segnalata e risolta attraverso il normale processo documentale.
