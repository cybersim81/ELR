# 10. EVIDENCE RULE
================================================================================

Use evidence in the following priority:

1. authoritative normative requirement;
2. approved architectural decisions;
3. approved implementation specifications;
4. repository source code;
5. repository tests;
6. current continuity artifacts;
7. conversation history.

Conversation history is never a substitute for repository evidence.

A missing implementation component is not automatically a defect.

An existing implementation component is not automatically conformant.

Conformance is established by responsibility and behavior.


================================================================================
# 11. ARCHITECTURAL AUTHORITY
================================================================================

The following principles remain mandatory:

* the repository is the source of truth;
* authoritative specifications define required behavior;
* ADRs define approved architectural decisions;
* the Architecture Consistency Matrix defines cross-document consistency;
* implementation does not acquire architectural authority merely because it
  exists;
* persistence structures must not be used to infer Domain semantics;
* ORM structures must not be used to infer Domain semantics;
* implementation gaps must not silently become architectural changes;
* architectural decisions must not be reopened without a real contradiction;
* continuity artifacts must not become alternative architectural authorities.


================================================================================
# 12. IMPLEMENTATION CHANGE RULE
================================================================================

Before modifying implementation:

1. establish the exact responsibility;
2. establish the authoritative requirement;
3. inspect existing behavior;
4. determine whether the behavior is already conformant;
5. determine whether the discrepancy is implementation, test, documentation,
   technical-decision or architectural;
6. modify only the layer responsible for the confirmed discrepancy.

Do not refactor unrelated code.

Do not introduce speculative abstractions.

Do not redesign architecture while resolving an implementation finding.


================================================================================
# 13. TESTING RULE
================================================================================

After an implementation change:

1. run focused tests covering the changed responsibility;
2. verify the focused tests;
3. run the complete test suite;
4. record the resulting full-suite baseline;
5. inspect for regressions;
6. update the Current Implementation Checkpoint.

A test count is current evidence only when the corresponding suite has actually
been executed.

Historical test counts remain historical.
