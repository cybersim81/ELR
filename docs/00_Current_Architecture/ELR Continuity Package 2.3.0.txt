# 1. PURPOSE

This document defines the persistent continuity model for ELR architectural
work across separate sessions.

Its purpose is to ensure that a new session can reconstruct the current
working state from repository evidence without relying on conversational
memory.

The repository is the source of truth.

This document does not replace:

* Architecture Specification;
* Architecture Decision Log;
* Architecture Consistency Matrix;
* domain specifications;
* implementation specifications;
* Roadmap;
* Handoff;
* Session Prompt.

It defines how those artifacts are used together for continuity.

---

# 2. SOURCE OF TRUTH

The ELR repository is the authoritative source for:

* document existence;
* document content;
* document version;
* document status;
* canonical document identity;
* current versioned filename;
* architecture decisions;
* implementation state;
* roadmap state;
* continuity state.

Conversational memory must not override repository evidence.

If the current repository state differs from a previous conversation, the
repository state is authoritative.

---

# 3. CANONICAL DOCUMENT IDENTITY

ELR continuity artifacts distinguish between:

* **canonical logical name**;
* **versioned repository filename**.

The canonical logical name identifies the artifact independently of version.

The versioned repository filename identifies the current physical document
version stored in the repository.

A version change does not create a new canonical identity.

Resolution rule:

**canonical name → repository lookup → current versioned filename**

When a document is referenced semantically, use the canonical name.

When a document must be read, modified or verified, resolve the canonical
name to the current versioned filename using repository evidence.

Never assume that a previous versioned filename remains current.

---

# 5. VERSION RESOLUTION RULES

When opening or modifying a continuity artifact:

1. identify the canonical document name;
2. inspect the repository;
3. determine the current versioned filename;
4. verify the version contained in the document;
5. verify that all continuity references point to the current version;
6. only then perform READ, WRITE or VERIFY operations.

A reference to a canonical name must not silently imply a historical version.

A reference to a versioned filename must be verified explicitly against the
repository.

# 10. SESSION BOOTSTRAP

A new session must read, in this order:

1. `ELR Session Prompt 1.4.0.txt`
2. `ELR Continuity Package 2.3.0.txt`
3. `ELR Architectural Work State - Handoff 6.3.0.txt`
4. `ELR Roadmap 1.3.0.txt`

The session must then:

1. verify the repository;
2. verify the current version of each continuity artifact;
3. resolve canonical names to current filenames;
4. determine the current phase;
5. read only the specialist documents relevant to the current phase;
6. begin the next authorized activity.

The current phase must not be reconstructed from conversational memory.

A completed checkpoint must not be repeated automatically.

---

# 11. SESSION WORKING PROTOCOL

Use the following sequence:

**repository verification
→ focused discrepancy
→ document analysis
→ one focused proposal
→ explicit approval
→ copyable documentation block
→ repository update
→ repository verification
→ next point**

A proposal is not an applied change until the repository has been reread and
the modified content has been verified.

Completed checkpoints should not be re-executed merely to reconstruct
context.

---

# 12. DOCUMENT PROPAGATION RULE

When a document is changed:

1. identify its canonical identity;
2. identify its current versioned filename;
3. identify all dependent continuity artifacts;
4. update only references affected by the version/path change;
5. preserve canonical identity;
6. reread the modified documents;
7. verify canonical name, filename and version consistency.

Propagation must be controlled.

When continuity artifacts are versioned as part of a checkpoint transition,
the propagation order is:

1. Session Prompt;
2. Continuity Package;
3. Handoff;
4. Roadmap.

Each artifact must be verified in the repository before the next artifact is
versioned.

A new versioned filename must not be treated as current until the file exists
in the repository and its internal version is verified.

Do not update unrelated documents merely because they mention the same
concept.

**problem → verification → proposal → explicit approval → documentation →
verification**

# 17. SESSION CLOSURE CHECKPOINT

A session may propose closure when:

* the current work item is verified;
* no partially applied correction remains;
* the next authorized action is explicit;
* the working state is reconstructable from repository evidence;
* continuity artifacts are internally consistent;
* canonical names resolve to current versioned filenames;
* no unresolved documentation finding remains.

A phase-transition checkpoint must additionally record:

* the completed phase;
* the completed phase result;
* the newly authorized phase;
* the absence or presence of unresolved findings;
* the continuity artifact update required for the next session.

The assistant must explicitly state when a clean checkpoint has been reached.

The assistant must not close the session automatically.

The user must explicitly approve closure.

A completed phase or checkpoint is a valid session stopping point.

## 17A. VISIBILITÀ DEL PROGRESSO DI FASE

Il workflow di continuità comprende una mappa sintetica del progresso della
fase utilizzata durante le sessioni di lavoro attive.

La mappa di progresso registra lo stato operativo della fase corrente usando:

* `[ ]` non iniziato;
* `[~]` in elaborazione;
* `[x]` verificato/completato.

La mappa deve identificare:

* la fase corrente;
* i principali punti di lavoro;
* il lavoro completato;
* il lavoro attualmente in elaborazione;
* il lavoro pianificato;
* il checkpoint o gate previsto.

La mappa di progresso non costituisce autorità architetturale e non sostituisce
le Specification, gli ADR, la Architecture Consistency Matrix, la Roadmap o
altri documenti autorevoli.

Il suo scopo è fornire visibilità operativa e supportare la gestione dei
checkpoint.

In prossimità di un checkpoint, la sessione deve rendere espliciti:

* gli elementi verificati;
* gli elementi ancora aperti;
* le decisioni che si sono rese necessarie;
* le apparenti decisioni risolte mediante documenti autorevoli già esistenti;
* la prossima azione autorizzata;
* l'eventuale necessità di aggiornare gli artefatti di continuità.

Questo meccanismo costituisce inoltre una base leggera per valutare
l'efficienza del workflow alla chiusura della sessione.

Un punto della mappa può essere marcato `[x]` solamente quando il lavoro
sottostante è stato verificato secondo le regole di verifica del repository.

La mappa di progresso, da sola, non costituisce evidenza del completamento di
un checkpoint.

Together they form the ELR continuity system.
