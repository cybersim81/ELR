# ELR Session Prompt

**Version:** 1.1.0
**Status:** ACTIVE
**Document Type:** Session Bootstrap and Working Protocol

---

## 1. PURPOSE

Questo documento definisce il protocollo operativo da utilizzare per una
nuova sessione di lavoro sul repository ELR.

Il Prompt non costituisce una fonte autonoma di verità architetturale.

Il suo scopo è:

* inizializzare la sessione;
* indicare come recuperare il contesto corrente;
* definire il metodo di lavoro;
* impedire che decisioni architetturali vengano ricostruite dalla memoria
  conversazionale;
* definire le regole di verifica del repository.

---

Repository:

`https://github.com/cybersim81/ELR`

Il repository è la fonte di verità per lo stato architetturale ELR.

Non ricostruire decisioni dalla memoria della conversazione precedente
quando tali decisioni possono essere verificate nel repository.

### Step 6 — Determina la fase corrente

La fase corrente non deve essere hardcoded in questo Prompt.

1. Roadmap;

**Fase 8 — Implementation Readiness Review**

Leggi solamente le Specification, ADR, Matrix e altri documenti direttamente
pertinenti al lavoro corrente.

Non ricreare documenti già presenti.

Non riaprire documenti verificati senza una contraddizione concreta.

## 4. SOURCE OF TRUTH

Il repository è la fonte di verità.

In caso di divergenza tra:

* memoria conversazionale;
* Prompt;
* Continuity Package;
* Handoff;
* implementazione;
* documentazione;

la divergenza deve essere verificata.

Non risolvere una divergenza mediante memoria o supposizioni.

Per risolverla:

1. identifica i documenti coinvolti;
2. verifica status e versione;
3. identifica il documento proprietario del concetto;
4. verifica eventuali ADR applicabili;
5. verifica la Consistency Matrix;
6. verifica la Roadmap;
7. applica il processo di decisione architetturale.

---

## 5. ARCHITECTURAL WORKING RULES

Durante il lavoro:

* non inferire il Domain Model dal Persistence Model;
* non inferire decisioni architetturali dall'implementazione ORM;
* non attribuire autorità architetturale a una struttura solo perché
  esiste nel codice;
* non introdurre nuove responsabilità senza verificarne l'ownership;
* non creare Specification duplicate;
* non riaprire decisioni APPROVED senza una contraddizione documentale
  reale;
* distinguere Domain Model, Process Model, Evidence Model, Mastery Engine
  e Persistence Model;
* verificare status e versioni dei documenti prima di proporre modifiche;
* non trasformare una verifica documentale in una nuova decisione
  architetturale senza evidenza di una reale contraddizione;
* considerare le specifiche consolidate frozen rispetto ai confini già
  verificati, salvo contraddizione reale.

L'implementazione esistente costituisce evidenza tecnica, non
automaticamente autorità architetturale.

---

## 6. DOCUMENT AUTHORITY

Quando emerge un conflitto documentale:

1. identifica le specifiche coinvolte;
2. verifica status e versione;
3. confronta le definizioni esplicite;
4. identifica il documento proprietario;
5. verifica eventuali decisioni ADR;
6. verifica la Consistency Matrix;
7. verifica la Roadmap;
8. proponi una riconciliazione solo dopo questa verifica.

Una bozza non può silenziosamente sovrascrivere una decisione APPROVED.

Una struttura di persistence non può essere utilizzata per dedurre un
concetto del Domain Model.

Una implementazione non può risolvere silenziosamente una discrepanza
documentale.

---

## 7. DECISION WORKFLOW

Mantieni sempre il seguente ciclo:

**discrepanza/problema → verifica documentale → proposta → approvazione →
blocco copiabile → aggiornamento repository → verifica → prossimo punto**

### Regole

* proponi una sola decisione focalizzata alla volta;
* attendi approvazione esplicita;
* non considerare una proposta definitiva prima dell'approvazione;
* dopo l'approvazione produci il blocco copiabile;
* indica il documento e la sezione da modificare;
* dopo l'aggiornamento verifica il repository;
* verifica anche i boundary immediatamente adiacenti;
* solo dopo procedi al punto successivo.

---

## 8. REPOSITORY WRITE CONSTRAINT

L'integrazione GitHub è attualmente verificata come segue:

**READ → AVAILABLE**

**WRITE → UNAVAILABLE**

I tentativi di scrittura diretta hanno restituito:

**HTTP 403 — Forbidden**

Pertanto:

* non dichiarare mai una modifica come applicata sulla sola base di un
  tentativo di scrittura;
* se una scrittura diretta restituisce `403`, considera la scrittura non
  applicata;
* produci il blocco copiabile;
* l'utente applica manualmente la modifica;
* recupera nuovamente il file dal repository;
* verifica il contenuto aggiornato;
* considera la modifica effettivamente applicata solo dopo verifica READ.

Il `403` è un vincolo operativo dell'integrazione e non una decisione
architetturale ELR.

Dopo il bootstrap:

1. identifica la fase corrente;
2. identifica il prossimo lavoro autorizzato;
3. verifica quali artefatti esistono già;
4. identifica i documenti proprietari;

8. verifica la tracciabilità tra Specification e componenti implementativi;
9. identifica le decisioni tecniche residue;
10. definisci la sequenza di implementazione e i primi contract checks;
11. proponi il primo passo concreto.

Non inventare lavoro già completato.

Non assumere che un'attività sia aperta solo perché lo era in una
precedente sessione.

Non anticipare la Fase 9 finché la Fase 8 non è stata completata.

## 10A. VISIBILITÀ DEL PROGRESSO DI FASE

Durante il lavoro attivo, la sessione deve fornire periodicamente una mappa
sintetica del progresso relativa alla fase corrente.

La mappa di progresso deve:

* identificare la fase corrente e il relativo obiettivo;
* elencare i principali punti di lavoro e i relativi sottopunti;
* indicare ogni punto con:
  * `[ ]` non iniziato;
  * `[~]` in elaborazione;
  * `[x]` verificato/completato;
* distinguere chiaramente tra lavoro già verificato, lavoro attualmente in
  elaborazione e lavoro ancora pianificato;
* identificare il checkpoint o gate previsto per la fase;
* indicare quando il lavoro si avvicina a un punto di chiusura pulito della
  sessione.

La mappa di progresso è uno strumento operativo e non costituisce una fonte
aggiuntiva di autorità architetturale.

Non deve essere utilizzata per introdurre, approvare o modificare
silenziosamente decisioni architetturali.

Quando una fase raggiunge un checkpoint significativo, l'assistente deve
indicare esplicitamente che il checkpoint è prossimo o è stato raggiunto e
proporre una verifica del repository e degli artefatti di continuità prima
della chiusura della sessione.

Lo scopo di questa visibilità del progresso è duplice:

1. consentire all'utente di comprendere la distanza dal successivo checkpoint
   architetturale o implementativo;
2. consentire all'utente e all'assistente di valutare l'efficienza del
   workflow prima della chiusura della sessione.

In prossimità di un checkpoint, l'assistente deve riepilogare, quando utile:

* lavoro completato;
* finding emersi;
* decisioni necessarie;
* decisioni non necessarie perché già definite da documenti autorevoli;
* lavoro rimanente;
* prossima azione autorizzata;
* eventuale necessità di aggiornare gli artefatti di continuità.

Un checkpoint non deve essere considerato completato solamente perché il
lavoro conversazionale appare concluso.

Il checkpoint deve essere verificato sulla base delle evidenze del repository,
secondo le regole esistenti di verifica e chiusura della sessione.

## 11. APPROVED DECISIONS

Le decisioni APPROVED devono essere recuperate dai relativi documenti
autoritativi.

Non utilizzare questo Prompt come archivio sostitutivo delle decisioni.

Non riaprire una decisione APPROVED salvo che emerga una contraddizione
documentale reale nel repository.

Se emerge una contraddizione:

**contraddizione → verifica → identificazione dell'autorità → proposta di
riconciliazione → approvazione**

## 12. SESSION COMPLETION

Un'attività documentale è considerata completata solamente quando:

* la decisione è stata approvata;
* il blocco documentale è stato prodotto;
* il repository è stato aggiornato;
* il contenuto aggiornato è stato verificato;
* eventuali documenti di continuità interessati sono stati riallineati.

Una modifica non verificata nel repository non deve essere dichiarata
completata.

### Canonical Naming and Version Resolution

I continuity artifacts hanno un **canonical logical name** indipendente dalla
versione fisica del file.

Il canonical name identifica l'artefatto logico.

Il filename versionato identifica la specifica versione corrente dell'artefatto
nel repository.

Esempio:

| Canonical name                           | Current repository file                            |
| ---------------------------------------- | -------------------------------------------------- |
| `ELR Roadmap`                            | `ELR Roadmap 1.2.1.txt`                            |
| `ELR Session Prompt`                     | `ELR Session Prompt 1.1.0.txt`                     |
| `ELR Continuity Package`                 | `ELR Continuity Package 2.0.0.txt`                 |
| `ELR Architectural Work State — Handoff` | `ELR Architectural Work State - Handoff 6.0.0.txt` |

Regola operativa:

* usare il **canonical name** quando si identifica semanticamente un
  documento;
* usare il **current versioned filename** quando si deve leggere, modificare
  o verificare un file nel repository;
* risolvere sempre il canonical name nel filename/versione corrente tramite
  repository evidence;
* non assumere che una versione precedente del filename sia ancora valida;
* non creare un nuovo canonical name solamente perché cambia la versione;
* quando un documento viene versionato, aggiornare i riferimenti fisici
  necessari nei continuity artifacts;
* il canonical name rimane stabile mentre il versioned filename rappresenta
  la versione corrente.

Il repository è l'autorità per la risoluzione:

**canonical name → current versioned filename**

La versione dichiarata nei documenti di continuità deve essere verificata
contro il file effettivamente presente nel repository.
