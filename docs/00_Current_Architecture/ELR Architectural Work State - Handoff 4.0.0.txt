## 6. WORKING METHOD

Use the following process:

**verification → focused problem or architectural gap → document analysis
→ one focused proposal → explicit approval → copyable documentation block
→ repository update → repository verification → next point**

Do not treat a proposal as an approved decision.

Do not treat an unverified repository write as an applied change.

Do not advance to the next architectural point until the current change,
when applicable, has been verified.

---

## 7. ARCHITECTURAL CONTINUITY RULES

The following rules remain in force:

* the repository is the source of truth;
* approved architectural decisions must not be reopened without a real
  documented contradiction;
* implementation does not acquire architectural authority merely because
  it exists;
* Domain semantics must not be inferred from ORM or persistence
  structures;
* each architectural responsibility must have an identifiable owning
  document;
* new architectural decisions require explicit approval;
* specifications must remain consistent with approved architectural
  decisions.

For detailed rules, use the ELR Continuity Package and the authoritative
repository documents.

## 8. GITHUB INTEGRATION STATUS

The GitHub integration has been operationally verified.

### READ

**Available.**

Repository files can be retrieved and inspected.

### WRITE

**Unavailable in the current integration state.**

Direct write attempts have returned:

**HTTP 403 — Forbidden**

Therefore:

* never claim that a repository modification was applied solely because
  a write operation was attempted;
* when direct write is unavailable, provide the exact copyable block;
* after the user applies the change, retrieve the repository file again;
* verify the complete modified section and its boundaries;
* only then mark the change as applied.

This is an operational tooling constraint and does not affect ELR
architectural authority.

A new session should:

3. read the current Roadmap;

5. identify the current Phase 6 artifacts;

decisions.

repository.

## 10. CHECKPOINT RULE

This document is a checkpoint, not a historical transcript.

When a new architectural phase is completed, this Handoff should be
updated so that:

* the completed phase is recorded;
* the current phase is identified;

* obsolete historical working details are removed or superseded.

The Handoff should remain concise enough to be useful as a session
