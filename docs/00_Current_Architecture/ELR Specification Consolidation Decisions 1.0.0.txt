# 2. Purpose
================================================================================

This document records the decisions made during M0.2 to resolve identified
differences, ambiguities and inconsistencies between the current ELR
specifications and the existing implementation baseline.

The purpose of this document is to establish an explicit decision record
before the affected specifications and implementation are modified.

This document does not replace the authoritative specifications.

Instead, it records the decisions that must subsequently be propagated into
the affected specifications and implementation.

No implementation change is authorized merely by the existence of a decision
in this document.


================================================================================
# 3. Context
================================================================================

The ELR project has completed its architectural design phase through Phase 10.

The repository has subsequently been inspected to establish the actual
implementation baseline.

The implementation baseline demonstrates substantial existing work in:

* Domain entities
* Domain repository abstractions
* Application services
* Automated tests
* Initial persistence models

However, the implementation is incomplete and contains several divergences
from the current specifications.

M0.2 exists to resolve the most consequential specification-level issues
before further implementation work is performed.


================================================================================
# 4. Consolidation Principles
================================================================================

The following principles govern the decisions recorded in this document.

1. Domain semantics take precedence over accidental implementation structure.

2. Stable Identity must be distinguished from Version Identity.

3. Aggregate membership must be distinguished from autonomous Domain Entity
   status.

4. Lifecycle state must be distinguished from process outcome, review
   decision and mutation operation.

5. Persistence representation must not introduce Domain semantics that do not
   exist in the Domain Model.

6. Historical information must remain recoverable.

7. Transactional consistency must be preserved between domain mutation,
   Version, Audit Record and Transactional Event Record.

8. The Domain Model must remain independent of specific infrastructure
   technologies.

9. Existing implementation must be reconciled with the consolidated model
   rather than assumed to be authoritative merely because it exists.

10. Decisions must be recorded before implementation changes are made in the
    affected areas.

# 6. M0.2.1 — Learning Object Lifecycle
================================================================================

Decision ID:

M0.2.1


Decision:

The persistent Learning Object lifecycle consists exclusively of:

* Candidate
* Proposed
* Active
* Retired

Review outcomes, approval decisions and update operations are process-level
or versioning-level concepts and are not persistent Learning Object lifecycle
states.


Rationale:

This separates aggregate lifecycle from process outcomes and versioning
operations, avoiding the conflation of state, decision and mutation.


Implementation consequence:

The existing lifecycle implementation must eventually be reconciled with
this model.

No implementation change is made during M0.2.1.


================================================================================
# 7. M0.2.2 — KnowledgeStatement Domain Representation
================================================================================

Decision ID:

M0.2.2


Decision:

KnowledgeStatement is part of the LearningObject aggregate and is not an
autonomous Domain Entity.

KnowledgeStatement has no independent Stable Identity, no independent
repository and no independent lifecycle.

A change to the KnowledgeStatement of an existing LearningObject does not
create a new LearningObject identity.


Rationale:

KnowledgeStatement describes the knowledge represented by the LearningObject
and has no independent existence within the ELR Domain Model.


Implementation consequence:

The existing autonomous KnowledgeStatement domain entity is considered
legacy/divergent implementation and must be reconciled with the consolidated
Domain Model before the Core Domain implementation is finalized.

No implementation change is made during M0.2.2.


================================================================================
# 8. M0.2.3 — KnowledgeStatement Persistence Mapping
================================================================================

Decision ID:

M0.2.3


Decision:

KnowledgeStatement is persisted as part of the LearningObject persistence
representation.

The canonical persistence representation stores the KnowledgeStatement value
within the LearningObject record.

No independent knowledge_statements persistence entity is required.

KnowledgeStatement does not receive an independent persistence identity that
is exposed as a Domain Identity.


Rationale:

KnowledgeStatement is an element of the LearningObject aggregate and has no
independent Domain identity, lifecycle or repository.

Keeping its persistence representation within LearningObject preserves the
aggregate boundary and avoids introducing an artificial persistence entity.


Implementation consequence:

The current knowledge_statements persistence design described in older
implementation material is considered superseded.

The existing app/domain/entities/knowledge_statement.py implementation is
legacy/divergent and must eventually be removed or transformed into an
appropriate value representation.

No implementation change is made during M0.2.3.


================================================================================
# 9. M0.2.4 — Versioning Semantics
================================================================================

Decision ID:

M0.2.4


Decision:

A LearningObject maintains its Stable Identity throughout its complete
lifecycle.

Changes to the knowledge represented by an existing LearningObject do not
create a new LearningObject identity when the underlying knowledge remains
conceptually the same.

Each persisted evolution of the LearningObject representation produces a new
immutable Version.

A Version represents a historical snapshot of the LearningObject
representation at a specific point in its evolution.

The current representation of a LearningObject is the latest valid Version
associated with its Stable Identity.

Versions are immutable.

Historical Versions must remain recoverable after subsequent updates.


Rationale:

ELR must preserve both the current usable representation of knowledge and its
historical evolution.

This formalizes the original repository concept of applying changes to a
persistent knowledge base while providing explicit identity, versioning and
audit semantics.


Implementation consequence:

The persistence layer must distinguish:

* LearningObject Stable Identity;
* current representation;
* immutable historical Versions;
* audit records.

Updating a LearningObject must never overwrite or destroy the historical
representation required for Version recovery.

A change proposal or patch may be used as an operational mechanism for
describing a proposed change, but a patch is not itself the canonical
persistence representation of the LearningObject.

The canonical persistent representation consists of the LearningObject Stable
Identity together with its Version History.

No implementation change is made during M0.2.4.


================================================================================
# 10. M0.2.5 — Transactional Event Boundary
================================================================================

Decision ID:

M0.2.5


Decision:

A persistent LearningObject mutation is treated as a single transactional
operation.

When a mutation produces a new Version, the following persistence operations
must belong to the same transaction:

* LearningObject state mutation;
* creation of the new immutable Version;
* creation of the corresponding Audit Record;
* creation of the corresponding Transactional Event Record.

The transaction must either commit all required records or roll back the
complete operation.

A Transactional Event Record represents the durable fact that the domain
mutation occurred.

The Event Record is persisted before the surrounding transaction commits.

Event publication to an external transport or consumer is a separate concern
from transactional event persistence.

Failure to publish an event externally after the database transaction has
committed must not invalidate the already committed domain mutation.

The Transactional Event Record therefore acts as the durable handoff between
the ELR transactional core and any external event delivery mechanism.


Rationale:

ELR requires consistency between current state, historical Version, audit
history and the recorded domain event.

Persisting these records independently could produce states in which a
LearningObject has changed without a corresponding Version, Audit Record or
Event Record, or in which an event exists for a mutation that was rolled back.

Separating transactional event persistence from external event publication
also preserves technology agnosticism and prevents the domain model from
depending on a specific messaging infrastructure.


Implementation consequence:

The persistence/application infrastructure must provide a transaction
boundary capable of atomically committing:

LearningObject mutation
+
Version
+
Audit Record
+
Transactional Event Record

Concrete event publication mechanisms must operate outside the domain model
and must not determine the success or failure of the domain mutation after
the transactional record has been committed.

No implementation change is made during M0.2.5.

# 12. Consolidated Persistence Consequences
================================================================================

The persistence architecture must distinguish between:

* LearningObject Stable Identity
* Current representation
* Version History
* Audit Records
* Transactional Event Records


KnowledgeStatement is persisted as part of the LearningObject representation
and does not require an independent domain-level persistence identity.


A LearningObject mutation must preserve the historical representation needed
to reconstruct previous Versions.


The persistence transaction must atomically coordinate:

* LearningObject mutation
* Version creation
* Audit creation
* Transactional Event Record creation


External event publication is not part of the domain transaction.

# 19. Final M0.2 Statement
================================================================================

M0.2 has converted the principal implementation-blocking conceptual
ambiguities identified during the repository baseline assessment into explicit
decisions.

The decisions establish:

* LearningObject as the stable aggregate identity;
* KnowledgeStatement as an aggregate value;
* a four-state persistent LearningObject lifecycle;
* immutable Version history;
* explicit audit history;
* transactional event persistence;
* separation between transactional persistence and external event publication.

These decisions provide the conceptual bridge between the architectural
design and the implementation phase.

They do not constitute implementation completion.

The next required activity is specification propagation and documentation
alignment.
