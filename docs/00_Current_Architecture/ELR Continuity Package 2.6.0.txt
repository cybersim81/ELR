# 1. PURPOSE

This document defines the persistent continuity model for ELR architectural
and implementation work across separate sessions.

Its purpose is to ensure that a new session can reconstruct the current
working state from repository evidence without relying on conversational
memory.

The repository is the source of truth.

This document does not replace:

* Architecture Specification;
* Architecture Decision Log;
* Architecture Consistency Matrix;
* domain specifications;
* implementation specifications;
* implementation plans;
* Roadmap;
* Handoff;
* Session Prompt;
* Current Implementation Checkpoint.

It defines how those artifacts are used together for continuity.

---

# 2. SOURCE OF TRUTH

The ELR repository is the authoritative source for:

* document existence;
* document content;
* document version;
* canonical document identity;
* current versioned filename;
* architecture decisions;
* implementation state;
* roadmap state;
* continuity state;
* verification evidence.

Conversational memory must not override repository evidence.

If the current repository state differs from a previous conversation, the
repository state is authoritative.

---

# 3. CANONICAL DOCUMENT IDENTITY

ELR continuity artifacts distinguish between:

* canonical logical name;
* versioned repository filename.

The canonical logical name identifies the artifact independently of version.

The versioned repository filename identifies the current physical document
version stored in the repository.

A version change does not create a new canonical identity.

---

# 5. VERSION RESOLUTION RULES

When opening or modifying a continuity artifact:

1. identify the canonical document name;
2. inspect the repository;
3. determine the current versioned filename;
4. verify the version contained in the document;
5. verify that all continuity references point to the current version;
6. only then perform READ, WRITE or VERIFY operations.

A reference to a canonical name must not silently imply a historical version.

A reference to a versioned filename must be verified explicitly against the
repository.

# 16. ARCHITECTURAL AUTHORITY

The following principles remain mandatory:

* the repository is the source of truth;
* Architecture Specification defines architectural responsibility;
* Architecture Decision Log records architectural decisions;
* Architecture Consistency Matrix records cross-document consistency;
* specifications define detailed behavior;
* implementation does not acquire architectural authority merely because it
  exists;
* persistence structures must not be used to infer Domain semantics;
* Domain semantics must not be inferred from ORM structures;
* approved architectural decisions must not be reopened without a real
  documented contradiction;
* implementation findings must not silently become architectural changes.

---

# 17. FROZEN SPECIFICATION RULE

The specifications consolidated during the Specification Consistency checkpoint
remain frozen with respect to their verified architectural boundaries.

They must not be reopened merely to:

* improve wording;
* introduce implementation preferences;
* accommodate an ORM structure;
* accommodate an existing code structure;
* change a previously approved architectural decision without contradiction.

A real contradiction may trigger a controlled reopening.

The Implementation Readiness Review and completed architectural checkpoints
remain closed unless new evidence requires controlled reassessment.

# 19. SESSION CLOSURE CHECKPOINT

A session may propose closure when:

* the current work item has a verified disposition;
* no partially applied correction remains;
* required tests have been executed;
* verification results are recorded;
* continuity artifacts describe the same state;
* the next authorized activity is explicit;
* the repository can reconstruct the working state without conversational
  memory.

The assistant must explicitly state when a clean checkpoint has been reached.

The assistant must not close the session automatically.

The user must explicitly approve closure.

# 21. SESSION RECOVERY RULE

A new session must be able to reconstruct the current state from repository
evidence alone.

Minimum reconstruction state:

* architectural position;
* implementation work package;
* last completed implementation finding;
* current implementation finding;
* next implementation finding;
* current verification baseline;
* current continuity artifact versions;
* current physical filenames.

If any of these cannot be established from repository evidence, continuity
must be considered incomplete.

The session must resolve the discrepancy before implementation work proceeds.

---

# 22. REOPENING RULE

Completed work must not be reopened without evidence.

Valid reopening evidence includes:

* authoritative contradiction;
* implementation regression;
* material specification change;
* newly discovered responsibility;
* explicit reassessment requirement.

Conversation history alone is not sufficient evidence.
