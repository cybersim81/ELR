Purpose:

This document establishes the normative ownership, authority boundaries and

It is an audit and coordination document.

It does not replace the specifications listed below.

It identifies which document owns each concept and identifies conflicts,

================================================================================
# 2. Context
================================================================================

This matrix was created to establish and maintain normative ownership,
authority boundaries and specification consistency across the ELR corpus.

It follows the architectural baseline established through Fase 10 and
supports the transition from architectural completion to the Product and
Implementation Roadmap.

The matrix is based on inspection of the current repository documentation and
implementation baseline.

Its purpose is to prevent multiple documents from independently defining the
same concept and to preserve the ELR principle of Single Document Ownership.

Specification consistency findings recorded in this matrix are documentation
and authority findings.

They do not by themselves constitute implementation milestone transitions.

The current product and implementation milestone is defined by the
ELR Product and Implementation Roadmap and the ELR Implementation Status
document.



================================================================================
# 3. Normative Authority Principles
================================================================================

The following rules apply to this matrix.


--------------------------------------------------------------------------------
AUTH-001 — Architecture Decision Authority
--------------------------------------------------------------------------------

The ELR Architecture Decision Log is the authoritative source for approved
architectural decisions.

Architectural specifications describe and organize the architecture derived
from those decisions.


--------------------------------------------------------------------------------
AUTH-002 — Domain Model Authority
--------------------------------------------------------------------------------

Core Domain Model specifications are authoritative for domain concepts,
aggregate boundaries, domain identity and domain semantics.


--------------------------------------------------------------------------------
AUTH-003 — Process Specification Authority
--------------------------------------------------------------------------------

Process specifications are authoritative for workflows and behavioural
processes operating on the Domain Model.


--------------------------------------------------------------------------------
AUTH-004 — Data and Persistence Authority
--------------------------------------------------------------------------------

Data and Persistence specifications are authoritative for canonical data and
persistence representation, subject to the constraints established by the
Domain Model.


--------------------------------------------------------------------------------
AUTH-005 — Interaction Authority
--------------------------------------------------------------------------------

Interaction specifications are authoritative for human-AI interaction
semantics and interaction protocols.


--------------------------------------------------------------------------------
AUTH-006 — System Specification Authority
--------------------------------------------------------------------------------

System specifications define technology-facing contracts and implementation
boundaries.

They must not redefine Domain Model semantics.


--------------------------------------------------------------------------------
AUTH-007 — Implementation Is Not Normative Authority
--------------------------------------------------------------------------------

Implementation code and automated tests describe the current implementation
baseline.

They provide evidence of implementation state.

They do not override contradictory normative specifications.


--------------------------------------------------------------------------------
AUTH-008 — Single Document Ownership
--------------------------------------------------------------------------------

Each architectural or domain concept must have one primary owner document.

Other documents may reference the concept.

Other documents must not independently redefine the concept unless explicitly
authorized by the architecture.

Associated shared linguistic reference; not a LearningObject aggregate member

Autonomous Versioning: NO

Persistence: YES

Normative interpretation:

* ADR-007 defines the Learning Object as associated with an Anchor.
* Anchor is outside the LearningObject aggregate boundary.
* Association does not imply containment or ownership.
* One Anchor may be associated with multiple independent Learning Objects.
* Anchor identity is independent of the identities of associated Learning Objects.
* Anchor is not independently versioned as a LearningObject Version.

Model and Versioning Model interpretations has been resolved by propagating
ADR-007 into the Domain Model and dependent specifications.

# 6. Versioning Classification
================================================================================

The following classification is normative for the consolidation process.


--------------------------------------------------------------------------------
6.1 Independently Versioned Domain Object
--------------------------------------------------------------------------------

LearningObject


--------------------------------------------------------------------------------
6.2 Versioned Historical Representation
--------------------------------------------------------------------------------

LearningObject Version


--------------------------------------------------------------------------------
6.3 Aggregate Members
--------------------------------------------------------------------------------

* KnowledgeStatement
* Examples
* Notes
* other LearningObject-owned content values

These evolve through LearningObject Versioning.

They are not independently versioned Domain Entities merely because their
values may be represented separately in persistence.

Anchor is not an aggregate member.

Anchor is an associated shared linguistic reference outside the
LearningObject aggregate boundary.

Anchor may be associated with multiple independent Learning Objects and has
its own persistent identity.

Anchor is not independently versioned as a LearningObject Version.


--------------------------------------------------------------------------------
6.4 Separately Versioned Reference / Structural Models
--------------------------------------------------------------------------------

Potential examples:

* Taxonomy
* Repository Schema
* API Contract

Their versioning is structurally distinct from LearningObject Versioning.


--------------------------------------------------------------------------------
6.5 Process / Learner State
--------------------------------------------------------------------------------

* Learning State
* Mastery State
* Evidence

These evolve according to their own process semantics.

They are not LearningObject Versions.


--------------------------------------------------------------------------------
6.6 Historical / Operational Records
--------------------------------------------------------------------------------

* Audit Record
* Transactional Event Record
* Published Event

These preserve operational history.

They are not LearningObject Versions.

# 7. Confirmed Conflicts
================================================================================

The following conflicts are currently confirmed.


CONFLICT-001

Concept:

KnowledgeStatement Persistence

Status:

RESOLVED

Resolution:

The ELR Data Model Specification and ELR Persistence Model Specification
now represent KnowledgeStatement as part of the LearningObject persistence
representation.

KnowledgeStatement does not constitute an independently persisted domain
entity.

It does not possess an independent repository or autonomous persistent
lifecycle.

Its persistence is subordinate to the owning LearningObject and its
versioned representation.

The previous cross-specification inconsistency is therefore closed.

No further specification propagation action is required for this conflict.


CONFLICT-002

Concept:

KnowledgeStatement Versioning

Status:

RESOLVED

Resolution:

The ELR Versioning Model Specification now defines LearningObject as the
primary unit of knowledge versioning.

KnowledgeStatement is not an independently versioned Domain Entity.

Changes to KnowledgeStatement are represented through evolution of the
owning LearningObject and its immutable Versions.

KnowledgeStatement therefore does not possess an autonomous version history
independent of the LearningObject.

The previous cross-specification inconsistency is therefore closed.

No further specification propagation action is required for this conflict.



CONFLICT-003

Concept:

Anchor Boundary / Versioning

Status:

RESOLVED

Resolution:

ADR-007, Domain Model 1.1.0, Anchor Specification 1.1.0, Data Model 1.0.0,
Persistence Model 1.0.0 and Versioning Model 1.0.0 now use the same semantic
boundary.

The Learning Object is associated with an Anchor.

The Anchor:

* is outside the LearningObject aggregate boundary;
* is not owned by the Learning Object;
* may be associated with multiple independent Learning Objects;
* has its own persistent identity;
* is not independently versioned as a LearningObject Version.

The previous cross-specification inconsistency is therefore closed.

No Anchor-specific contradiction remains in the verified specification chain.



CONFLICT-004

Concept:

KnowledgeCategory Versioning

Status:

RESOLVED

Resolution:

The ELR Versioning Model explicitly distinguishes taxonomy and reference
model evolution from LearningObject content version evolution.

KnowledgeCategory is a taxonomy classification reference.

Its taxonomy identity and evolution are not LearningObject Version history.

No further specification propagation action is required for this conflict.

GAP-004

Status:

RESOLVED

Resolution:

The ELR Architecture Consistency Matrix 1.1.0 has been reviewed and aligned

The ELR Architecture Decision Log 1.0.0 has also been reviewed.

================================================================================
# 12. Consolidation Rules
================================================================================

Rule 1:

Do not modify implementation to compensate for contradictory specifications
before the specifications are reconciled.


Rule 2:

Do not modify a document merely because another document uses different
terminology.

First determine whether the difference is semantic or terminological.


Rule 3:

When a genuine contradiction exists, update the document that does not own
the concept.


Rule 4:

When ownership is unclear, resolve ownership before modifying content.


Rule 5:

Do not create a new specification merely to avoid updating an existing
authoritative specification.


Rule 6:

Do not allow implementation structure to create artificial domain concepts.


Rule 7:

Tests should verify the consolidated model after implementation alignment;
they should not define the model independently.
