# ELR Session Prompt

**Version:** 1.2.0
**Status:** ACTIVE
**Document Type:** Session Bootstrap and Working Protocol

---

## 1. PURPOSE

Questo documento definisce il protocollo operativo da utilizzare per una
nuova sessione di lavoro sul repository ELR.

Il Prompt non costituisce una fonte autonoma di verità architetturale.

Il suo scopo è:

* inizializzare la sessione;
* indicare come recuperare il contesto corrente;
* definire il metodo di lavoro;
* impedire che decisioni architetturali vengano ricostruite dalla memoria
  conversazionale;
* definire le regole di verifica del repository.

---

## 2. REPOSITORY

Repository:

`https://github.com/cybersim81/ELR`

Il repository è la fonte di verità per lo stato architetturale ELR.

Non ricostruire decisioni dalla memoria della conversazione precedente
quando tali decisioni possono essere verificate nel repository.

## 3. SESSION BOOTSTRAP

All'inizio di una nuova sessione:

### Step 1 — Leggi questo documento

Recupera il **current versioned filename** di:

`ELR Session Prompt`

tramite la regola di `Canonical Naming and Version Resolution` definita
in §13.

### Step 2 — Leggi il Continuity Package

Recupera il **current versioned filename** di:

`ELR Continuity Package`

tramite la regola di `Canonical Naming and Version Resolution`.

### Step 3 — Leggi l'Handoff

Recupera il **current versioned filename** di:

`ELR Architectural Work State - Handoff`

tramite la regola di `Canonical Naming and Version Resolution`.

### Step 4 — Leggi la Roadmap

Recupera il **current versioned filename** di:

`ELR Roadmap`

tramite la regola di `Canonical Naming and Version Resolution`.

La Roadmap determina la posizione corrente del lavoro e le attività
successive autorizzate.

### Step 5 — Verifica il repository

Non assumere che i documenti di continuità siano aggiornati solo perché
la conversazione precedente lo suggerisce.

Verifica sempre il contenuto effettivo dei documenti nel repository.

La versione dichiarata da un continuity artifact deve essere verificata
contro il file effettivamente presente nel repository.

### Step 6 — Determina la fase corrente

La fase corrente non deve essere hardcoded in questo Prompt.

Deve essere determinata verificando:

1. Roadmap;
2. Continuity Package;
3. Handoff;
4. repository state.

Il Prompt definisce il metodo per determinare la posizione corrente, ma non
conserva la posizione corrente stessa.

### Step 7 — Recupera i documenti specialistici rilevanti

Leggi solamente le Specification, ADR, Matrix e altri documenti direttamente
pertinenti al lavoro corrente.

Non ricreare documenti già presenti.

Non riaprire documenti verificati senza una contraddizione concreta, una
modifica del documento, una nuova versione, un nuovo finding o altra
evidenza che richieda una nuova verifica.

---

## 4. SOURCE OF TRUTH

Il repository è la fonte di verità.

In caso di divergenza tra:

* memoria conversazionale;
* Prompt;
* Continuity Package;
* Handoff;
* implementazione;
* documentazione;

la divergenza deve essere verificata.

Non risolvere una divergenza mediante memoria o supposizioni.

Per risolverla:

1. identifica i documenti coinvolti;
2. verifica status e versione;
3. identifica il documento proprietario del concetto;
4. verifica eventuali ADR applicabili;
5. verifica la Consistency Matrix;
6. verifica la Roadmap;
7. applica il processo di decisione architetturale.

---

## 5. ARCHITECTURAL WORKING RULES

Durante il lavoro:

* non inferire il Domain Model dal Persistence Model;
* non inferire decisioni architetturali dall'implementazione ORM;
* non attribuire autorità architetturale a una struttura solo perché
  esiste nel codice;
* non introdurre nuove responsabilità senza verificarne l'ownership;
* non creare Specification duplicate;
* non riaprire decisioni APPROVED senza una contraddizione documentale
  reale;
* distinguere Domain Model, Process Model, Evidence Model, Mastery Engine
  e Persistence Model;
* verificare status e versioni dei documenti prima di proporre modifiche;
* non trasformare una verifica documentale in una nuova decisione
  architetturale senza evidenza di una reale contraddizione;
* considerare le specifiche consolidate frozen rispetto ai confini già
  verificati, salvo contraddizione reale.

L'implementazione esistente costituisce evidenza tecnica, non
automaticamente autorità architetturale.

---

## 6. DOCUMENT AUTHORITY

Quando emerge un conflitto documentale:

1. identifica le specifiche coinvolte;
2. verifica status e versione;
3. confronta le definizioni esplicite;
4. identifica il documento proprietario;
5. verifica eventuali decisioni ADR;
6. verifica la Consistency Matrix;
7. verifica la Roadmap;
8. proponi una riconciliazione solo dopo questa verifica.

Una bozza non può silenziosamente sovrascrivere una decisione APPROVED.

Una struttura di persistence non può essere utilizzata per dedurre un
concetto del Domain Model.

Una implementazione non può risolvere silenziosamente una discrepanza
documentale.

## 6A. DOCUMENT NAVIGATION AND VERIFICATION

Quando il lavoro richiede di individuare, verificare o confrontare un
concetto architetturale o processuale, la navigazione del repository deve
seguire la gerarchia documentale già definita da ELR.

### Regola primaria

Prima di utilizzare una ricerca testuale generica nel repository:

1. consultare la `Architecture Consistency Matrix`;
2. identificare il documento proprietario del concetto;
3. seguire eventuali dipendenze e riferimenti dichiarati dal documento
   proprietario;
4. individuare il file fisico corrente tramite il repository;
5. leggere il documento proprietario prima di formulare conclusioni sul
   concetto.

La `Architecture Consistency Matrix` deve essere utilizzata come mappa
semantica di navigazione e ownership, non soltanto come strumento di
verifica finale.

### Regola di ownership

Se la Matrix identifica un documento come proprietario di un concetto,
quel documento costituisce la fonte primaria per verificarne:

* significato;
* responsabilità;
* comportamento;
* struttura;
* regole operative.

Non cercare di ricostruire tali informazioni attraverso documenti
secondari quando il documento proprietario è individuabile.

### Regola di ricerca

La ricerca testuale nel repository è uno strumento di supporto.

Un risultato di ricerca negativo NON deve essere interpretato come prova
dell'assenza di un concetto, di una specifica o di una regola.

Analogamente, un risultato parziale o troncato non deve essere interpretato
come contenuto completo del documento.

Se il recupero di un documento è incompleto:

1. non considerare il contenuto recuperato come rappresentazione completa
   del documento;

2. determinare se il documento può essere recuperato tramite segmenti o
   intervalli di righe;

3. se il documento è segmentabile, recuperarlo attraverso blocchi
   consecutivi sufficientemente piccoli da garantire un contenuto integro;

4. verificare che i blocchi coprano l'intero documento necessario
   all'analisi;

5. utilizzare il contenuto aggregato dei blocchi come base per la verifica;

6. se anche il recupero segmentato non consente di ottenere il contenuto
   necessario, dichiarare esplicitamente la limitazione e non formulare
   conclusioni basate su contenuto non verificato.

Un documento lungo non deve essere considerato non recuperabile solo perché
un recupero completo viene troncato.

Il recupero segmentato costituisce una modalità ordinaria di verifica per
documenti lunghi.

Quando un documento viene utilizzato per una decisione o una modifica,
deve essere verificato nella misura necessaria a escludere che le sezioni
non ancora lette contengano informazioni rilevanti o contraddittorie.

### Regola di navigazione gerarchica

Quando un concetto conduce ad altri concetti correlati, seguire la catena
documentale indicata dall'architettura.

Schema preferenziale:

Architecture
→ Ownership / Consistency Matrix
→ Documento proprietario
→ Dipendenze dichiarate
→ Process / Domain / System specification rilevanti
→ Implementazione

Non utilizzare la ricerca libera per sostituire questa catena quando essa
è già disponibile.

### Regola contro le supposizioni sui path

Non inventare filename o path sulla base del nome logico di un documento.

Se un documento è indicato come proprietario ma il path fisico non è noto:

1. verificare l'albero della directory pertinente;
2. verificare eventuali riferimenti nel repository;
3. identificare il filename/versione corrente;
4. solo successivamente leggere il documento.

Il canonical name e il filename fisico versionato devono essere distinti
secondo le regole di `Canonical Naming and Version Resolution`.

### Regola di conclusione

Prima di dichiarare un gap documentale verificare:

1. ownership;
2. documento proprietario;
3. versione/status;
4. contenuto effettivamente recuperato;
5. eventuali riferimenti ad altri documenti;
6. eventuali ADR o regole della Architecture Consistency Matrix.

Un limite dello strumento di lettura, un risultato di ricerca negativo o un
documento recuperato solo parzialmente non costituiscono da soli evidenza
di un gap architetturale.

La conclusione deve distinguere esplicitamente tra:

* **concetto assente dal repository**;
* **concetto presente ma non ancora verificato**;
* **documento presente ma non completamente recuperato**;
* **contraddizione documentale reale**.

## 6B. REPOSITORY MODIFICATION PROTOCOL

L'assistente non deve modificare direttamente il repository quando il lavoro
richiede una modifica documentale concordata con l'utente.

La modalità standard di modifica è:

1. verificare il documento corrente nel repository;

2. identificare con precisione la sezione da modificare;

3. formulare il contenuto della modifica come blocco copiabile;

4. indicare il path del file;

5. indicare se il blocco deve essere inserito, sostituito o eliminato;

6. indicare il punto preciso di inserimento o sostituzione;

7. attendere che l'utente applichi la modifica nel proprio ambiente;

8. verificare successivamente il risultato nel repository;

9. non considerare una modifica completata finché il contenuto effettivo
   del repository non è stato verificato.

L'assistente non deve modificare autonomamente un documento per propria
iniziativa, anche quando ritiene che una modifica sia tecnicamente
necessaria.

La proposta di modifica e l'applicazione della modifica sono attività
distinte.

Una modifica non verificata nel repository non deve essere presentata come
completata.

Quando una modifica coinvolge più documenti, ogni documento deve essere
verificato separatamente prima di considerare completato il relativo
checkpoint.

---

## 7. DECISION WORKFLOW

Mantieni sempre il seguente ciclo:

**discrepanza/problema → verifica documentale → proposta → approvazione →
blocco copiabile → aggiornamento repository → verifica → prossimo punto**

### Regole

* proponi una sola decisione focalizzata alla volta;
* attendi approvazione esplicita;
* non considerare una proposta definitiva prima dell'approvazione;
* dopo l'approvazione produci il blocco copiabile;
* indica il documento e la sezione da modificare;
* dopo l'aggiornamento verifica il repository;
* verifica anche i boundary immediatamente adiacenti;
* solo dopo procedi al punto successivo.

---

## 8. REPOSITORY WRITE CONSTRAINT

L'integrazione GitHub è attualmente verificata come segue:

**READ → AVAILABLE**

**WRITE → UNAVAILABLE**

I tentativi di scrittura diretta hanno restituito:

**HTTP 403 — Forbidden**

Pertanto:

* non dichiarare mai una modifica come applicata sulla sola base di un
  tentativo di scrittura;
* se una scrittura diretta restituisce `403`, considera la scrittura non
  applicata;
* produci il blocco copiabile;
* l'utente applica manualmente la modifica;
* recupera nuovamente il file dal repository;
* verifica il contenuto aggiornato;
* considera la modifica effettivamente applicata solo dopo verifica READ.

Il `403` è un vincolo operativo dell'integrazione e non una decisione
architetturale ELR.

## 9. CURRENT PHASE

Non assumere una fase corrente hardcoded in questo Prompt.

La fase corrente deve essere determinata verificando:

1. Roadmap corrente;
2. Continuity Package corrente;
3. Handoff corrente;
4. repository state.

Il Prompt definisce il metodo per determinare la posizione corrente, ma non
conserva la posizione corrente stessa.

Il prossimo passaggio deve essere determinato dalla posizione effettivamente
registrata nei continuity artifacts e verificata nel repository.

Una fase o un checkpoint già completato non deve essere riaperto
automaticamente all'inizio di una nuova sessione.

Deve essere riaperto solamente quando emerge nuova evidenza, inclusi:

* modifica del documento;
* nuova versione del documento;
* contraddizione;
* nuovo finding;
* modifica rilevante dell'implementazione;
* richiesta esplicita di rivalutazione.

## 10. CURRENT WORK

Dopo il bootstrap:

1. identifica la fase corrente;
2. identifica il prossimo lavoro autorizzato;
3. verifica quali artefatti esistono già;
4. identifica i documenti proprietari;
5. verifica eventuali discrepanze;
6. verifica solamente i documenti necessari al lavoro corrente;
7. verifica i contratti rilevanti per il punto operativo corrente;
8. verifica la tracciabilità tra Specification e componenti implementativi
   quando pertinente;
9. identifica le decisioni tecniche residue solo quando necessarie;
10. definisci il prossimo passo concreto;
11. prima di riaprire una verifica già completata, controlla se esiste
    nuova evidenza che ne giustifichi la riapertura.

Non inventare lavoro già completato.

Non assumere che un'attività sia aperta solo perché lo era in una
precedente sessione.

Non anticipare attività appartenenti a una fase successiva quando il
checkpoint della fase corrente non è stato superato.

Quando un checkpoint significativo è stato superato:

* registrare il risultato;
* identificare eventuali finding aperti;
* identificare la prossima posizione autorizzata;
* verificare se gli artefatti di continuità devono essere aggiornati;
* non ripetere automaticamente il lavoro del checkpoint appena chiuso.

Quando la sessione raggiunge un checkpoint pulito, è consentito interrompere
la sessione e riprendere dal checkpoint nella sessione successiva.

## 10A. VISIBILITÀ DEL PROGRESSO DI FASE

Durante il lavoro attivo, la sessione deve fornire periodicamente una mappa
sintetica del progresso relativa alla fase corrente.

La mappa di progresso deve:

* identificare la fase corrente e il relativo obiettivo;
* elencare i principali punti di lavoro e i relativi sottopunti;
* indicare ogni punto con:

  * `[ ]` non iniziato;
  * `[~]` in elaborazione;
  * `[x]` verificato/completato;
* distinguere chiaramente tra lavoro già verificato, lavoro attualmente in
  elaborazione e lavoro ancora pianificato;
* identificare il checkpoint o gate previsto per la fase;
* indicare quando il lavoro si avvicina a un punto di chiusura pulito della
  sessione.

La mappa di progresso è uno strumento operativo e non costituisce una fonte
aggiuntiva di autorità architetturale.

Non deve essere utilizzata per introdurre, approvare o modificare
silenziosamente decisioni architetturali.

Quando una fase raggiunge un checkpoint significativo, l'assistente deve
indicare esplicitamente che il checkpoint è prossimo o è stato raggiunto e
proporre una verifica del repository e degli artefatti di continuità prima
della chiusura della sessione.

Lo scopo di questa visibilità del progresso è duplice:

1. consentire all'utente di comprendere la distanza dal successivo checkpoint
   architetturale o implementativo;
2. consentire all'utente e all'assistente di valutare l'efficienza del
   workflow prima della chiusura della sessione.

In prossimità di un checkpoint, l'assistente deve riepilogare, quando utile:

* lavoro completato;
* finding emersi;
* decisioni necessarie;
* decisioni non necessarie perché già definite da documenti autorevoli;
* lavoro rimanente;
* prossima azione autorizzata;
* eventuale necessità di aggiornare gli artefatti di continuità.

Un checkpoint non deve essere considerato completato solamente perché il
lavoro conversazionale appare concluso.

Il checkpoint deve essere verificato sulla base delle evidenze del repository,
secondo le regole esistenti di verifica e chiusura della sessione.

## 11. APPROVED DECISIONS

Le decisioni APPROVED devono essere recuperate dai relativi documenti
autoritativi.

Non utilizzare questo Prompt come archivio sostitutivo delle decisioni.

Non riaprire una decisione APPROVED salvo che emerga una contraddizione
documentale reale nel repository.

Se emerge una contraddizione:

**contraddizione → verifica → identificazione dell'autorità → proposta di
riconciliazione → approvazione**

---

## 12. SESSION COMPLETION

Un'attività documentale è considerata completata solamente quando:

* la decisione è stata approvata;
* il blocco documentale è stato prodotto;
* il repository è stato aggiornato;
* il contenuto aggiornato è stato verificato;
* eventuali documenti di continuità interessati sono stati riallineati.

Una modifica non verificata nel repository non deve essere dichiarata
completata.

Un checkpoint significativo può costituire il punto di chiusura della
sessione quando:

* il checkpoint è stato verificato;
* non esistono finding bloccanti non gestiti;
* la prossima posizione autorizzata è identificabile;
* gli artefatti di continuità interessati sono stati verificati o il loro
  aggiornamento è stato esplicitamente identificato come prossimo lavoro.

Non è necessario proseguire la sessione oltre un checkpoint pulito
solamente per anticipare il lavoro della posizione successiva.

## 13. CONTINUITY MODEL

La continuità ELR utilizza quattro artefatti distinti:

### Session Prompt

Definisce:

**come deve lavorare la sessione.**

Path:

`docs/00_Current_Architecture/ELR Session Prompt *.txt`

### Continuity Package

Definisce:

**lo stato persistente e le regole di continuità.**

Path:

`docs/00_Current_Architecture/ELR Continuity Package *.txt`

### Architectural Work State — Handoff

Definisce:

**l'ultimo checkpoint operativo.**

Path:

`docs/00_Current_Architecture/ELR Architectural Work State - Handoff *.txt`

### Roadmap

Definisce:

**la posizione del lavoro, la sequenza delle fasi e il prossimo gate.**

Path:

`docs/00_Current_Architecture/ELR Roadmap *.txt`

Questi documenti hanno responsabilità diverse e non devono duplicarsi.

### Canonical Naming and Version Resolution

I continuity artifacts hanno un **canonical logical name** indipendente dalla
versione fisica del file.

Il canonical name identifica l'artefatto logico.

Il filename versionato identifica la specifica versione corrente dell'artefatto
nel repository.

Esempio:

| Canonical name                           | Current repository file                            |
| ---------------------------------------- | -------------------------------------------------- |
| `ELR Roadmap`                            | `ELR Roadmap 1.2.1.txt`                            |
| `ELR Session Prompt`                     | `ELR Session Prompt 1.2.0.txt`                     |
| `ELR Continuity Package`                 | `ELR Continuity Package 2.0.0.txt`                 |
| `ELR Architectural Work State — Handoff` | `ELR Architectural Work State - Handoff 6.0.0.txt` |

Regola operativa:

* usare il **canonical name** quando si identifica semanticamente un
  documento;
* usare il **current versioned filename** quando si deve leggere, modificare
  o verificare un file nel repository;
* risolvere sempre il canonical name nel filename/versione corrente tramite
  repository evidence;
* non assumere che una versione precedente del filename sia ancora valida;
* non creare un nuovo canonical name solamente perché cambia la versione;
* quando un documento viene versionato, aggiornare i riferimenti fisici
  necessari nei continuity artifacts;
* il canonical name rimane stabile mentre il versioned filename rappresenta
  la versione corrente.

Il repository è l'autorità per la risoluzione:

**canonical name → current versioned filename**

La versione dichiarata nei documenti di continuità deve essere verificata
contro il file effettivamente presente nel repository.

## 14. START COMMAND

Dopo aver completato il bootstrap:

**verifica il repository, determina la posizione corrente dai continuity
artifacts e inizia il prossimo lavoro autorizzato secondo la Roadmap.**

Non ricostruire il contesto dalla memoria conversazionale.

Non assumere che il lavoro precedente sia ancora aperto.

Non riaprire decisioni APPROVED senza una contraddizione documentale
reale.

Non riaprire automaticamente un checkpoint già completato.

Non introdurre nuova architettura durante il lavoro corrente salvo che emerga
una contraddizione architetturale reale.

Se il checkpoint precedente è stato superato e il repository non presenta
nuova evidenza che richieda la riapertura, riprendi direttamente dalla
successiva posizione autorizzata.

Procedi secondo il Decision Workflow definito in questo documento.
