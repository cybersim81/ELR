# 7. Domain Conformance Findings
================================================================================


--------------------------------------------------------------------------------
D1 — Learning Object Lifecycle Divergence
--------------------------------------------------------------------------------

Status:

DIVERGENT

The current implementation contains lifecycle states including:

* Candidate
* Proposed
* Reviewed
* Active
* Updated
* Retired
* Rejected

The current domain model specification defines the persistent Learning Object
lifecycle as:

* Candidate
* Proposed
* Active
* Retired

Review outcomes and process states such as Reviewed, Approved, Rejected and
Updated must not automatically be treated as persistent Learning Object
lifecycle states.

The existing implementation therefore reflects an earlier or divergent
lifecycle model.

Required action:

Resolve the authoritative lifecycle model before modifying the lifecycle
implementation.


--------------------------------------------------------------------------------
D2 — KnowledgeStatement Domain Representation Divergence
--------------------------------------------------------------------------------

Status:

DIVERGENT

The current implementation contains:

app/domain/entities/knowledge_statement.py

as an autonomous domain entity with its own identity and timestamps.

The current domain model specification defines KnowledgeStatement as a value
contained within LearningObject rather than as an autonomous domain Entity.

Required action:

Resolve the authoritative KnowledgeStatement representation before further
domain or persistence implementation.


--------------------------------------------------------------------------------
D3 — Existing Domain Implementation Should Not Be Discarded
--------------------------------------------------------------------------------

Status:

PRESERVE / REFACTOR AS REQUIRED

Despite the divergences above, the current domain implementation contains
substantial useful work.

The implementation should therefore be treated as an existing baseline to be
reconciled with the current specifications rather than discarded wholesale.

# 10. Persistence Conformance Findings
================================================================================


--------------------------------------------------------------------------------
P1 — KnowledgeStatement Persistence Representation Conflict
--------------------------------------------------------------------------------

Status:

DOCUMENTATION CONFLICT

The Persistence Mapping Specification treats KnowledgeStatement as a value
inside LearningObject.

The Persistence Implementation Specification defines a normalized
knowledge_statements table while explicitly stating that the technical
database identity must not become a domain identity.

This is technically possible, but the authoritative mapping decision must be
made explicit and consistent across specifications.

Required action:

Consolidate the mapping decision before implementing the persistence layer.


--------------------------------------------------------------------------------
P2 — Lifecycle Persistence Conflict
--------------------------------------------------------------------------------

Status:

DOCUMENTATION CONFLICT

The current Persistence Mapping Specification contains lifecycle terminology
that includes process states such as Reviewed, Updated and Rejected.

The newer domain and persistence model specifications define the persistent
Learning Object lifecycle as:

* Candidate
* Proposed
* Active
* Retired

Required action:

Align persistence lifecycle mapping with the authoritative current domain
lifecycle model.


--------------------------------------------------------------------------------
P3 — Historical Preservation
--------------------------------------------------------------------------------

Status:

SPECIFIED / NOT IMPLEMENTED

The persistence specifications require:

* immutable historical versions;
* explicit versioning;
* audit traceability;
* preservation of previous state.

The current repository does not yet contain the complete implementation
required to satisfy these requirements.


--------------------------------------------------------------------------------
P4 — Transactional Event Records
--------------------------------------------------------------------------------

Status:

SPECIFIED / NOT IMPLEMENTED

The persistence implementation specification requires Event Records to be
created in the same transaction as the domain change which produces them.

No corresponding implementation is currently present.

# 15. Required Documentation Consolidation
================================================================================

Before implementation work modifies the affected areas, the following
documentation questions must be resolved:

1. Authoritative Learning Object lifecycle states.

2. Whether KnowledgeStatement is:
   * a pure value inside LearningObject;
   * or a persistence-normalized value representation with technical
     identity only.

3. Exact persistence mapping of LearningObject and its internal values.

4. Exact relationship between lifecycle state, Review decisions and
   versioning.

5. Exact transaction boundary for:
   * domain mutation;
   * version creation;
   * audit record;
   * transactional event record.


These are specification consolidation tasks, not coding tasks.


================================================================================

================================================================================

The following implementation principles should be preserved unless a later
approved specification explicitly changes them:

* domain independence;
* repository abstraction;
* aggregate-oriented domain structure;
* application service boundary;
* separation between domain and persistence;
* automated testing;
* immutable historical version concept;
* auditability;
* technology agnosticism at the domain level.


================================================================================
# 17. Implementation Work Not Yet Authorized
================================================================================

The following should not be implemented merely to advance the roadmap until
the corresponding specification conflicts are resolved:

* final LearningObject lifecycle implementation;
* final KnowledgeStatement persistence mapping;
* complete version persistence;
* complete lifecycle persistence;
* complete transactional event persistence.


This prevents implementation from hardening an inconsistent specification.

# 22. Final Baseline Statement
================================================================================

The ELR repository has crossed the boundary from architectural design into
implementation.

The implementation is real but incomplete.

The strongest existing foundation is the technology-independent Core Domain
and its application service layer.

The largest implementation gaps are persistence, transactional infrastructure,
events, API, security, import/export and end-to-end user workflows.

The most immediate risks are not missing code alone.

They are unresolved differences between older implementation assumptions and
the current specifications, especially:

* Learning Object lifecycle;
* KnowledgeStatement representation;
* persistence mapping;
* versioning semantics;
* transactional event handling.

These must be consolidated before the affected implementation areas are
expanded.

The project therefore proceeds from:

ARCHITECTURE COMPLETE

to:

SPECIFICATION-CONSOLIDATED CORE IMPLEMENTATION

and ultimately to:

FULL ELR USER-READY.
