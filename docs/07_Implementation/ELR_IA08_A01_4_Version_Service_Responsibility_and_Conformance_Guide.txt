# 1. Purpose

================================================================================

This document defines the implementation and conformance disposition for
A01.4 — Version Service.

Its purpose is to establish and document the responsibility boundary for
Version-specific application operations.

This document does not redefine Version domain semantics.

The authoritative ELR specification corpus remains the controlling authority.

The implementation boundary documented here distinguishes:

* Learning Object use-case coordination;
* Version-specific application coordination;
* Version domain semantics;
* Version persistence;
* operational audit coordination.

================================================================================

# 2. Current Disposition

================================================================================

### A01.4 — Version Service

The Version Service responsibility is explicitly established by the applicable
Application Service Implementation Specification.

The current implementation satisfies the Version Service responsibility for
Version creation and Version-specific application coordination through
`VersionService`.

`VersionService` coordinates:

* Version creation;
* Version-specific application coordination;
* delegation of Version persistence to `VersionRepository`.

However, Version history access is not yet fully isolated behind `VersionService`.
The current `LearningObjectService` implementation performs Version history
retrieval through the Version repository directly.

Therefore, the implementation currently exhibits two Version access paths:

```text
LearningObjectService
        │
        ├── VersionService
        │       │
        │       └── VersionRepository
        │
        └── VersionRepository
                └── Version history retrieval
```

This does not transfer Version domain ownership to `VersionService`.
Version domain semantics remain owned by the Domain Layer and the applicable
Versioning Model.

Version persistence remains owned by `VersionRepository`.

The remaining A01.4 alignment item is therefore the isolation of Version
history access behind `VersionService`, so that the documented responsibility
boundary and the concrete application implementation converge on the same
path.


================================================================================

# 3. Implementation Evidence

================================================================================

The current implementation provides:

* `app/application/services/version_service.py`;
* `VersionService.create_version()`;
* `VersionService.get_versions()`;
* injection of VersionService into LearningObjectService;
* delegation of Version creation from LearningObjectService to VersionService;
* delegation of Version persistence from VersionService to VersionRepository;
* Version numbering through the applicable Versioning Model;
* immutable Version snapshot construction;
* Version persistence through VersionRepository.

The concrete Version creation flow is:

LearningObjectService
↓
VersionService.create_version()
↓
VersionRepository.save()

Version history retrieval is currently implemented through a direct repository path:

LearningObjectService
↓
VersionRepository.find_by_entity()

Although VersionService provides `get_versions()`, the current LearningObjectService implementation does not yet consistently route Version history access through that service boundary.

The implementation therefore establishes the Version Service responsibility for Version creation and persistence delegation, while Version history coordination remains an outstanding responsibility-boundary alignment item.

The remaining implementation alignment is:

LearningObjectService
↓
VersionService.get_versions()
↓
VersionRepository.find_by_entity()

No change to Version domain semantics or VersionRepository persistence responsibility is implied by this alignment.


================================================================================

# 4. Responsibility Boundary

================================================================================

The Version Service is an application-service responsibility.

Its responsibility includes:

* coordinating Version creation;
* coordinating Version history access;
* determining the required Version operation according to the applicable
  Versioning Model;
* constructing the required Version state;
* delegating Version persistence to VersionRepository;
* participating in the transaction boundary established by the originating
  application operation.

The Version Service does not own independent Version domain semantics.

The following remain outside VersionService:

* Version numbering rules as domain semantics;
* Version immutability rules;
* snapshot semantics;
* historical preservation semantics;
* Learning Object lifecycle semantics;
* persistence implementation details.

The responsibility separation is therefore:

Application use-case coordination
↓
LearningObjectService

Version-specific application coordination
↓
VersionService

Version domain semantics
↓
Domain Layer / Versioning Model

Version persistence
↓
VersionRepository

Operational audit coordination
↓
AuditService

================================================================================

# 5. LearningObjectService Delegation

================================================================================

LearningObjectService coordinates the originating Learning Object operation.

When an operation requires Version creation, LearningObjectService delegates
the Version-specific responsibility to VersionService.

The implementation therefore does not require LearningObjectService to
directly coordinate Version persistence.

The resulting boundary is:

LearningObjectService
│
└── VersionService
│
└── VersionRepository

This separation isolates Version-specific application coordination without
transferring ownership of Version domain semantics.

================================================================================

# 6. Version Persistence

================================================================================

Version persistence remains the responsibility of VersionRepository.

VersionService does not implement an alternative persistence mechanism.

VersionService delegates persistence to VersionRepository.

The persistence flow is:

VersionService
↓
VersionRepository
↓
Persistence Model
↓
Database

VersionRepository therefore remains the persistence boundary for Version
state.

The introduction or use of VersionService does not alter VersionRepository
semantics.

================================================================================

# 7. Transaction Boundary

================================================================================

VersionService participates in the transaction boundary established by the
originating application operation.

VersionService does not own an independent transaction boundary.

It does not independently:

* begin a transaction;
* commit Version persistence;
* terminate the originating transaction;
* persist Version state outside the originating application operation.

When LearningObjectService executes an operation requiring Version creation,
Version persistence participates in the same persistence operation as the
other state changes belonging to that application operation.

The transaction relationship is therefore:

Originating application operation
↓
Existing transaction boundary
↓
Learning Object persistence
+
Version persistence
+
Audit persistence
+
other participating persistence

VersionService coordinates Version work within this boundary.

It does not replace or redefine transaction ownership.

================================================================================

# 8. Domain Responsibility

================================================================================

VersionService must not duplicate or redefine Version domain invariants.

Version domain responsibility remains with the Domain Layer and applicable
Versioning Model.

In particular, VersionService does not independently redefine:

* Version numbering semantics;
* Version immutability;
* snapshot semantics;
* historical preservation;
* Learning Object lifecycle semantics.

The service coordinates application behavior around these domain rules.

This preserves the separation between:

application orchestration;
domain semantics;
persistence.

================================================================================

# 9. Verification Evidence

================================================================================

The existing implementation verification covers Version behavior including:

* approval creates the first Version;
* the first Version is numbered correctly;
* the Version references the correct Learning Object;
* the expected snapshot is preserved;
* knowledge update creates a subsequent Version;
* Version numbers increment correctly;
* previous Versions remain unchanged;
* previous snapshots remain preserved;
* updated knowledge is represented by the new Version;
* Version history can be retrieved;
* Version persistence participates in the originating transaction;
* persistence failure produces the required rollback behavior.

Responsibility-boundary verification establishes that:

* Version creation is coordinated through VersionService;
* LearningObjectService delegates Version creation to VersionService;
* VersionService delegates persistence to VersionRepository;
* VersionService does not redefine Version domain semantics;
* VersionService does not introduce an independent transaction boundary.

Version history responsibility is not yet fully conformant to the documented boundary because LearningObjectService currently retains a direct VersionRepository history-retrieval path.

Therefore:

Behavioral Conformance
│
├── Version semantics
├── Version numbering
├── Snapshot preservation
├── Immutability
└── Transaction / rollback behavior

Responsibility Conformance
│
├── Version creation
│       └── VersionService
│
├── Version history
│       └── Alignment remaining
│
└── Version persistence
└── VersionRepository

The verification therefore confirms the implemented VersionService boundary for Version creation and persistence delegation, but does not establish full A01.4 responsibility-level conformance until Version history access is isolated behind VersionService.

# 11. Prohibited Changes

================================================================================

The following changes shall not be introduced under A01.4 without authoritative
specification or new implementation evidence:

* changing Version numbering semantics;
* changing Version immutability;
* changing snapshot semantics;
* changing historical preservation;
* moving domain rules into VersionService;
* introducing independent Version domain rules;
* changing VersionRepository semantics;
* bypassing the originating transaction boundary;
* introducing an independent VersionService transaction;
* replacing existing behavioral tests without equivalent coverage;
* moving unrelated application responsibilities into VersionService.

A01.4 must not be interpreted as requiring additional Version abstractions,
additional domain services, or unrelated application-service restructuring.

================================================================================

# 12. Resolution Rule

================================================================================

# 12. Resolution Rule

================================================================================

A01.4 is assessed on the basis of responsibility-level conformance.

The resolution criterion is not the existence of a class named VersionService alone.

The required responsibility placement is:

Version creation
↓
VersionService

Version history access
↓
VersionService

Version persistence
↓
VersionRepository

Learning Object use-case coordination
↓
LearningObjectService

Version domain semantics
↓
Domain Layer / Versioning Model

The current implementation satisfies the required VersionService responsibility for Version creation and persistence delegation.

The Version history responsibility is not yet fully satisfied because LearningObjectService retains a direct VersionRepository history-retrieval path.

The remaining alignment condition is:

* Version history access must be coordinated through VersionService;
* LearningObjectService must delegate Version history access to VersionService;
* VersionService must delegate Version history retrieval to VersionRepository;
* Version domain semantics must remain owned by the Domain Layer and Versioning Model;
* Version persistence must remain within the originating application transaction;
* existing Version behavior must remain preserved.

Until the Version history path is isolated behind VersionService, A01.4 shall remain classified as partially implemented / alignment remaining.

No additional Version abstractions, domain services, or unrelated application-service restructuring are required by this alignment item.
