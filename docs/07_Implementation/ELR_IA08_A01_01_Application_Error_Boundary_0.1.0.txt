================================================================================
# 1. Purpose
================================================================================

This document defines the minimum implementation change required to establish
an Application Layer error boundary.

The objective is to separate:

* Domain errors;
* Application-level errors;
* transport-level error handling.

The change must not alter Domain behavior, lifecycle semantics, persistence
semantics, or API behavior.


================================================================================
# 2. Confirmed Finding
================================================================================

The current Application Layer has an incomplete application error boundary.

The current implementation already defines LearningObjectNotFound inside
LearningObjectService. This is an application-level not-found error.

The Domain Layer independently defines InvalidStateTransition.

InvalidStateTransition currently crosses the Application Service boundary
without translation into an application-level error taxonomy.

The confirmed gap is therefore:

IA-08-A01.1 — Application Error Taxonomy and Domain-Error Translation
Incomplete


================================================================================
# 3. Required Responsibility Boundary
================================================================================

The intended dependency direction is:

Domain
    ->
Application Error Boundary
    ->
Application Consumer


The Domain Layer remains the authority for domain rules.

The Application Layer translates domain failures into stable application-level
failures.

The API Layer, when implemented, will subsequently translate application
failures into transport-level responses.

The Application Layer must therefore not:

* raise HTTPException;
* depend on FastAPI;
* expose SQLAlchemy exceptions;
* expose database-specific exceptions;
* redefine domain rules.


================================================================================
# 4. Current Error Ownership
================================================================================

The current implementation establishes two different error ownership
locations.

Application Layer:

LearningObjectNotFound

This exception is currently defined in LearningObjectService and therefore
already belongs to the Application Layer.

Domain Layer:

InvalidStateTransition

This exception is defined by the LearningObject domain model and remains owned
by the Domain Layer.

This distinction must be preserved.


================================================================================
# 5. Application Error Model
================================================================================

The Application Layer shall provide a stable application-level error
taxonomy.

The initial categories are:

* EntityNotFound;
* InvalidOperation;
* ValidationFailure;
* UnauthorizedOperation.

The taxonomy shall be centralized in the Application Layer.

The implementation must not create duplicate application error classes inside
individual Application Services.

UnauthorizedOperation is reserved for authorization failures and shall not be
introduced into A01.1 through artificial mappings.


================================================================================
# 6. Error Mapping
================================================================================

The initial mapping shall be limited to failures that actually exist in the
current implementation.

Current Domain Error:

InvalidStateTransition

shall map to:

InvalidOperation


Current Application Error:

LearningObjectNotFound

shall be normalized to:

EntityNotFound


The LearningObjectNotFound class must therefore not be treated as a Domain
exception.

No mapping shall be introduced for ValidationFailure until an applicable
Domain validation failure exists in the current implementation.

No mapping shall be introduced for UnauthorizedOperation until the Security
Layer defines an authorization failure boundary.

The objective is to establish the taxonomy without inventing unused
semantics.


================================================================================
# 7. Preservation of Original Cause
================================================================================

Application-level translation must preserve the original exception as the
underlying cause.

Conceptually:

raise EntityNotFound(...) from original_exception


or the equivalent mechanism supported by the implementation language.

This preserves diagnostic information without exposing the Domain exception
as the primary Application boundary.

For existing application-level errors that are normalized into the central
Application Error taxonomy, exception chaining is optional unless an original
Domain or infrastructure exception is being translated.

Domain-to-Application translations shall preserve the original Domain
exception as the underlying cause.


================================================================================
# 8. Scope of Translation
================================================================================

Translation shall occur at the Application Service boundary.

It shall not be performed:

* inside Domain entities;
* inside repository implementations;
* inside persistence models;
* inside API routes.


================================================================================
# 9. Repository Error Handling
================================================================================

Repository-specific infrastructure failures must not be silently converted
into EntityNotFound.

Only a repository result that semantically means "entity does not exist" may
be mapped to EntityNotFound.

Unexpected infrastructure failures must remain distinguishable from a normal
not-found condition.

This prevents database failures from being incorrectly represented as
business-level absence.


================================================================================
# 10. LearningObjectService
================================================================================

The existing LearningObjectService shall be the first Application Service
covered by this boundary.

The following operations must be inspected and, where applicable, brought
under application-level error translation:

* create_candidate();
* submit_for_review();
* approve();
* update_knowledge();
* retire();
* get();
* get_history().

The implementation must not change their successful behavior.


================================================================================
# 11. No Semantic Change
================================================================================

This change must not alter:

* lifecycle transitions;
* aggregate invariants;
* version creation rules;
* audit semantics;
* repository interfaces;
* persistence mappings;
* database schema.


================================================================================
# 12. Proposed Implementation Shape
================================================================================

The preferred initial structure is:

app/
    application/
        errors.py
        services/
            learning_object_service.py


The exact filename may differ if an equivalent existing application error
module is already present.

Do not create duplicate error modules.


================================================================================
# 13. Required Inspection Before Modification
================================================================================

Before applying the change, inspect the existing code for:

* application exception classes;
* domain exception classes;
* repository not-found behavior;
* existing error translation;
* existing tests for exception behavior.

Search for:

* Exception;
* NotFound;
* InvalidStateTransition;
* ValidationError;
* Unauthorized;
* raise;
* except.


================================================================================
# 14. Minimal Change Rule
================================================================================

The implementation shall introduce only the minimum structures required to:

1. define the initial application error taxonomy;
2. translate currently known domain failures;
3. preserve exception causes;
4. preserve successful behavior;
5. provide testable Application Layer error semantics.


================================================================================
# 15. Test Requirements
================================================================================

Add focused Application Layer tests for:

## 15.1 Not Found

A missing Learning Object must result in:

EntityNotFound

at the Application boundary.

## 15.2 Invalid State Transition

An invalid lifecycle operation must result in:

InvalidOperation

at the Application boundary.

## 15.3 Validation

A domain validation failure must result in:

ValidationFailure

when such a failure exists in the current implementation.

## 15.4 Cause Preservation

The application error must preserve the original domain exception as its
cause.

## 15.5 Successful Operations

Existing successful operations must continue to return the same successful
results.

## 15.6 Regression

All existing tests must remain green.


================================================================================
# 16. Explicit Non-Goals
================================================================================

This change does not implement:

* FastAPI error handlers;
* HTTP status mapping;
* Authentication;
* Authorization;
* Identity Context;
* Security middleware;
* Transaction management;
* Transactional Event Records;
* Review;
* Change Proposal;
* Category Service.


================================================================================
# 17. Acceptance Criteria
================================================================================

A01.1 is resolved when:

AC-001

An application-level error taxonomy exists.

AC-002

Known Domain errors are translated at the Application boundary.

AC-003

Domain exceptions remain owned by the Domain Layer.

AC-004

HTTP and framework-specific errors are absent from the Application Layer.

AC-005

Unexpected infrastructure failures are not incorrectly converted into
EntityNotFound.

AC-006

Original exception causes remain available for diagnostics.

AC-007

Existing successful Application Service behavior remains unchanged.

AC-008

Focused error tests pass.

AC-009

The complete existing regression suite passes.

AC-010

No persistence, lifecycle, versioning, audit, or domain semantics have
changed.


================================================================================
# 18. Stop Conditions
================================================================================

Stop implementation if:

* an existing application error taxonomy is discovered;
* Domain exception semantics are ambiguous;
* repository behavior cannot distinguish absence from infrastructure failure;
* implementing translation requires changing Domain behavior;
* an API-specific error model is required;
* a previously passing persistence or lifecycle test fails.


================================================================================
