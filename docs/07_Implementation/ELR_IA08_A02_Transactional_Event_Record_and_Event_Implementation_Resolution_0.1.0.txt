# 1. Purpose
================================================================================

This document defines the controlled implementation resolution for:

IA-08-A02 — Transactional Event Record and Event Implementation.

The objective is to introduce the minimum implementation required to bring the
current repository into conformance with the authoritative Event Model and
Event Implementation specifications, while preserving all previously verified
Domain, Application, Audit, Version, and Persistence boundaries.

The implementation shall be minimal and incremental.

No unrelated architectural or semantic changes are authorized by this
document.


================================================================================
# 2. Conformance Finding Under Inspection
================================================================================

The current implementation contains an AuditRecord boundary and an existing
transaction mechanism, but no confirmed Transactional Event Record boundary.

The current implementation therefore does not yet provide the required Event
Record persistence and first Event Implementation layer.

The confirmed areas requiring resolution are:

* Transactional Event Record representation;
* Event Record persistence model;
* Event Record repository boundary;
* required event envelope fields;
* atomic persistence with the domain change;
* event-source and schema/version preservation;
* payload persistence;
* publication boundary after successful commit;
* separation between Event Records and Audit Records;
* tests proving the above behavior.

The implementation must not reinterpret AuditRecord as a Transactional Event
Record.


================================================================================
# 3. Authoritative Requirements
================================================================================

The authoritative Event specifications define an Event as a fact representing
an already completed domain or application change.

The Transactional Event Record is an infrastructure/persistence artifact used
to preserve that fact durably and transactionally.

The Event Record must preserve, at minimum, the following envelope semantics:

* event_id;
* event_type;
* event_source;
* aggregate_type;
* aggregate_id;
* version / schema version as defined by the authoritative Event
  specification;
* payload;
* occurred_at;
* published_at;
* created_at;
* metadata.

The exact field names, types, defaults, and constraints must be taken from the
authoritative Event Implementation Specification rather than invented here.

The Event Record must be immutable after creation.

The Event Record must be persisted in the same transaction as the domain
change that caused the event.

Publication is a separate concern. Publication must occur only after the
transaction has successfully committed and publication failure must not
roll back an already committed domain change.

Audit History and Event Records are distinct concerns and must remain distinct
in both domain meaning and persistence representation.


================================================================================
# 4. Current Implementation Baseline
================================================================================

The current Application Layer coordinates Learning Object changes and records
AuditRecord instances.

LearningObjectService currently uses repository interfaces and, for selected
operations, an injected transaction factory. The existing persistence wiring
passes a shared SQLAlchemy Session to the repositories and the transaction
context commits or rolls back that session.

This existing transaction infrastructure is considered reusable.

The A02 implementation must not introduce a second or competing transaction
architecture.

The current AuditRecord persistence model contains audit-specific fields such
as entity_id, event_type, actor, timestamp, and metadata. It is not an Event
Record implementation and must not be expanded merely to emulate one.


================================================================================
# 5. Architectural Constraints
================================================================================

The following previously verified boundaries remain closed:

* Domain model authority;
* Application Service responsibility boundary established by IA-08-A01;
* Version persistence and history;
* Audit persistence and Audit boundary;
* existing transaction mechanism;
* existing repository-to-persistence direction;
* existing database session ownership model.

A02 must not reopen A01.

A02 must not move event semantics into Domain entities unless the authoritative
Event specification explicitly requires a domain event representation there.

A02 must not make AuditRecord a superclass, alias, or replacement for Event
Record.

A02 must not introduce broker infrastructure, retry infrastructure, or
external messaging semantics unless such capability is explicitly required by
the applicable authoritative Event Implementation Specification.

A02 must not modify the Learning Object persistence schema beyond the minimum
changes required to establish the Event Record persistence boundary.

A02 must not alter already verified Audit semantics.


================================================================================
# 6. Resolution Strategy
================================================================================

The A02 resolution shall follow this sequence:

1. verify the authoritative Event Model and Event Implementation requirements;
2. inspect current Domain, Application, Persistence, wiring, and tests;
3. reconcile every required Event responsibility against implementation
   evidence;
4. classify each responsibility as CONFORMANT, PARTIAL, GAP, or BLOCKED;
5. implement only confirmed GAP responsibilities;
6. reuse the existing transaction boundary;
7. add focused tests for each new responsibility;
8. run the full existing regression suite;
9. verify that Audit behavior remains unchanged;
10. record the final conformance disposition and checkpoint state.

No implementation shall be introduced solely because a class, file, or method
name differs from the specification.

The implementation must not invent event semantics absent from the
authoritative specification.


================================================================================
# 7. Responsibility Model
================================================================================

A02 is divided into the following implementation responsibilities.

A02.1 — Event Record Representation

Define the minimum representation required for a Transactional Event Record,
using authoritative field semantics.

A02.2 — Event Record Persistence

Introduce the persistence model and database representation required by the
Event Implementation Specification.

A02.3 — Event Repository Boundary

Introduce the repository contract and concrete persistence implementation
needed to store Event Records.

A02.4 — Transactional Integration

Ensure that creation of the Event Record occurs inside the same transaction as
the domain change that caused it.

A02.5 — Event Envelope Preservation

Ensure event_source, event type, aggregate identity, version/schema version,
payload, timestamps, and metadata are preserved according to the authoritative
specification.

A02.6 — Event / Audit Separation

Ensure Event Records and Audit Records remain independently represented,
persisted, and semantically distinguishable.

A02.7 — Publication Boundary

Provide only the first publication boundary required by the authoritative
Event Implementation Specification. Publication must not participate in the
already-committed domain transaction.

A02.8 — Verification

Provide focused tests for persistence, atomicity, immutability, envelope
preservation, separation from Audit, and publication ordering as applicable.

# 8. Classification
================================================================================

The required responsibility is already satisfied by confirmed implementation
evidence.

The responsibility is substantially present, but an explicit capability or
integration remains incomplete.

GAP

A required responsibility is confirmed missing or incorrectly implemented.

BLOCKED

The responsibility cannot be implemented correctly because a required
authoritative upstream capability or prerequisite is not available.

================================================================================
# 10. A02.1 — Event Record Representation
================================================================================

Status:

GAP

Implementation requirement:

Introduce only the minimum representation needed to express the authoritative
Transactional Event Record.

The implementation must not add speculative fields or behavior.

The representation must make the Event Record immutable by design wherever
practical and must not expose mutation operations that contradict the
specification.


================================================================================
# 11. A02.2 — Event Record Persistence
================================================================================

Status:

GAP

Implementation requirement:

Introduce the persistence model for the authoritative Event Record.

The persistence model must preserve the authoritative event envelope without
collapsing event fields into the AuditRecord schema.

The implementation must use the existing persistence technology and Base/model
conventions unless authoritative evidence requires otherwise.


================================================================================
# 12. A02.3 — Event Repository Boundary
================================================================================

Status:

GAP

Implementation requirement:

Introduce a repository contract and concrete persistence implementation for
creating and retrieving Event Records only to the extent required by the
authoritative specification and current use cases.

Do not introduce speculative query APIs.

Do not couple the Domain Layer to SQLAlchemy.


================================================================================
# 13. A02.4 — Transactional Integration
================================================================================

Status:

GAP

Implementation requirement:

The Event Record must be persisted through the same transaction/session as the
domain mutation that produced the event.

The implementation must reuse the existing transaction mechanism rather than
introducing a second transaction abstraction.

Required verification cases include:

* domain change succeeds -> Event Record commits;
* domain change fails -> Event Record does not commit;
* Event Record persistence fails -> domain change does not commit;
* both domain and Event Record become visible only after commit.

The exact test shape must match the current repository test architecture.


================================================================================
# 14. A02.5 — Event Envelope Preservation
================================================================================

Status:

GAP

Every required field must be preserved without semantic loss.

Particular attention must be given to:

* event_source as an explicit field rather than inferred metadata;
* event/version or schema version as explicitly required;
* aggregate_type and aggregate_id;
* payload as structured event data rather than Audit metadata;
* occurred_at versus created_at semantics;
* published_at remaining unset until publication, if so required by the
  authoritative specification.

No field may be repurposed merely because an existing Audit field appears
similar.


================================================================================
# 15. A02.6 — Event / Audit Separation
================================================================================

Status:

PARTIAL -> GAP RESOLUTION REQUIRED

Audit History answers the question of what was recorded for audit purposes.

Event Records represent facts intended for event/integration processing.

The implementation must therefore preserve separate:

* domain representation;
* persistence model;
* repository boundary;
* lifecycle semantics.

Existing Audit behavior must remain regression-tested and unchanged except
where explicit contradictory evidence is discovered.


================================================================================
# 16. A02.7 — Publication Boundary
================================================================================

Status:

GAP / SCOPE TO BE CONFIRMED

Publication must be downstream of successful persistence/commit.

The first A02 implementation must not introduce an external broker unless the
authoritative Event Implementation Specification explicitly requires one at
this stage.

If the authoritative implementation requires only a publication boundary,
introduce the smallest abstraction necessary to represent that boundary and
keep external delivery concerns outside the transactional persistence path.

The following invariant must hold:

Committed domain change
+
Committed Event Record
->
publication may be attempted

A publication failure must not retroactively roll back the committed domain
transaction.


================================================================================
# 17. A02.8 — Verification Strategy
================================================================================

Focused tests shall be added before the A02 finding is considered resolved.

At minimum, tests shall cover the confirmed authoritative requirements for:

1. Event Record creation;
2. required envelope field persistence;
3. event/source/version preservation;
4. aggregate identity preservation;
5. payload preservation;
6. timestamp semantics;
7. Event Record immutability or absence of mutation path;
8. same-transaction persistence;
9. rollback behavior;
10. Event / Audit separation;
11. post-commit publication ordering, if publication is in A02 scope;
12. reconstruction/read-back from a new database session.

Tests must be narrowly scoped and must not duplicate unrelated A01 coverage.


================================================================================
# 18. Implementation Order
================================================================================

The preferred implementation order is:

Step 1

Add the Event Record representation and its focused unit tests.

Step 2

Add the persistence model and mapping tests.

Step 3

Add the Event repository contract and concrete repository.

Step 4

Wire the repository using the existing persistence/session architecture.

Step 5

Integrate Event Record creation into the confirmed transactional application
use cases without changing domain semantics.

Step 6

Add atomicity and rollback tests.

Step 7

Add only the publication boundary explicitly required by the authoritative
specification.

Step 8

Run the focused A02 test set.

Step 9

Run the full regression suite.

Step 10

Record the final responsibility-level disposition and update the IA-08
continuity/checkpoint artifacts.


================================================================================
# 19. Explicit Non-Goals
================================================================================

A02 does NOT authorize:

* reopening IA-08-A01;
* changing Domain lifecycle rules;
* changing Version semantics;
* changing Audit semantics;
* introducing API endpoints;
* introducing authentication or authorization;
* introducing a message broker without authoritative requirement;
* implementing retry/delivery guarantees beyond the authoritative scope;
* redesigning the database transaction architecture;
* changing existing Learning Object persistence semantics;
* speculative event types unrelated to confirmed use cases;
* generic event-sourcing infrastructure.


================================================================================
# 20. Completion Criteria
================================================================================

IA-08-A02 may be classified COMPLETE / CLOSED only when all of the following
are true:

* every applicable A02 responsibility has a final disposition;
* Transactional Event Record persistence is implemented according to the
  authoritative specification;
* Event Records are distinct from Audit Records;
* domain change and Event Record persistence share the required transaction;
* required event envelope fields are preserved;
* publication boundary, if applicable to A02, is correctly ordered after
  commit;
* focused A02 tests pass;
* the full regression suite passes;
* no previously closed IA-08 boundary has been unintentionally changed;
* implementation documentation reflects the verified final state;
* the session/bootstrap continuity state is updated with the A02 checkpoint.
