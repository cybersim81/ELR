# 1. Purpose

================================================================================

This document provides the controlled implementation plan for resolving the
confirmed implementation-conformance findings identified during IA-08.

The purpose is to:

* record confirmed implementation gaps;
* establish their dependency order;
* define the intended target state;
* constrain implementation changes;
* define verification requirements;
* prevent accidental reopening of already verified architectural boundaries;
* provide a controlled bridge from conformance analysis to implementation.

This document is a guide for implementation work.

It is not itself an implementation specification.

# 5. Finding A02 — Transactional Event Record

================================================================================

## 5.1 Current State

IA-08-A02 is the current implementation-conformance finding.

Audit Records are already implemented.

Audit Records are not equivalent to Transactional Event Records.

The authoritative Event Implementation Specification defines a separate
transactional event persistence mechanism.

A02 must therefore be inspected against the authoritative event requirements
and the current repository implementation before any implementation change is
made.

================================================================================

## 5.2 Required Inspection

================================================================================

The A02 inspection shall establish:

* required event envelope;
* required Transactional Event Record semantics;
* event persistence boundary;
* event source semantics;
* event schema version semantics;
* aggregate identity semantics;
* event payload semantics;
* event timestamps;
* transactional relationship with the originating domain change;
* subsequent publication boundary;
* relationship between Event Records and Audit Records.

The repository inspection shall search existing:

* event entities;
* event records;
* event repositories;
* persistence models;
* event adapters;
* transaction boundaries;
* tests;
* wiring;
* publication abstractions.

No implementation gap shall be declared until the authoritative requirement
and existing repository behavior have been compared.

================================================================================

## 5.3 Target State

================================================================================

If the inspection confirms the A02 gap, the first Event Implementation shall
provide a Transactional Event Record mechanism consistent with the authoritative
Event Implementation Specification.

The event record shall preserve at minimum:

* event_id;
* event_type;
* event_source;
* aggregate_type;
* aggregate_id;
* version;
* payload;
* occurred_at;
* published_at;
* created_at;
* metadata.

================================================================================

## 5.4 Transaction Rule

================================================================================

A transactional event record produced by a domain/application operation shall
be persisted within the same transaction as the domain change that produced
the event.

The external publication of the event shall not be required for domain
transactional consistency.

A publication failure must therefore not invalidate an already committed
domain transaction.

The transactional event record is the durable bridge between the originating
transaction and later event publication.

================================================================================

## 5.5 Separation Rule

================================================================================

Transactional Event Records are infrastructure artifacts.

They are not:

* Learning Objects;
* Knowledge Statements;
* Versions;
* Audit Records;
* repository knowledge entities.

Audit Records and Transactional Event Records serve different responsibilities
and must remain separate.

Audit history must not be replaced by event history.

Event persistence must not expand the semantic knowledge persistence boundary.

================================================================================

## 5.6 Verification

================================================================================

A02 shall be considered resolved only when verification demonstrates, as
applicable to the confirmed implementation boundary:

* event creation;
* event immutability;
* correct event envelope mapping;
* correct persistence mapping;
* preservation of event_source;
* preservation of version;
* atomicity with the originating domain change;
* separation from Audit Records;
* behavior after transaction failure;
* compatibility with the existing transaction boundary;
* existing application behavior remains green.

Focused verification shall be performed first.

The complete test suite shall be run before A02 is declared resolved.

================================================================================

# 6. Finding A03 — Security and Authorization

================================================================================

## 6.1 Current State

================================================================================

IA-08-A03 remains pending.

The current application service accepts actor information for audit purposes.

A complete Identity Context and Authorization boundary must be evaluated
against the authoritative Security Implementation Specification.

================================================================================

## 6.2 Required Inspection

================================================================================

The Security Implementation Specification shall be inspected for:

* authentication boundary;
* Identity Context;
* actor identity;
* actor type;
* roles;
* authorization decisions;
* authorization failure semantics;
* protected operations;
* Application Layer integration;
* API Layer integration;
* auditability requirements.

================================================================================

## 6.3 Target State

================================================================================

If the inspection confirms an implementation gap, the implementation shall
introduce the minimum security abstraction required by the authoritative
Security and Access Model.

The first implementation shall support:

* Identity Context;
* actor identity;
* actor type;
* roles;
* authorization decisions;
* explicit authorization failures;
* Application Layer access to the authenticated identity context.

================================================================================

## 6.4 Authentication Boundary

================================================================================

Authentication must remain abstract.

The first implementation shall not introduce a concrete external identity
provider unless separately authorized by the applicable specification.

An AuthenticationProvider abstraction is sufficient for the initial
implementation boundary where the authoritative requirements permit it.

================================================================================

## 6.5 Authorization Rules

================================================================================

The implementation shall preserve the authoritative initial role model,
including:

* SYSTEM_ADMIN;
* KNOWLEDGE_REVIEWER;
* KNOWLEDGE_PRODUCER;
* READ_ONLY_USER.

Authorization must not be redefined independently inside the API layer.

The API Layer shall invoke the authorization model rather than create a
competing role or permission model.

================================================================================

## 6.6 Auditability

================================================================================

Significant knowledge modifications shall remain attributable to an actor.

Security integration must enrich and protect auditability.

It must not replace the Audit Model with the Event Model.

================================================================================

## 6.7 Verification

================================================================================

A03 shall be considered resolved only when verification demonstrates the
required security behavior, including as applicable:

* unauthenticated access rejection;
* insufficient-role rejection;
* authorized operation;
* correct Identity Context propagation;
* authorization before protected operation;
* actor attribution in significant modifications.

Focused verification shall be performed first.

The complete test suite shall be run before A03 is declared resolved.

================================================================================

================================================================================

## 7.1 Current State

================================================================================

IA-08-A04 remains pending.

The implementation shall be compared against the authoritative API

================================================================================

## 7.2 Required Inspection

================================================================================

The inspection shall establish:

* required FastAPI boundary;
* required REST endpoints;
* `/api/v1` boundary;
* Learning Object access;
* history access;
* category access;
* health endpoint;
* protected write operations;
* delegation to Application Services;
* Identity Context integration;
* authorization integration;
* application error translation;
* response mapping.

================================================================================

## 7.3 Target State

================================================================================

If the inspection confirms the API gap, the API Layer shall be an adapter.

It shall:

* receive HTTP requests;
* validate transport-level input;
* establish or receive the Identity Context;
* invoke authorization;
* invoke Application Services;
* map application-level failures to HTTP responses;
* return API response representations.

It shall not:

* implement domain rules;
* implement lifecycle semantics;
* implement Review semantics;
* implement Version semantics;
* implement Audit semantics;
* implement transactional event semantics;
* directly manipulate persistence models;
* create a competing authorization model.

================================================================================

## 7.4 Verification

================================================================================

A04 shall be considered resolved only when verification demonstrates:

* required endpoints exist;
* request validation behaves correctly;
* authorization is enforced;
* Application Services are used as the application boundary;
* domain semantics remain outside the API layer;
* application failures are translated correctly;
* successful responses conform to the authoritative API contract;
* protected operations reject unauthorized access;
* existing persistence and application tests remain green.

Focused API verification shall be performed first.

The complete test suite shall be run before A04 is declared resolved.

# 9. Implementation Constraints

================================================================================

All implementation work shall follow these constraints:

1. The authoritative normative specifications remain the final authority.

2. Responsibility must be evaluated before naming.

3. Existing repository abstractions shall be reused when they satisfy the
   required responsibility.

4. No new service shall be introduced solely to satisfy a class-name
   expectation.

5. Audit Records and Transactional Event Records shall remain distinct.

6. Version history and Audit history shall remain distinct.

7. Application Services shall not contain HTTP-specific logic.

8. Application Services shall not contain persistence-framework-specific
   logic.

9. API adapters shall not implement domain semantics.

10. Security semantics shall not be independently redefined by the API.

11. Transaction boundaries shall remain explicit and testable.

12. Existing verified IA-07 persistence behavior shall remain green.

13. Previously closed IA-08-A01 responsibilities shall not be reopened
    without contradictory evidence.

14. Implementation changes shall remain minimal and responsibility-focused.

15. The user performs repository modifications directly.

16. The assistant must provide exact paths, replacement blocks, insertion
    points, and test commands, but must not modify the repository directly
    unless explicitly authorized.

================================================================================

# 10. Verification and Closure Protocol

================================================================================

For every IA-08 finding:

1. Inspect the authoritative requirement.

2. Inspect the current repository implementation.

3. Compare responsibility and behavior.

4. Determine the evidence state.

5. Classify the responsibility.

6. Implement only a confirmed gap.

7. Run focused tests.

8. Run relevant integration/application tests.

9. Run the complete test suite.

10. Record the exact verification result.

11. Update the roadmap.

12. Update session continuity state.

13. Update the session prompt when the resume point changes.

14. Establish a checkpoint.

A finding is not resolved merely because the code appears correct.

A finding is resolved only after implementation evidence and verification
support the final disposition.

================================================================================

# 11. Checkpoint Protocol

================================================================================

After a responsibility receives a final disposition, establish a checkpoint
containing:

`docs/00_Bootstrap/06_Session_Continuity_State.txt`
