# 1. Purpose
================================================================================

This document defines the controlled implementation resolution for:

IA-08-A01 — Application Service Conformance.

The objective is to bring the Application Layer into conformance with the
authoritative ELR Application Service Implementation Specification while
preserving all previously verified domain and persistence behavior.

The implementation shall be minimal.

No unrelated architectural or semantic changes are authorized by this
document.


================================================================================
# 2. Conformance Finding Under Inspection
================================================================================

The current implementation contains a LearningObjectService and already
coordinates several Learning Object operations.

Existing capabilities include:

* create_candidate();
* submit_for_review();
* approve();
* update_knowledge();
* retire();
* get();
* get_history().

The current implementation does not yet provide the complete Application
Service structure required by the Application Service Implementation
Specification.

The suspected missing or incomplete areas requiring implementation
inspection are:

* Change Proposal approval/rejection coordination;
* Category Service boundary;
* Version Service boundary;
* Audit Service boundary;
* explicit application transaction coordination;
* application-level error translation.


================================================================================
# 3. Authoritative Requirements
================================================================================

The Application Layer is responsible for coordinating:

* API requests;
* use cases;
* domain rules;
* persistence;
* audit.

The Application Layer is not responsible for:

* cognitive logic;
* database schema;
* HTTP details.

Application Services must:

* represent explicit use cases;
* preserve Domain Layer authority;
* define transaction boundaries;
* coordinate components without replacing their responsibilities.


================================================================================
# 4. Current Implementation Baseline
================================================================================

The current LearningObjectService already demonstrates the intended basic
dependency direction.

It depends on:

* Domain entities;
* Repository interfaces.

It does not directly depend on:

* FastAPI;
* SQLAlchemy;
* PostgreSQL.

This dependency direction must be preserved.


================================================================================
# 5. Resolution Strategy
================================================================================

The A01 resolution shall be handled according to the verified Application
Service conformance matrix.

The implementation sequence follows the responsibilities defined by IA-08-A01:

A01.1 — Candidate / Learning Object
A01.2 — Review / Change Proposal
A01.3 — Category Service
A01.4 — Version Service
A01.5 — Audit Service
A01.6 — Application Error Boundary
A01.7 — Transaction Boundary

The current implementation shall be reconciled against each responsibility
before source changes are introduced.

The resolution strategy is:

1. preserve responsibilities already satisfied by the current implementation;
2. identify confirmed partial boundaries;
3. identify confirmed gaps;
4. keep unsupported responsibilities blocked;
5. implement only confirmed gaps or verified incomplete boundaries;
6. verify each implementation increment before proceeding.

No implementation shall be introduced solely to satisfy a naming difference
between the specification and the existing implementation.

No Domain, Review, Security, persistence, or API semantics shall be invented
inside the Application Layer.

# 22.9 A01.7 — Transaction Boundary Conformance Correction

================================================================================


**STATUS:** PARTIAL — CORRECTION REQUIRED

### Finding

The transactional infrastructure is implemented and available through `transaction_factory`.

However, transaction-boundary application is not yet consistent across the Application Service use cases.

`LearningObjectService.update_knowledge()` performs multiple persistence operations:

1. Learning Object update;
2. Version creation;
3. Event Record persistence;
4. Audit Record persistence;

but the complete sequence is currently executed outside `with self.transaction_factory():`.

This creates a conformance gap: a failure occurring after one or more persistence operations may leave the operation partially persisted.

### Required Correction

`update_knowledge()` SHALL execute its complete state-changing workflow inside the same transaction boundary:

```text
transaction begin
    retrieve Learning Object
    apply knowledge update
    determine next Version
    create Version
    persist Learning Object
    persist Version
    persist Event Record
    persist Audit Record
transaction commit
```

Any exception occurring during the workflow SHALL cause the transaction to roll back as a single unit.

The correction SHALL preserve the existing domain behavior, version-history semantics, event-record semantics, and audit semantics.

### Verification Requirements

The implementation SHALL demonstrate that:

* the Learning Object update and Version creation are atomic;
* Event Record persistence participates in the same transaction;
* Audit Record persistence participates in the same transaction;
* a failure in a downstream persistence operation rolls back all preceding writes;
* successful execution commits all records together;
* existing application and persistence tests remain green.

### Documentation Correction

The previous statement that A01.7 is fully conformant SHALL NOT be considered authoritative until the implementation and rollback verification above are present.

**Checkpoint status after correction:**

```text
A01.7 — Transaction Boundary Conformance
Status: PARTIAL
Blocking correction: update_knowledge transaction boundary
Required evidence: success + rollback integration test
```

### Exit Criterion

A01.7 may be promoted to `CONFORMANT` only when the transaction boundary is applied to the complete `update_knowledge()` workflow and automated tests demonstrate atomic commit/rollback behavior.
