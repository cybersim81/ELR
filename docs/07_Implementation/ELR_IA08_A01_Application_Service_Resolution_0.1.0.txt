================================================================================
# 1. Purpose
================================================================================

This document defines the controlled implementation resolution for:

IA-08-A01 — Application Service Conformance.

The objective is to bring the Application Layer into conformance with the
authoritative ELR Application Service Implementation Specification while
preserving all previously verified domain and persistence behavior.

The implementation shall be minimal.

No unrelated architectural or semantic changes are authorized by this
document.


================================================================================
# 2. Conformance Finding Under Inspection
================================================================================

The current implementation contains a LearningObjectService and already
coordinates several Learning Object operations.

Existing capabilities include:

* create_candidate();
* submit_for_review();
* approve();
* update_knowledge();
* retire();
* get();
* get_history().

The current implementation does not yet provide the complete Application
Service structure required by the Application Service Implementation
Specification.

The suspected missing or incomplete areas requiring implementation
inspection are:

* Change Proposal approval/rejection coordination;
* Category Service boundary;
* Version Service boundary;
* Audit Service boundary;
* explicit application transaction coordination;
* application-level error translation.


================================================================================
# 3. Authoritative Requirements
================================================================================

The Application Layer is responsible for coordinating:

* API requests;
* use cases;
* domain rules;
* persistence;
* audit.

The Application Layer is not responsible for:

* cognitive logic;
* database schema;
* HTTP details.

Application Services must:

* represent explicit use cases;
* preserve Domain Layer authority;
* define transaction boundaries;
* coordinate components without replacing their responsibilities.


================================================================================
# 4. Current Implementation Baseline
================================================================================

The current LearningObjectService already demonstrates the intended basic
dependency direction.

It depends on:

* Domain entities;
* Repository interfaces.

It does not directly depend on:

* FastAPI;
* SQLAlchemy;
* PostgreSQL.

This dependency direction must be preserved.


================================================================================
# 5. Resolution Strategy
================================================================================

The A01 resolution shall be implemented incrementally.

The first implementation increment shall NOT attempt to implement the complete
Review, Security, Event, or API systems.

The objective is to establish the correct Application Service boundaries
without introducing semantics that are not yet implemented elsewhere.

The resolution is therefore divided into:

A01.1 — Application Service boundary normalization

A01.2 — Supporting service boundaries

A01.3 — Error translation boundary

A01.4 — Transaction boundary

A01.5 — Application Service verification


================================================================================
# 6. A01.1 — Application Service Boundary Normalization
================================================================================

The existing LearningObjectService shall remain the primary coordinator for
Learning Object use cases unless the current implementation evidence requires
a different decomposition.

The service shall remain responsible for coordinating:

* candidate creation;
* submission for review;
* approved changes;
* rejected changes;
* retrieval;
* history access;
* lifecycle operations;
* version coordination;
* audit coordination.

The service shall not independently decide:

* whether a Change Proposal is semantically approvable;
* whether a Review decision is valid;
* whether a lifecycle transition is legal;
* whether a version is semantically required.

Those decisions remain owned by their respective domain/process authorities.


================================================================================
# 7. A01.2 — Change Proposal Operations
================================================================================

The Application Service specification requires:

approve_change_proposal();

reject_change_proposal();

The current implementation shall not create artificial Change Proposal
semantics merely to satisfy the method names.

Before implementing these methods, the implementation baseline must establish
whether the corresponding:

* Change Proposal entity;
* Review model;
* Review repository;
* Review decision model;

already exist in the current implementation.

If these components do not exist, the Application Service shall not invent
replacement domain objects inside the Application Layer.

In that situation the finding remains partially resolved until the required
authoritative domain/process components are available.


================================================================================
# 8. A01.3 — Category Service
================================================================================

The Application Service specification defines:

get_categories();

get_category_tree();

The implementation shall provide a Category Service boundary only if the
corresponding Category domain/repository contract already exists.

The Category Service shall:

* coordinate category retrieval;
* delegate persistence access to repository interfaces;
* avoid HTTP concerns;
* avoid database-specific logic;
* avoid introducing taxonomy semantics.

If the Category domain contract is not yet implemented, the missing Category
Service shall be recorded as a dependent implementation gap rather than
invented inside this change.


================================================================================
# 9. A01.4 — Version Service
================================================================================

The Application Service specification defines:

create_version();

get_versions();

The existing LearningObjectService already coordinates version creation for
approved or updated Learning Objects.

The implementation must therefore first determine whether Version coordination
is currently sufficiently cohesive to extract or formalize as a Version
Service.

The following invariant must be preserved:

Version validity remains governed by the Versioning Model and Domain
implementation.

The Version Service may coordinate version creation.

It may not independently decide the semantic validity of a version.


================================================================================
# 10. A01.5 — Audit Service
================================================================================

The Application Service specification defines:

record_event();

get_events();

The current implementation already records Audit Records through an
AuditRepository.

The first A01 implementation should therefore introduce an Audit Service
boundary around the existing audit contract rather than redesigning the Audit
Model.

The Audit Service shall:

* receive application-level audit information;
* create or coordinate Audit Records according to the existing contract;
* delegate persistence to AuditRepository;
* provide retrieval according to the existing access contract.

The Audit Service shall not:

* become an Event Store;
* publish domain events;
* replace Transactional Event Records;
* introduce a new audit semantic model.


================================================================================
# 11. A01.6 — Application Error Boundary
================================================================================

The Application Service specification requires application-level translation
of domain failures.

The intended categories include:

* InvalidStateTransition;
* EntityNotFound;
* UnauthorizedOperation;
* ValidationFailure.

The implementation shall introduce an application-level error boundary without
destroying the original domain error semantics.

Domain exceptions must remain owned by the Domain Layer.

The Application Layer may translate them into stable application-level errors
for its consumers.


================================================================================
# 12. A01.7 — Transaction Boundary
================================================================================

Application-level write use cases must be atomic.

The Application Layer owns the use-case transaction boundary.

This statement defines the responsibility boundary, not the concrete
infrastructure mechanism.

The transaction boundary is an Application Layer responsibility.

The concrete transaction mechanism remains an implementation dependency and
must be determined from the existing infrastructure before any new mechanism
is introduced.

No new Unit of Work, transaction manager, session abstraction, or equivalent
mechanism shall be introduced solely to satisfy this document until the
existing transaction infrastructure has been inspected.

For a write operation, the conceptual flow is:

BEGIN TRANSACTION

    validate application preconditions
    load required entities
    invoke domain behavior
    coordinate versioning when required
    persist domain changes
    record audit information

COMMIT

On failure:

ROLLBACK


The first A01 implementation must not introduce a new infrastructure-specific
transaction mechanism if an existing transaction abstraction already exists.

The implementation baseline must first be inspected for:

* Unit of Work;
* session factory;
* transaction manager;
* repository transaction support.

If none exists, the missing transaction boundary shall be recorded as a
separate implementation dependency rather than hidden inside repositories.


================================================================================
# 13. Dependency Rules
================================================================================

The Application Layer may depend on:

* Domain Layer;
* Repository Interfaces;
* application-level services;
* technical abstractions required for coordination.

The Application Layer may consume an Identity Context or authorization
decision supplied by the Security boundary.

The Application Layer must not implement, duplicate, or redefine the
authentication or authorization model.

Security semantics remain owned by the Security Layer and its authoritative
specification.

This finding therefore does not authorize implementation of IA-08-A03 as
part of IA-08-A01.

The Application Layer must not depend directly on:

* FastAPI;
* SQLAlchemy;
* PostgreSQL;
* HTTP request/response objects;
* infrastructure-specific database models.


================================================================================
# 14. Scope Control
================================================================================

The following changes are explicitly excluded from A01:

* implementation of FastAPI;
* implementation of authentication;
* implementation of authorization;
* implementation of Transactional Event Records;
* implementation of an external event bus;
* redesign of the Domain Model;
* redesign of the Persistence Model;
* introduction of Change Proposal semantics not already specified;
* introduction of Review semantics not already specified.

# 16. Minimal Expected Implementation Shape
================================================================================

The intended application structure is conceptually:

Application Services
    |
    +-- LearningObjectService
    |
    +-- CategoryService
    |
    +-- VersionService
    |
    +-- AuditService
    |
    +-- Application Error Boundary
    |
    +-- Transaction Boundary


The exact class/module decomposition remains an implementation decision,
provided that the authoritative dependency and responsibility rules are
preserved.


================================================================================
# 17. Verification Requirements
================================================================================

A01 verification shall include at minimum:

## Application Unit Tests

Verify:

* create candidate use case;
* submit for review use case;
* approval coordination;
* knowledge update coordination;
* retirement coordination;
* retrieval;
* history retrieval;
* error translation.

## Repository Boundary Tests

Verify:

* Application Services use repository interfaces;
* Application Services do not access infrastructure directly.

## Transaction Tests

Where transaction infrastructure exists, verify:

* successful commit;
* rollback on failure;
* no partial application-level write state.

## Regression Tests

All previously passing tests must remain green.

In particular:

* domain lifecycle tests;
* persistence tests;
* cross-session reconstruction tests;
* version history tests;
* audit history tests;
* E2E-GATE-01 tests.


================================================================================
# 18. A01 Acceptance Criteria
================================================================================

IA-08-A01 may be marked RESOLVED only when all applicable criteria are true.

AC-001

The Application Layer exposes the required implemented use-case boundaries.

AC-002

Application Services remain independent of HTTP and database frameworks.

AC-003

Domain rules remain delegated to the Domain Layer.

AC-004

Version semantics remain delegated to the Versioning Model and Domain Layer.

AC-005

Audit remains distinct from Transactional Events.

AC-006

Application errors have a stable application-level boundary.

AC-007

Write use cases have an explicit transaction boundary where infrastructure
supports transactional execution.

AC-008

No unsupported Change Proposal or Review semantics have been invented.

AC-009

Previously verified persistence behavior remains green.

AC-010

All required A01 tests pass.


================================================================================
# 19. Stop Conditions
================================================================================

Implementation work must stop immediately if any of the following occurs:

* a missing domain concept must be invented;
* an authoritative specification is ambiguous;
* a required Review rule is undefined;
* transaction ownership cannot be established without changing the
  Persistence Model;
* implementing A01 requires API-specific code in the Application Layer;
* implementing A01 requires Security semantics not yet defined;
* a previously verified IA-07 boundary fails.

In these cases, record the evidence and return to conformance analysis before
continuing.


================================================================================
# 20. Controlled Implementation Sequence
================================================================================

The controlled sequence is:

STEP 1

Inspect the local Application, Domain, Repository, Review, Category, Version,
Audit, and transaction components.

STEP 2

Map existing implementation components against the required Application
Service responsibilities.

STEP 3

Identify which required service boundaries can be implemented without
introducing new domain semantics.

STEP 4

Define the minimum source change.

STEP 5

Apply only that change locally.

STEP 6

Run focused A01 tests.

STEP 7

Run the full regression suite.

STEP 8

Record the verification result.

STEP 9

Only after A01 passes, proceed to IA-08-A02.

# 22. Implementation Inspection Matrix
================================================================================

This matrix records the verified implementation state of IA-08-A01.

The matrix reconciles:

* the Bootstrap Pack;
* the authoritative IA-08 Application Service specification;
* the current repository structure;
* the current Application Layer implementation;
* the Domain Layer contracts;
* the Persistence Layer capabilities.

A classification shall be based on confirmed implementation evidence.

A structural naming difference alone is not sufficient to establish a gap.


================================================================================
# 22.1 Classification
================================================================================

CONFORMANT

The required responsibility is already satisfied by the current implementation.

PARTIAL

The required responsibility is substantially present, but an explicit
application boundary, capability, or integration remains incomplete.

GAP

A required responsibility is confirmed missing or incorrectly exposed.

BLOCKED

The responsibility cannot be implemented correctly because a required
authoritative upstream capability is not currently available.

# 22.6 A01.4 — Version Service
================================================================================

Status:

PARTIAL

Existing LearningObjectService already coordinates:

* Version creation;
* version sequencing;

================================================================================

PARTIAL

* AuditRecord;
* AuditRepository;
* audit recording;
* audit retrieval.

* record_event();
* get_events();

is not separately established.

Further implementation shall preserve the existing AuditRecord and
AuditRepository contracts.


================================================================================
# 22.8 A01.6 — Application Error Boundary
================================================================================

Status:

GAP

Confirmed issues:

* LearningObjectNotFound is defined locally in LearningObjectService;
* InvalidStateTransition is owned by the Domain Layer;
* InvalidStateTransition is not translated into a stable Application error;
* no centralized Application error taxonomy is confirmed.

Required initial Application error categories:

* EntityNotFound;
* InvalidOperation;
* ValidationFailure;
* UnauthorizedOperation.

The Domain Layer shall retain ownership of Domain exceptions.

# 22.9 A01.7 — Transaction Boundary

No replacement transaction infrastructure shall be introduced until this
boundary is verified.
