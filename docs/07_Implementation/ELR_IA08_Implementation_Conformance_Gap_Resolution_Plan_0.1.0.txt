# 1. Purpose
================================================================================

This document provides the controlled implementation plan for resolving the
confirmed implementation-conformance findings identified during IA-08.

The purpose is to:

* record confirmed implementation gaps;
* establish their dependency order;
* define the intended target state;
* constrain implementation changes;
* define verification requirements;
* prevent accidental reopening of already verified architectural boundaries;
* provide a controlled bridge from conformance analysis to implementation.

This document is a guide for implementation work.

It is not itself an implementation specification.

# 3. Confirmed Findings
================================================================================

The IA-08 analysis has identified four implementation-conformance findings.

The findings do not all have the same evidence state.

The distinction between a confirmed conformance finding and a confirmed
implementation gap must be preserved.

IA-08-A01

Confirmed conformance finding.

The Application Service implementation does not yet provide sufficient
evidence of complete conformance with the authoritative Application Service
Implementation Specification.

Responsibility-level implementation inspection is required before defining
the concrete resolution.

IA-08-A02

Confirmed implementation gap.

The Transactional Event Record and the first Event Implementation layer
required by the authoritative Event Implementation Specification are not
implemented.

IA-08-A03

Confirmed implementation gap.

The Security and Authorization boundary required by the authoritative
Security Implementation Specification is not implemented.

IA-08-A04

Confirmed implementation gap.

The API Implementation Layer required by the authoritative API Implementation
Specification is not implemented.

The implementation resolution process shall not treat the four findings as
identical.

IA-08-A01 requires evidence-based responsibility-level inspection before
implementation changes are defined.

IA-08-A02, IA-08-A03, and IA-08-A04 may proceed according to their respective
resolution plans once their dependencies and implementation boundaries are
confirmed.

# 4. Finding A01 — Application Service Conformance
================================================================================

## 4.1 Current State

The current implementation contains a LearningObjectService.

The service already coordinates several domain operations, repositories,
version creation, and audit recording.

Existing capabilities include:

* create_candidate();
* submit_for_review();
* approve();
* update_knowledge();
* retire();
* get();
* get_history().

The implementation does not yet provide the complete Application Service
surface defined by the current Application Service Implementation
Specification.


================================================================================
## 4.2 Conformance Finding Under Inspection
================================================================================

The Application Service implementation currently provides a substantial part
of the required Learning Object use-case coordination.

However, complete conformance with the authoritative Application Service
Implementation Specification has not yet been established.

The following responsibilities require evidence-based implementation
inspection:

* approve_change_proposal();
* reject_change_proposal();
* Category Service;
* Version Service;
* Audit Service;
* explicit application transaction coordination;
* application-level error translation.

These responsibilities must not be classified as implementation gaps solely
because a dedicated class or method is not yet visible.

Conformance shall be assessed at the responsibility and boundary level.

The result of the inspection shall determine whether each responsibility is:

* CONFORMANT;
* PARTIAL;
* GAP;
* BLOCKED.

No implementation change shall be derived from an UNKNOWN or uninspected
responsibility.


## 4.3 Target State

The Application Layer shall provide the application-service boundaries
required by the authoritative Application Service Implementation
Specification.

Application Services shall:

* coordinate use cases;
* invoke domain behavior;
* coordinate repositories;
* coordinate versioning;
* coordinate audit;
* consume the applicable identity and authorization context where required;
* define transaction boundaries;
* translate domain failures into application-level failures.

Application Services shall not:

* contain HTTP-specific logic;
* contain FastAPI dependencies;
* contain SQLAlchemy-specific logic;
* contain PostgreSQL-specific logic;
* introduce new domain semantics;
* independently decide Review or Lifecycle semantics.

The Application Layer may consume an authorization decision or Identity
Context provided by the Security boundary.

The Application Layer must not independently implement or redefine the
Security and Authorization model.

The Security Layer remains responsible for authentication and authorization
semantics according to the authoritative Security Implementation Specification.


## 4.4 Invariants

The following invariants must remain true:

* Domain rules remain owned by the Domain Layer.
* Lifecycle rules remain owned by the Lifecycle/Domain implementation.
* Version validity remains owned by the Versioning model and its implementation.
* Review decisions remain owned by the Review process.
* Repository interfaces remain independent of infrastructure.
* Audit remains distinct from transactional domain events.


## 4.5 Verification

A01 shall be considered resolved only when:

* required application-service boundaries exist;
* application services remain framework-independent;
* use-case behavior is covered by tests;
* domain rules remain delegated to the Domain Layer;
* repository boundaries remain preserved;
* transaction behavior is verified where required;
* existing IA-07 persistence tests remain green.

# 5. Finding A02 — Transactional Event Record
================================================================================

## 5.1 Current State

The implementation contains Audit Record handling.

Audit Records are not equivalent to Transactional Event Records.

The current Event Implementation Specification requires a separate transactional
event persistence mechanism.


## 5.2 Confirmed Gap

The following Event Implementation responsibilities are not yet implemented:

* event envelope;
* transactional event record;
* event_records persistence;
* event source preservation;
* event schema version preservation;
* transactional creation of the event record;
* subsequent event publication boundary.


## 5.3 Target State

The first Event Implementation shall provide a Transactional Event Record
mechanism consistent with the authoritative Event Implementation
Specification.

The event record shall preserve at minimum:

* event_id;
* event_type;
* event_source;
* aggregate_type;
* aggregate_id;
* version;
* payload;
* occurred_at;
* published_at;
* created_at;
* metadata.


## 5.4 Transaction Rule

A transactional event record produced by a domain/application operation shall
be persisted within the same transaction as the domain change that produced
the event.

The external publication of the event shall not be required for domain
transactional consistency.

A publication failure must therefore not invalidate an already committed
domain transaction.


## 5.5 Separation Rule

Transactional Event Records are infrastructure artifacts.

They are not:

* Learning Objects;
* Knowledge Statements;
* Versions;
* Audit Records;
* Repository knowledge entities.

The Event implementation must not expand the semantic persistence boundary
of the knowledge repository.


## 5.6 Verification

A02 shall be considered resolved only when tests demonstrate:

* event creation;
* event immutability;
* correct event envelope mapping;
* correct persistence mapping;
* preservation of event_source;
* preservation of version;
* atomicity with the originating domain change;
* separation from Audit Records;
* behavior after transaction failure.

# 6. Finding A03 — Security and Authorization
================================================================================

## 6.1 Current State

The current application service accepts actor information for audit purposes.

A complete Identity Context and Authorization boundary is not yet implemented.


## 6.2 Confirmed Gap

The Security Implementation Specification requires:

Authentication
    ->
Identity Context
    ->
Authorization
    ->
API
    ->
Application Services
    ->
Domain

The implementation does not yet provide this boundary.


## 6.3 Target State

The implementation shall introduce the minimum security abstraction required
by the authoritative Security and Access Model.

The first implementation shall support:

* Identity Context;
* actor identity;
* actor type;
* roles;
* authorization decisions;
* explicit authorization failures;
* Application Layer access to the authenticated identity context.


## 6.4 Authentication Boundary

Authentication must remain abstract.

The first implementation shall not introduce a concrete external identity
provider unless separately authorized by the applicable specification.

An AuthenticationProvider abstraction is sufficient for the initial
implementation boundary.


## 6.5 Authorization Rules

The implementation shall preserve the authoritative initial role model,
including:

* SYSTEM_ADMIN;
* KNOWLEDGE_REVIEWER;
* KNOWLEDGE_PRODUCER;
* READ_ONLY_USER.

Authorization must not be redefined independently inside the API layer.

The API Layer shall invoke the authorization model rather than create a
competing role or permission model.


## 6.6 Auditability

Significant knowledge modifications shall remain attributable to an actor.

Security integration must enrich and protect auditability.

It must not replace the Audit Model with the Event Model.


## 6.7 Verification

A03 shall be considered resolved only when tests demonstrate:

* unauthenticated access rejection;
* insufficient-role rejection;
* authorized operation;
* correct Identity Context propagation;
* authorization before protected operation;
* actor attribution in significant modifications.


================================================================================
# 7. Finding A04 — API Implementation
================================================================================

## 7.1 Current State

The implementation does not yet contain the API layer required by the
current API Implementation Specification.


## 7.2 Confirmed Gap

The required API boundary includes:

* FastAPI;
* REST endpoints;
* /api/v1;
* Learning Object access;
* history access;
* category access;
* health endpoint;
* protected write operations;
* delegation to Application Services.


## 7.3 Target State

The API Layer shall be an adapter.

It shall:

* receive HTTP requests;
* validate transport-level input;
* establish or receive the Identity Context;
* invoke authorization;
* invoke Application Services;
* translate application errors into HTTP responses;
* return transport representations.

The API Layer shall not:

* contain domain rules;
* contain lifecycle semantics;
* contain versioning semantics;
* directly access persistence infrastructure;
* directly manipulate database models;
* define an independent authorization model.


## 7.4 Dependency Rule

The intended dependency direction is:

API
    ->
Application
    ->
Domain / Repository Interfaces

Infrastructure implementations shall remain behind the appropriate
application/repository boundaries.


## 7.5 Verification

A04 shall be considered resolved only when tests demonstrate:

* endpoint availability;
* request validation;
* correct Application Service delegation;
* authorization enforcement;
* correct response mapping;
* correct error mapping;
* absence of direct persistence bypass.

# 9. Implementation Control Rules
================================================================================

The following rules apply to all IA-08 implementation work.

RULE-001

One confirmed finding shall be implemented at a time.

RULE-002

Each implementation change shall have an explicit verification step.

RULE-003

No implementation change may introduce new domain semantics without a
corresponding authoritative specification.

RULE-004

Previously verified IA-07 persistence behavior must remain green.

RULE-005

Audit Records and Transactional Event Records must remain distinct.

RULE-006

The API must not bypass Application Services.

RULE-007

Security must not redefine domain semantics.

RULE-008

Authentication providers remain abstract unless explicitly brought into
scope.

RULE-009

Infrastructure dependencies must not leak into the Domain Layer.

RULE-010

The implementation must not modify the authoritative specification corpus
as a substitute for resolving an implementation gap.

RULE-011

If implementation evidence contradicts this plan, stop and reconcile against
the authoritative specification before proceeding.

RULE-012

Repository modifications are not performed as part of this planning
document. Implementation changes are applied only through the controlled
local development workflow.
