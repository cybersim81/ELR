### A01.2 — Change Proposal / Learning Review Boundary

**IMPLEMENTED / VERIFIED / CONFORMANT**

The application-service implementation establishes the required Change Proposal
/ Learning Review boundary.

The repository contains the application components required to establish the
review-gated change flow:

* `ChangeProposal`;
* `ChangeType`, including `CREATE`, `UPDATE`, and `MERGE`;
* `ChangeProposalService`;
* `LearningReviewService`;
* `LearningReviewAdapter`;
* `LearningObjectChangeApplier`;
* ChangeProposal persistence;
* Review Decision Trace persistence;
* review validation and decision services;
* focused application and review tests.

`ChangeProposalService` coordinates the use case in the following order:

```text
Change Proposal
        |
        v
Learning Review
        |
        +-- APPROVE ------------> LearningObjectChangeApplier.apply()
        |
        +-- REJECT -------------> no apply()
        |
        +-- REQUEST_REVISION ---> no apply()
````

The application service therefore does not apply a Change Proposal before
Learning Review has produced an `APPROVE` decision.

`REJECT` and `REQUEST_REVISION` do not invoke
`LearningObjectChangeApplier.apply()`.

The `LearningObjectChangeApplier` additionally verifies:

```text
review_trace.proposal_id == proposal.id
review_trace.decision == APPROVE
```

before mutation is permitted.

#### CREATE

**VERIFIED / CONFORMANT**

An approved `CREATE` Change Proposal:

* creates a new Learning Object;
* persists it;
* creates the initial Version;
* records the corresponding Audit event.

#### UPDATE

**VERIFIED / CONFORMANT**

An approved `UPDATE` Change Proposal:

* resolves the target Learning Object;
* updates the existing Learning Object;
* preserves its identity;
* creates the next immutable Version;
* records the corresponding Audit event.

#### MERGE

**VERIFIED / CONFORMANT**

An approved `MERGE` Change Proposal:

* resolves the target Learning Object;
* updates the existing Learning Object;
* preserves its identity;
* creates the next immutable Version;
* records the corresponding Audit event.

The implementation therefore provides an execution path for all three
Change Proposal types through the review-gated ChangeApplier boundary.

#### Negative Paths

The focused tests verify rejection of:

* non-approved proposals;
* Review Decision Traces belonging to a different proposal;
* missing target Learning Objects;
* invalid target identifiers;
* invalid Knowledge Statement payloads.

Non-approved proposals do not produce Learning Object mutation.

### A01.4 — Version Responsibility

**CONFORMANT**

Version creation is implemented through `VersionService`.

The service determines the next Version number from the repository and
persists a new immutable Version.

Existing Version history is preserved.

### A01.5 — Learning Object Update

**CONFORMANT**

`LearningObjectService.update_knowledge()`:

* validates the domain state transition;
* updates the Learning Object;
* creates a new immutable Version;
* records the corresponding AuditRecord;
* records a `LearningObjectUpdated` EventRecord.

The review-gated `UPDATE` execution path is provided separately through
`LearningObjectChangeApplier`.

Persistence and rollback behavior are covered by focused tests.
