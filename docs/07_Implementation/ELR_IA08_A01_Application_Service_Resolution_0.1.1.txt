# IA-08-A01 — Application Service Resolution

**Version:** 0.1.1
**Status:** ACTIVE — PARTIAL CONFORMANCE

## Current Disposition

IA-08-A01 is **not fully closed**.

The application-service layer contains implemented responsibilities for:

* Learning Object creation;
* Learning Object submission for review;
* Learning Object approval;
* immutable Version creation;
* Learning Object knowledge update;
* AuditRecord creation;
* EventRecord creation for Learning Object updates;
* ChangeProposal creation;
* Learning Review invocation;
* transactional persistence boundaries where explicitly verified.

The remaining A01 status shall therefore be assessed **by responsibility**, rather than by treating the entire A01 area as either open or closed.

## Responsibility Status

### A01.1 — Learning Object Creation

**CONFORMANT**

Evidence includes:

* `LearningObjectService.create_candidate()`;
* Learning Object repository persistence;
* creation audit record;
* corresponding application-service tests.

### A01.2 — Change Proposal / Learning Review Boundary

**IMPLEMENTED / CONFORMANCE VERIFICATION IN PROGRESS**

The current application-service implementation establishes the Change Proposal / Learning Review boundary.

The repository contains the application components required to establish the review-gated change flow:

* `ChangeProposal`;
* `ChangeType`, including `CREATE`, `UPDATE`, and `MERGE`;
* `ChangeProposalService`;
* `LearningReviewService`;
* `LearningReviewAdapter`;
* `LearningObjectChangeApplier`;
* ChangeProposal persistence;
* Review Decision Trace persistence;
* review validation and decision services;
* focused application and review tests.

`ChangeProposalService` coordinates the use case in the following order:

```text
Change Proposal
        │
        v
Learning Review
        │
        ├── APPROVE ───────────→ LearningObjectChangeApplier.apply()
        │
        ├── REJECT ─────────────→ no apply()
        │
        └── REQUEST_REVISION ───→ no apply()
```

The application service therefore does not apply a Change Proposal before Learning Review has produced an `APPROVE` decision.

`REJECT` and `REQUEST_REVISION` do not invoke `LearningObjectChangeApplier.apply()`.

The current implementation and focused tests resolve the previous implementation-level `BLOCKED` condition for the Change Proposal / Learning Review application boundary.

The remaining A01.2 activity is responsibility-level conformance verification of the implemented `CREATE`, `UPDATE`, and `MERGE` semantics against the authoritative `03_Processes` and `06_System` specifications.

Therefore A01.2 remains open only as a **conformance verification item**. It is no longer blocked by absence of the required application boundary or by absence of the `APPROVE` / `REJECT` / `REQUEST_REVISION` gating behavior.

### A01.3 — Learning Object Approval

**CONFORMANT**

Approval transitions a proposed Learning Object to Active and creates the initial immutable Version.

Evidence includes:

* `LearningObject.approve()`;
* `LearningObjectService.approve()`;
* Version creation;
* AuditRecord creation;
* transactional persistence tests;
* rollback verification.

### A01.4 — Version Responsibility

**CONFORMANT**

Version creation is implemented through `VersionService`.

The service determines the next Version number from the repository and persists a new immutable Version.

The existing Version history is preserved.

### A01.5 — Learning Object Update

**CONFORMANT**

`LearningObjectService.update_knowledge()`:

* validates the domain state transition;
* updates the Learning Object;
* creates a new immutable Version;
* records the corresponding AuditRecord;
* records a `LearningObjectUpdated` EventRecord.

Persistence and rollback behavior are covered by focused tests.

### A01.6 — Application Error Boundary

**RESOLVED / CONFORMANT**

The application service translates domain state-transition failures into application-level `InvalidOperation` errors.

The detailed responsibility remains documented by:

`ELR_IA08_A01_06_Application_Error_Boundary_0.2.0.txt`

### A01.7 — Transaction Boundary

**RESOLVED / CONFORMANT**

The verified transactional boundary uses the existing SQLAlchemy Session.

Application services do not autonomously commit the relevant operations.

Rollback tests verify that Learning Object, Version, AuditRecord and EventRecord persistence participate in the expected transaction boundary.

## Final A01 Position

A01 shall **not** be marked `COMPLETE / CLOSED` until the remaining responsibility-level conformance questions have been verified.

The principal remaining verification area is:

**A01.2 — Change Proposal / Learning Review / CREATE / UPDATE / MERGE semantics**

The implementation-level `BLOCKED` condition previously associated with the Change Proposal / Learning Review application boundary is resolved.

The current implementation establishes the required review-gated application flow:

```text
APPROVE
    ↓
LearningObjectChangeApplier.apply()

REJECT
    ↓
no apply()

REQUEST_REVISION
    ↓
no apply()
```

Accordingly, the remaining A01.2 status represents a **conformance verification gap**, not an implementation absence and not an implementation blocker.

A01 remains partially conformant only because the responsibility-level semantic comparison of `CREATE`, `UPDATE`, and `MERGE` against the authoritative specifications has not yet been recorded as complete.
