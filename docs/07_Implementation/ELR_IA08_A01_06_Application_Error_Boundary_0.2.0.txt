# 1. Purpose
================================================================================

This document records the implemented IA-08-A01.6 Application Error Boundary and its verified conformance status.

The Application Layer provides a stable error boundary while preserving:

* Domain ownership of domain rules and domain exceptions;
* existing LearningObject lifecycle behavior;
* existing repository contracts;
* existing persistence behavior;
* existing API behavior.

No additional implementation work is currently required for IA-08-A01.6.


================================================================================
# 2. Confirmed Finding
================================================================================

The previously identified IA-08-A01.6 Application Error Boundary gap has been resolved.

The current implementation provides:

* a centralized Application error taxonomy;
* `EntityNotFound` for missing Learning Objects;
* `InvalidOperation` for translated known domain state-transition failures;
* preservation of the original Domain exception through exception chaining;
* no catch-all exception translation.

The current Application Service implementation therefore establishes the required Domain-to-Application error boundary.


================================================================================
# 3. Required Boundary
================================================================================

The implemented error flow is:

```text
Domain exception
    ↓
Application Service
    ↓
Application error
    ↓
Application consumer
```

The Domain Layer retains ownership of domain rules, invariants, and domain exceptions.

The Application Layer translates only known Domain failures at the Application boundary.

This boundary is implemented and verified for the currently identified A01.6 responsibilities.


================================================================================
# 4. Application Error Taxonomy
================================================================================

The current Application Layer provides a centralized application-error taxonomy for errors crossing the Application boundary. The taxonomy is implemented through dedicated Application-layer exception definitions and is used consistently by the relevant Application Services.

* ApplicationError;
* EntityNotFound;
* InvalidOperation;
* ValidationFailure;
* UnauthorizedOperation.


ApplicationError shall be the common Application Layer base exception.

These exceptions shall contain no:

* HTTP behavior;
* FastAPI dependencies;
* SQLAlchemy dependencies;
* database-driver dependencies;
* transport-specific response behavior.


================================================================================
# 5. Not-Found Boundary
================================================================================

The former service-local LearningObjectNotFound exception has been removed
and replaced by the centralized Application error:

EntityNotFound


The Application Service raises EntityNotFound when a requested Learning
Object does not exist.

Unexpected repository or infrastructure failures shall not be converted into
EntityNotFound.


================================================================================
# 6. Domain-to-Application Translation
================================================================================

The confirmed initial Domain-to-Application translation is:

InvalidStateTransition
    ->
InvalidOperation


The Domain exception shall remain defined and owned by the Domain Layer.

The Application Service shall translate the known exception at the
Application boundary.


================================================================================
# 7. Exception Cause Preservation
================================================================================

Domain-to-Application translation shall preserve the original Domain
exception as the exception cause.

Conceptually:

try:
    domain_operation()
except InvalidStateTransition as exc:
    raise InvalidOperation(...) from exc


The original InvalidStateTransition must therefore remain available through:

exception.__cause__


No catch-all exception translation is permitted.


================================================================================
# 8. Affected Application Operations
================================================================================

The following LearningObjectService operations were inspected for
InvalidStateTransition translation:

* submit_for_review();
* approve();
* update_knowledge();
* retire().


Only operations that can actually raise InvalidStateTransition receive the
translation boundary.

Successful behavior shall remain unchanged.


================================================================================
# 9. ValidationFailure
================================================================================

ValidationFailure shall exist as part of the centralized Application error
taxonomy.

This implementation does not introduce a new Domain-to-Application mapping
for ValidationFailure.

No existing validation behavior shall be changed solely to exercise this
exception.


================================================================================
# 10. UnauthorizedOperation
================================================================================

UnauthorizedOperation shall exist as part of the centralized Application
error taxonomy.

This implementation does not introduce authorization logic.

Authorization remains outside the scope of A01.6.


================================================================================
# 11. Exception Scope
================================================================================

Only known, explicitly handled Domain exceptions shall be translated.

The implementation shall not introduce:

except Exception:

or equivalent catch-all translation.

Unexpected programming, persistence, infrastructure, or system errors shall
remain distinguishable from known Application failures.


================================================================================

================================================================================
# 13. Architectural Constraints
================================================================================

The implementation must preserve:

Application
    ->
Domain
    ->
Repository Interfaces


The Application Layer shall not import:

* FastAPI;
* SQLAlchemy;
* PostgreSQL drivers;
* concrete persistence repositories;
* HTTP response classes.


The Domain Layer shall not be modified merely to support the Application
error translation.
