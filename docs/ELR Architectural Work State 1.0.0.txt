4. ESTABLISHED ARCHITECTURAL DECISIONS
======================================

LearningObject.state:

Represents the editorial/domain lifecycle of the Learning Object.

It does not represent:

* Learning State;
* Mastery;
* Mastery State.

Learning State:

Represents the user's current learning-process condition with respect to
a Learning Object.

Learning State and Mastery State are distinct concepts.

Mastery State:

Represents the user's current mastery state with respect to a Learning
Object.

Mastery Evidence:

Represents observable evidence used by the Mastery Engine to evaluate
and update Mastery State.

Mastery Engine:

Interprets Mastery Evidence and produces Mastery State updates.

Knowledge:

The persistent knowledge model is centered on:

* Learning Object;
* Anchor;
* Knowledge Statement;
* Knowledge Category.

Knowledge Statement:

Represents the principal knowledge content of a Learning Object.

The approved architecture conceptually represents a Learning Object as:

```
Anchor + Knowledge Statement
```

A Learning Object represents one independent atomic knowledge.

A single source statement may produce multiple Learning Objects.

A new Knowledge Statement may update an existing Learning Object when
the underlying atomic knowledge remains the same.

Knowledge Statement is NOT currently established as an autonomous
Domain Entity with:

* independent UUID;
* independent lifecycle;
* independent versioning;
* independent ownership.

Therefore no autonomous KnowledgeStatement Domain Entity should be
introduced without an explicit architectural decision.

================================================================
5. CURRENT KNOWLEDGE STATEMENT DOMAIN QUESTION
==============================================

The current Python LearningObject contains:

```
statement: str
```

The semantic role of this field appears to correspond to the documented
Knowledge Statement concept.

However, the Domain implementation does not explicitly name the concept
as Knowledge Statement.

The current open question is NOT whether Knowledge Statement exists
architecturally. It clearly does.

The open question is its executable Domain representation:

* primitive/string representation;
* explicitly named Value Object;
* another approved Domain construct.

Do not introduce an autonomous KnowledgeStatement Entity merely because
the Persistence Model contains a KnowledgeStatement persistence
structure.

The Persistence Model must follow the approved Domain decision.

================================================================
6. CURRENT MASTERY QUESTION
===========================

Mastery State is already formally specified.

Do NOT create another Mastery State Specification.

The current architecture established by the Mastery Engine and Mastery
State documentation treats Mastery State as the user's mastery state
with respect to a Learning Object.

However, the ELR Domain Model Specification 1.0.0 still contains wording
that states:

```
Every Learning Object possesses exactly one Mastery.
```

It further describes Mastery as:

* a dependent element of the LearningObject aggregate;
* non-autonomous;
* persistent with the Learning Object.

This creates a documentation discrepancy with the User-specific Mastery
State model defined by the Mastery Engine / Mastery State documentation.

This discrepancy must be reconciled in documentation.

Do NOT resolve it through Python implementation.

Do NOT add Mastery to LearningObject.

Do NOT create Mastery persistence models.

Do NOT infer a final cardinality from the current SQLAlchemy model.

```
|
```

```
   Mastery Evidence
          |

          |

    Mastery State
```

reconciliation of the remaining Domain Model documentation conflict.

