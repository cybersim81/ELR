ELR Core Model Discrepancy Matrix

Status: Working Architectural Audit
Scope: Core Model, Domain Model, Learning State, Mastery, Persistence
Purpose: Track discrepancies between approved/draft ELR specifications and the current implementation.

================================================================

1. LearningObject lifecycle state vs Learning State
   ================================================================

Status: RESOLVED

Finding:

LearningObject.state represents the editorial/domain lifecycle of the
Learning Object.

Current lifecycle states:

* Candidate
* Proposed
* Reviewed
* Active
* Updated
* Retired
* Rejected

Learning State is a separate concept representing the current learning
condition of a User with respect to a Learning Object.

Decision:

LearningObject.state must not represent Learning State.

Learning State must not be added as an attribute of LearningObject.

The two concepts belong to different semantic boundaries:

LearningObject.state
= lifecycle of the knowledge object

Learning State
= learning condition of a User in relation to the knowledge object

Evidence:

* Learning Object Specification 1.0.0
* Learning State Specification 1.0.0
* Current LearningObject domain implementation

================================================================

2. Learning State vs Mastery State
   ================================================================

Status: RESOLVED

Finding:

Learning State and Mastery State are distinct concepts.

Learning State represents the learner's current condition in the learning
process.

Mastery State represents the user's degree/state of mastery with respect
to a Learning Object.

Decision:

The concepts must not be merged.

Learning State:

* Unknown
* Introduced
* Practicing
* Developing
* Established
* Needs Review

Mastery State represents the state of the user's mastery with respect to
a Learning Object.

The relationship between the concepts is:

Learning State
= learner's current learning-process condition

Mastery State
= learner's current mastery state

The Learning State Specification explicitly distinguishes the Mastery
Reference from the complete Mastery State.

The Mastery Reference does not constitute the Mastery State itself.

Evidence:

* Learning State Specification 1.0.0
* Mastery State Specification 1.0.0
* Mastery Engine Specification 1.0.0

3. Learning Object vs Mastery
=============================

Status: RESOLVED

Resolution:

The documentation conflict concerning the ownership and semantic nature of
Mastery has been resolved.

The reconciled model is:

Learning Object
= persistent linguistic knowledge

Mastery State
= current mastery state of a specific User
with respect to a specific Learning Object

Mastery State is not an intrinsic property of the Learning Object and does
not belong to the LearningObject aggregate boundary.

The Mastery Engine is responsible for interpreting Mastery Evidence and
evolving the Mastery State according to the Mastery Engine and Mastery State
Specifications.

Resolution Actions Completed:

1. ELR Domain Model Specification

   The Domain Model has been reconciled so that:

   • Mastery State is User-specific;
   • Mastery State is not owned by the Learning Object;
   • Mastery State is outside the LearningObject aggregate boundary;
   • Learning Object represents persistent linguistic knowledge;
   • Mastery State represents the user's mastery of that knowledge.

2. Mastery State / Mastery Engine

   The Mastery State Specification and Mastery Engine Specification remain
   the authoritative definitions of the semantic nature and evolution of
   Mastery State.

3. Architecture Decision Log

   ADR-013 has been reconciled to define Mastery as a User-specific
   Mastery State relative to a specific Learning Object.

   ADR-015 has been reconciled so that the Mastery Engine updates the
   Mastery State of the specific User with respect to the specific Learning
   Object, without making Mastery State a property of the Learning Object.

4. Architecture Specification

   ELR Architecture Specification 1.1.0 has been reconciled under:

   "Mastery State as User-Specific Learning State"

   The Architecture Specification now explicitly separates:

   • Learning Object = knowledge;
   • Mastery State = User-specific mastery state.

5. Evidence Model

   Mastery Evidence remains evidence consumed by the Mastery Engine and does
   not become part of the Learning Object or Mastery State.

6. Persistence Boundary

   No persistence implementation has been changed as part of this
   reconciliation.

   Persistence decisions concerning Mastery State remain governed by the
   Persistence Mapping Specification and the applicable Mastery
   specifications.

Authoritative Interpretation:

The authoritative conceptual relationship is:

User
|
+---- Mastery State ----> Learning Object

The Learning Object may therefore be associated with different Mastery
States for different Users.

The Learning Object itself does not possess a Mastery State.

Validation:

The reconciled model has been checked against:

• ELR Domain Model Specification 1.0.0 (reconciled content);
• Learning Object Specification 1.0.0;
• Learning State Specification 1.0.0;
• Mastery Engine Specification 1.0.0;
• Mastery State Specification 1.0.0;
• Evidence Model Specification 1.0.1;
• Persistence Mapping Specification 0.1.0;
• ELR Architecture Specification 1.1.0;
• ELR Architecture Decision Log 1.0.0;
• ELR Architecture Consistency Matrix 1.1.0.

Implementation Boundary:

No Python implementation or persistence implementation change is implied by
this documentation reconciliation.

The reconciliation is considered complete at the documentation level.
Implementation changes, if any, require a separate architectural and
implementation review.

Resolution Date:

2026-08-09

4. Mastery State Domain Contract
   ================================================================

Status: DOCUMENTATION BASELINE ESTABLISHED / IMPLEMENTATION DEFERRED

Finding:

Mastery Engine Specification 1.0.0 defines Mastery State as the current
state of the relationship between a User and a Learning Object.

The precise Mastery State model was intentionally delegated to a separate
specification.

Decision:

The Mastery State Specification 1.0.0 now establishes the architectural
baseline for Mastery State.

The specification defines:

* semantic role;
* relationship to User;
* relationship to Learning Object;
* relationship to Learning State;
* relationship to Mastery Evidence;
* relationship to the Mastery Engine;
* current persistence boundary.

The specification does not require immediate Python or persistence
implementation.

Current implementation:

The Domain Python model does not contain a Mastery State representation.

Persistence:

The Persistence Mapping Specification 0.1.0 excludes Mastery State from
Core Repository v0.1 persistence.

Decision:

Mastery State remains architecturally defined but implementation-deferred.

Do not implement:

* MasteryState domain entity;
* MasteryState value object;
* MasteryState SQLAlchemy model;
* Mastery persistence tables;

until an explicit implementation decision is approved.

5. Mastery Evidence vs Mastery State
   ================================================================

Status: RESOLVED

Finding:

Mastery Evidence is used by the Mastery Engine as input for mastery
calculation and evolution.

Mastery Evidence is not itself the Mastery State.

Decision:

The conceptual processing boundary is:

Learning Activity / Evidence
|
v
Mastery Evidence
|
v
Mastery Engine
|
v
Mastery State

Mastery Evidence represents observable evidence.

Mastery Engine interprets the evidence and determines mastery updates.

Mastery State represents the current state of mastery.

Evidence history must not be treated as the Mastery State itself.

Mastery Evidence must not be introduced into the LearningObject domain
entity merely to support Mastery Engine implementation.

Evidence history belongs to the Evidence Model and its historical
persistence boundary.

Evidence:

* Evidence Model Specification 1.0.1
* Mastery Engine Specification 1.0.0
* Mastery State Specification 1.0.0

|
+-- Learning State

Process Evidence
|
+-- Mastery Evidence

Mastery Engine

Learning State and Mastery State do not constitute persistent knowledge.

Mastery State represents the learner's mastery of existing knowledge.

7. LearningObject implementation vs documented Domain Model
   ================================================================

Status: OPEN / DEFERRED

Finding:

The approved/domain documentation describes the Learning Object as the
central knowledge object and references supporting structures including
Anchor, Knowledge Statement, Knowledge Category, Examples, Notes and
Mastery-related concepts.

The current Python LearningObject implementation contains:

* anchor_id
* statement
* category_id
* id
* state
* version
* created_at
* updated_at

Decision:

The current implementation may represent only the subset of the Domain
Model that has been explicitly implemented and verified.

Missing documented concepts must not be added automatically.

Each missing concept requires an explicit architectural decision before
implementation.

No implementation should infer additional Domain attributes solely from
high-level documentation.

8.  LearningObject Domain representation vs Knowledge Statement
    ================================================================

Status: OPEN / DOCUMENTATION CONFLICT / ARCHITECTURAL DECISION REQUIRED

Finding:

The Architecture Consistency Matrix identifies the Learning Object
Specification as the owner of the Knowledge Statement concept.

The current Learning Object Specification defines Knowledge Statement as
part of the Learning Object conceptual model.

The current Domain Model Specification 1.0.0 is a DRAFT document and
therefore does not constitute an independently authoritative architectural
decision.

However, the current DRAFT implementation documentation introduces a
different representation.

The ELR Core Domain Implementation Specification 0.1.0 defines:

```
Entity: KnowledgeStatement
```

with an explicit:

```
id: Identificativo
```

The ELR Persistence Mapping Specification 0.1.0 defines a dedicated
knowledge_statements persistence structure and states that the Knowledge
Statement has an independent UUID identity.

Architectural discrepancy:

The authoritative architectural ownership of Knowledge Statement belongs
to the Learning Object Specification.

The DRAFT implementation and persistence specifications currently express
Knowledge Statement as an independently identifiable construct.

This does not by itself establish an independent Domain identity or
aggregate boundary for Knowledge Statement.

The Persistence Mapping Specification explicitly states that the current
LearningObject domain contract remains authoritative for the first
implementation and that the Persistence Layer must not silently replace
the existing Domain contract.

Therefore, the persistence representation must not be interpreted as an
architectural decision to make Knowledge Statement an autonomous Domain
Entity.

Decision required:

Determine the authoritative executable Domain representation of
Knowledge Statement within the LearningObject model.

The decision must explicitly establish whether Knowledge Statement is:

1. represented as an internal value/primitive representation within
   LearningObject;
2. represented as an explicit Value Object within LearningObject; or
3. represented as an autonomous Domain Entity with independent identity.

If option 3 is selected, the relevant authoritative Domain documentation
and architectural documentation must be explicitly revised and approved
before implementation.

Constraints:

• Learning Object remains the aggregate root unless an explicit
architectural decision states otherwise;

• Knowledge Statement is owned documentally by the Learning Object
Specification;

• the Domain Model Specification 1.0.0 is currently DRAFT;

• the DRAFT implementation specifications cannot override approved
architectural decisions;

• persistence identity must not be interpreted as Domain identity without
an explicit architectural decision;

• the Persistence Layer must not silently replace or redefine the current
Domain contract.

Required follow-up:

1. determine the authoritative executable Domain representation of
   Knowledge Statement;
2. reconcile the DRAFT Core Domain Implementation Specification;
3. reconcile the DRAFT Persistence Implementation Specification;
4. revise the relevant authoritative Domain documentation if the decision
   requires a different Domain construct;
5. update persistence mapping and implementation specifications if
   required;
6. update this matrix after the decision.

 No Python or persistence implementation should precede this decision.

9. Mastery persistence boundary
   ================================================================

Status: RESOLVED FOR CORE REPOSITORY v0.1 / DEFERRED FOR FUTURE REPOSITORIES

Finding:

The Persistence Mapping Specification 0.1.0 explicitly excludes Mastery
State from Core Repository v0.1 persistence.

The broader ELR architecture recognizes Mastery State as an architectural
concept.

Decision:

Core Repository v0.1 persistence must not introduce Mastery persistence.

This is a persistence boundary decision, not a rejection of the Mastery
concept.

Future persistence of Mastery requires:

* an approved Mastery Domain contract;
* an explicit persistence boundary;
* an approved Data Model relationship;
* an explicit implementation decision.

Until those decisions are made, no Mastery persistence model or table
should be introduced.

10. ORM isolation
    ================================================================

Status: RESOLVED

Finding:

SQLAlchemy persistence models must remain separate from Domain entities.

Decision:

Domain entities:

* must not inherit from SQLAlchemy declarative classes;
* must not import SQLAlchemy;
* must not depend on database sessions;
* must not contain ORM metadata.

Persistence models belong under:

app/persistence/

The current AnchorModel implementation follows this boundary.

================================================================

11. Domain identity vs persistence identity
    ================================================================

Status: RESOLVED

Finding:

ELR Domain entities use UUID-based identity.

Decision:

Persistence must preserve existing domain-generated UUIDs.

Persistence must not silently replace domain identity with a separate
database-generated identity.

Database surrogate identifiers may only be introduced when they do not
replace or alter the Domain identity contract.

================================================================

12. Timestamp preservation
    ================================================================

Status: RESOLVED

Finding:

Domain timestamps are timezone-aware UTC timestamps.

Decision:

Persistence must preserve:

* created_at
* updated_at
* historical creation timestamps where applicable

Database persistence must not silently convert domain timestamps into
local time.

================================================================

13. Version history preservation
    ================================================================

Status: RESOLVED

Finding:

Version represents immutable historical state.

Decision:

Persistence must preserve historical Version records independently of
current LearningObject state.

Ordinary LearningObject updates must not overwrite historical Version
records.

================================================================

14. Audit history preservation
    ================================================================

Status: RESOLVED / IMPLEMENTATION CONSTRAINT

Finding:

Audit records represent append-oriented historical information.

Decision:

Updating an entity must not silently overwrite or erase existing audit
records.

16. Documentation authority and status
    ================================================================

Status: OPEN / ACTION REQUIRED

Finding:

The repository contains documents with different statuses, including
APPROVED and DRAFT specifications.

Some discrepancies arise because high-level Domain documentation,
specialized specifications, and Persistence documentation do not always
express the same level of detail.

Decision:

Before implementing a disputed concept:

1. identify the authoritative specification;
2. identify its status and version;
3. reconcile conflicting specifications;
4. update the documentation where required;
5. only then modify the Domain or Persistence implementation.

No implementation decision should be used to silently resolve an
architectural documentation conflict.

This rule remains an active architectural constraint.

# Current Architectural Position

The current architecture establishes the following separation:

Learning Object
= persistent knowledge object

LearningObject.state
= editorial/domain lifecycle

Learning State
= learner's current learning-process condition

Mastery Evidence
= observable evidence concerning mastery

Mastery Engine
= interpretation and processing of Mastery Evidence

Mastery State
= current mastery state of User with respect to Learning Object

Knowledge Statement
= principal knowledge content of the Learning Object

Anchor
= linguistic unit to which the Learning Object and Knowledge Statement
are associated

Core Repository v0.1 Persistence
= knowledge and historical repository structures explicitly approved by
the Persistence Mapping Specification

Mastery State is therefore architecturally recognized, formally
documented, and intentionally implementation-deferred.

Knowledge Statement alignment is architecturally recognized but remains
open at the executable Domain representation level until the Learning
Object Specification is reviewed.
