ELR Core Model Discrepancy Matrix

Status: Working Architectural Audit
Scope: Core Model, Domain Model, Learning State, Mastery, Persistence
Purpose: Track discrepancies between approved/draft ELR specifications and the current implementation.

================================================================

1. LearningObject lifecycle state vs Learning State
   ================================================================

Status: RESOLVED

Finding:

LearningObject.state represents the editorial/domain lifecycle of the
Learning Object.

Current lifecycle states:

* Candidate
* Proposed
* Reviewed
* Active
* Updated
* Retired
* Rejected

Learning State is a separate concept representing the current learning
condition of a User with respect to a Learning Object.

Decision:

LearningObject.state must not represent Learning State.

Learning State must not be added as an attribute of LearningObject.

The two concepts belong to different semantic boundaries:

LearningObject.state
= lifecycle of the knowledge object

Learning State
= learning condition of a User in relation to the knowledge object

Evidence:

* Learning Object Specification 1.0.0
* Learning State Specification 1.0.0
* Current LearningObject domain implementation

================================================================

2. Learning State vs Mastery State
   ================================================================

Status: RESOLVED

Finding:

Learning State and Mastery State are distinct concepts.

Learning State represents the learner's current condition in the learning
process.

Mastery State represents the user's degree/state of mastery with respect
to a Learning Object.

Decision:

The concepts must not be merged.

Learning State:

* Unknown
* Introduced
* Practicing
* Developing
* Established
* Needs Review

Mastery State represents the state of the user's mastery with respect to
a Learning Object.

The relationship between the concepts is:

Learning State
= learner's current learning-process condition

Mastery State
= learner's current mastery state

The Learning State Specification explicitly distinguishes the Mastery
Reference from the complete Mastery State.

The Mastery Reference does not constitute the Mastery State itself.

Evidence:

* Learning State Specification 1.0.0
* Mastery State Specification 1.0.0
* Mastery Engine Specification 1.0.0

================================================================

3. Learning Object vs Mastery
   ================================================================

Status: RESOLVED

Finding:

The Learning Object represents knowledge.

Mastery represents the user's mastery of that knowledge.

The Mastery Engine Specification defines Mastery as a relationship
between a User and a Learning Object.

Decision:

Mastery must not be interpreted as an editorial property of
LearningObject.

The semantic relationship is:

User
|
+---- Learning Object
|
+---- Mastery State

The Learning Object represents the knowledge.

The Mastery State represents the user's mastery of that knowledge.

The Mastery Engine is responsible for producing/updating Mastery State.

No Mastery attribute must be added to LearningObject merely because
Mastery appears as a supporting concept in high-level Domain
documentation.

Evidence:

* Learning Object Specification 1.0.0
* Mastery Engine Specification 1.0.0
* Mastery State Specification 1.0.0

================================================================

4. Mastery State Domain Contract
   ================================================================

Status: DOCUMENTATION BASELINE ESTABLISHED / IMPLEMENTATION DEFERRED

Finding:

Mastery Engine Specification 1.0.0 defines Mastery State as the current
state of the relationship between a User and a Learning Object.

The precise Mastery State model was intentionally delegated to a separate
specification.

Decision:

The Mastery State Specification 1.0.0 now establishes the architectural
baseline for Mastery State.

The specification defines:

* its semantic role;
* its relationship to User;
* its relationship to Learning Object;
* its relationship to Learning State;
* its relationship to Mastery Evidence;
* its relationship to the Mastery Engine;
* its current persistence boundary.

The specification does not require immediate Python or persistence
implementation.

Current implementation:

The Domain Python model does not contain a Mastery State representation.

Persistence:

The Persistence Mapping Specification 0.1.0 excludes Mastery State from
Core Repository v0.1 persistence.

Decision:

Mastery State remains architecturally defined but implementation-deferred.

Do not implement:

* MasteryState domain entity;
* MasteryState value object;
* MasteryState SQLAlchemy model;
* Mastery persistence tables;

until an explicit implementation decision is approved.

================================================================

5. Mastery Evidence vs Mastery State
   ================================================================

Status: RESOLVED

Finding:

Mastery Evidence is used by the Mastery Engine as input for mastery
calculation and evolution.

Mastery Evidence is not itself the Mastery State.

Decision:

The conceptual processing boundary is:

Learning Activity / Evidence
|
v
Mastery Evidence
|
v
Mastery Engine
|
v
Mastery State

Mastery Evidence represents observable evidence.

Mastery Engine interprets the evidence and determines mastery updates.

Mastery State represents the current state of mastery.

Evidence history must not be treated as the Mastery State itself.

Mastery Evidence must not be introduced into the LearningObject domain
entity merely to support Mastery Engine implementation.

Evidence history belongs to the Evidence Model and its historical
persistence boundary.

Evidence:

* Evidence Model Specification 1.0.1
* Mastery Engine Specification 1.0.0
* Mastery State Specification 1.0.0

================================================================

6. Knowledge vs Learning State vs Mastery State
   ================================================================

Status: RESOLVED

Finding:

The Evidence Model and related documentation previously used terminology
that could be interpreted as treating Mastery as knowledge.

Decision:

The architectural distinction is:

Knowledge
|
+-- Learning Object
+-- Anchor
+-- Knowledge Statement
+-- Knowledge Category

User Learning Context
|
+-- Learning State
+-- Mastery State

Process Evidence
|
+-- Mastery Evidence
|
v
Mastery Engine
|
v
Mastery State

Learning State and Mastery State do not constitute persistent knowledge.

Mastery State represents the learner's mastery of existing knowledge.

Evidence:

* Evidence Model Specification 1.0.1
* Learning Object Specification 1.0.0
* Learning State Specification 1.0.0
* Mastery State Specification 1.0.0

================================================================

7. LearningObject implementation vs documented Domain Model
   ================================================================

Status: OPEN / DEFERRED

Finding:

The approved/domain documentation describes the Learning Object as the
central knowledge object and references supporting structures including
Anchor, Knowledge Statement, Knowledge Category, Examples, Notes and
Mastery-related concepts.

The current Python LearningObject implementation contains:

* anchor_id
* statement
* category_id
* id
* state
* version
* created_at
* updated_at

Decision:

The current implementation may represent only the subset of the Domain
Model that has been explicitly implemented and verified.

Missing documented concepts must not be added automatically.

Each missing concept requires an explicit architectural decision before
implementation.

No implementation should infer additional Domain attributes solely from
high-level documentation.

================================================================

8. LearningObject.statement vs KnowledgeStatement persistence
   ================================================================

Status: OPEN / DEFERRED

Finding:

The current LearningObject domain entity contains:

statement: str

The Persistence Model defines KnowledgeStatement as an independent
persistent structure.

This creates a structural discrepancy between the current Domain
implementation and the Persistence Model.

Decision:

The Persistence Layer must not silently replace the current LearningObject
statement contract with a KnowledgeStatement relationship.

Until the Domain Model is explicitly revised:

* LearningObject.statement remains authoritative for the current Domain
  implementation;
* KnowledgeStatement may exist as a separate persistence structure;
* no implicit LearningObject -> KnowledgeStatement domain relationship
  may be introduced.

Required architectural decision:

Clarify the intended future relationship between LearningObject.statement
and KnowledgeStatement.

================================================================

9. Mastery persistence boundary
   ================================================================

Status: RESOLVED FOR CORE REPOSITORY v0.1 / DEFERRED FOR FUTURE REPOSITORIES

Finding:

The Persistence Mapping Specification 0.1.0 explicitly excludes Mastery
State from Core Repository v0.1 persistence.

The broader ELR architecture recognizes Mastery State as an architectural
concept.

Decision:

Core Repository v0.1 persistence must not introduce Mastery persistence.

This is a persistence boundary decision, not a rejection of the Mastery
concept.

Future persistence of Mastery requires:

* an approved Mastery Domain contract;
* an explicit persistence boundary;
* an approved Data Model relationship;
* an explicit implementation decision.

Until those decisions are made, no Mastery persistence model or table
should be introduced.

================================================================

10. ORM isolation
    ================================================================

Status: RESOLVED

Finding:

SQLAlchemy persistence models must remain separate from Domain entities.

Decision:

Domain entities:

* must not inherit from SQLAlchemy declarative classes;
* must not import SQLAlchemy;
* must not depend on database sessions;
* must not contain ORM metadata.

Persistence models belong under:

app/persistence/

The current AnchorModel implementation follows this boundary.

================================================================

11. Domain identity vs persistence identity
    ================================================================

Status: RESOLVED

Finding:

ELR Domain entities use UUID-based identity.

Decision:

Persistence must preserve existing domain-generated UUIDs.

Persistence must not silently replace domain identity with a separate
database-generated identity.

Database surrogate identifiers may only be introduced when they do not
replace or alter the Domain identity contract.

================================================================

12. Timestamp preservation
    ================================================================

Status: RESOLVED

Finding:

Domain timestamps are timezone-aware UTC timestamps.

Decision:

Persistence must preserve:

* created_at
* updated_at
* historical creation timestamps where applicable

Database persistence must not silently convert domain timestamps into
local time.

================================================================

13. Version history preservation
    ================================================================

Status: RESOLVED

Finding:

Version represents immutable historical state.

Decision:

Persistence must preserve historical Version records independently of
current LearningObject state.

Ordinary LearningObject updates must not overwrite historical Version
records.

================================================================

14. Audit history preservation
    ================================================================

Status: RESOLVED / IMPLEMENTATION CONSTRAINT

Finding:

Audit records represent append-oriented historical information.

Decision:

Updating an entity must not silently overwrite or erase existing audit
records.

================================================================

15. Approved persistence relationships
    ================================================================

Status: OPEN / IMPLEMENTATION CONSTRAINT

Finding:

The Persistence Mapping Specification defines approved relationships
including:

* learning_objects.anchor_id -> anchors.id
* learning_objects.category_id -> knowledge_categories.id
* knowledge_categories.parent_id -> knowledge_categories.id

Decision:

These relationships may be implemented in persistence.

Additional relationships involving KnowledgeStatement, Version,
AuditRecord, or Mastery must not be invented without explicit support
from the approved Domain/Data Model.

================================================================

16. Documentation authority and status
    ================================================================

Status: OPEN / ACTION REQUIRED

Finding:

The repository contains documents with different statuses, including
APPROVED and DRAFT specifications.

Some discrepancies arise because high-level Domain documentation,
specialized specifications, and Persistence documentation do not always
express the same level of detail.

Decision:

Before implementing a disputed concept:

1. identify the authoritative specification;
2. identify its status and version;
3. reconcile conflicting specifications;
4. update the documentation where required;
5. only then modify the Domain or Persistence implementation.

No implementation decision should be used to silently resolve an
architectural documentation conflict.

This rule remains an active architectural constraint.

================================================================

17. Mastery State implementation
    ================================================================

Status: DEFERRED

Finding:

Mastery State is now formally documented but is not yet represented in
the current Domain Python implementation.

Decision:

Do not implement MasteryState until the Domain implementation scope has
been explicitly approved.

In particular:

1. do not add MasteryState to LearningObject;
2. do not reinterpret LearningObject.state as Learning State or Mastery;
3. do not create Mastery persistence models;
4. do not create implicit LearningObject -> KnowledgeStatement domain
   relationships;
5. do not infer additional Domain attributes from documentation alone.

The current persistence implementation may continue for concepts whose
Domain and Persistence contracts are already sufficiently defined.

================================================================

18. Remaining architectural work
    ================================================================

The following work remains before implementing Mastery in the Domain
Layer:

1. determine the authoritative Domain representation of User;
2. determine the exact Domain construct representing Mastery State;
3. define identity semantics, if required;
4. define lifecycle/update semantics;
5. define the relationship between Mastery State and Mastery Evidence;
6. define the boundary between Mastery State and Learning State in the
   executable Domain Model;
7. determine whether and when Mastery becomes part of a future persistence
   model;
8. update this matrix after each approved architectural decision.

No implementation should precede these decisions.

================================================================

# Current Architectural Position

The current architecture establishes the following separation:

Learning Object
= persistent knowledge

LearningObject.state
= editorial/domain lifecycle

Learning State
= learner's current learning-process condition

Mastery Evidence
= observable evidence concerning mastery

Mastery Engine
= interpretation and processing of Mastery Evidence

Mastery State
= current mastery state of User with respect to Learning Object

Core Repository v0.1 Persistence
= knowledge and historical repository structures explicitly approved by
the Persistence Mapping Specification

Mastery State is therefore architecturally recognized, formally
documented, and intentionally implementation-deferred.
