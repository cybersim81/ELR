================================================================================
Scopo
================================================================================

La Versioning Model Specification definisce i principi con cui l'Educational
Learning Repository gestisce l'evoluzione delle proprie entità nel tempo.

Il Versioning Model garantisce che le modifiche alla conoscenza siano:


- tracciabili;

- reversibili quando necessario;

- coerenti con la storia del Repository;

- separate dagli eventi di apprendimento.


Il versioning riguarda l'evoluzione delle entità ELR.


Non rappresenta:


- progresso dell'utente;

- Mastery;

- cronologia conversazionale.


================================================================================
Responsabilità del documento
================================================================================

Questo documento definisce:


- concetto di versione;

- tipi di cambiamento;

- relazione tra identità e versione;

- gestione della storia evolutiva.


Questo documento NON definisce:


- criteri KEP CREATE / MERGE / UPDATE;

- approvazione delle modifiche;

- calcolo della Mastery;

- persistenza fisica.


================================================================================
Principio fondamentale
================================================================================

Una versione rappresenta una variazione controllata della stessa entità.


La versione risponde alla domanda:


"Come è cambiata questa conoscenza nel tempo?"


Non risponde alla domanda:


"Quanto l'utente conosce questa informazione?"


================================================================================
1. Versioning Boundary
================================================================================

Il Versioning Model opera sul livello di evoluzione del Repository.


Relazione:


Learning Process

        |

        v

Change Proposal

        |

        v

Versioned Entity

        |

        v

Repository History


================================================================================
2. Versioning Principles
================================================================================


--------------------------------------------------------------------------------
VERSION-001 — Identity Before Version
--------------------------------------------------------------------------------

L'identità di una entità precede le sue versioni.


Una modifica non deve creare una nuova identità quando rappresenta la stessa
conoscenza.


--------------------------------------------------------------------------------
VERSION-002 — History Preservation
--------------------------------------------------------------------------------

Le modifiche significative devono preservare la storia precedente.


--------------------------------------------------------------------------------
VERSION-003 — Knowledge Evolution Separation
--------------------------------------------------------------------------------

L'evoluzione della conoscenza è separata dall'evoluzione della Mastery.


--------------------------------------------------------------------------------
VERSION-004 — Explicit Change
--------------------------------------------------------------------------------

Ogni cambiamento deve essere riconducibile a un processo autorizzato.


================================================================================
3. Versioned Objects and Structures
================================================================================

Il versionamento del Repository distingue tra evoluzione del contenuto del
Learning Object ed evoluzione di strutture esterne al contenuto.

--------------------------------------------------------------------------------
3.1 Learning Object Content Versioning
--------------------------------------------------------------------------------

Il Learning Object è l'unità primaria di versionamento della conoscenza.

Una modifica al Knowledge Statement o alla rappresentazione interna del
Learning Object viene gestita attraverso una nuova versione del Learning
Object quando la conoscenza mantiene la stessa identità concettuale.

Una modifica all'associazione tra Learning Object e Anchor può essere
rappresentata attraverso una nuova versione del Learning Object quando la
modifica riguarda la rappresentazione della stessa conoscenza.

L'Anchor è associato al Learning Object e può essere condiviso da più Learning
Object indipendenti.

Una modifica dell'Anchor come entità condivisa non costituisce
automaticamente una nuova versione del Learning Object.

Knowledge Statement e Anchor non sono entità autonomamente versionate dal
Learning Object Versioning Model.


--------------------------------------------------------------------------------
3.2 Taxonomy Versioning
--------------------------------------------------------------------------------

La tassonomia può evolvere attraverso proprie versioni.

La versione della tassonomia è distinta dalla versione del Learning Object.

Una modifica a una Knowledge Category o ad altro elemento tassonomico non
costituisce automaticamente una nuova versione del Learning Object.

--------------------------------------------------------------------------------
3.3 Repository Schema Versioning
--------------------------------------------------------------------------------

Il Repository Schema può evolvere attraverso versioni dello schema.

Lo schema descrive la struttura dei dati persistenti e non costituisce una
versione della conoscenza contenuta nel Repository.

--------------------------------------------------------------------------------
3.4 API Contract Versioning
--------------------------------------------------------------------------------

I contratti API possono avere una propria versione secondo le specifiche di
sistema.

L'API Contract Versioning è distinto dal Learning Object Versioning,
Taxonomy Versioning e Repository Schema Versioning.

L'API non ridefinisce la semantica del Domain Model.


================================================================================
4. Learning Object Versioning
================================================================================

Il Learning Object rappresenta la principale entità soggetta a evoluzione.


Una nuova versione può derivare da:


- miglioramento della formulazione;

- correzione di errore;

- arricchimento informativo;

- aggiornamento della rappresentazione.


L'identità del Learning Object rimane invariata quando la conoscenza fondamentale
rimane la stessa.

Il versionamento del Learning Object riguarda l'evoluzione della conoscenza
rappresentata dall'entità.

Il Learning State non viene versionato insieme al Learning Object e non
appartiene a una specifica versione del Learning Object.

================================================================================
5. Version Change Types
================================================================================

Il modello ELR distingue:

--------------------------------------------------------------------------------
Minor Change
--------------------------------------------------------------------------------

Modifica della rappresentazione senza variazione della conoscenza
fondamentale.

Esempi:

- miglioramento linguistico del Knowledge Statement;
- chiarimento di un esempio;
- modifica della formulazione dell'Anchor all'interno del Learning Object.

Quando tali modifiche riguardano il contenuto di un Learning Object, sono
rappresentate come nuova versione dello stesso Learning Object.

--------------------------------------------------------------------------------
Major Change
--------------------------------------------------------------------------------

Modifica significativa della conoscenza rappresentata dal Learning Object.

Esempi:

- ridefinizione della conoscenza fondamentale;
- modifica sostanziale della relazione tra Anchor e Knowledge Statement;
- fusione o ristrutturazione di conoscenze precedenti quando il processo di
  revisione stabilisce la continuità della stessa identità.

Il cambiamento dell'Anchor non costituisce di per sé una versione autonoma
dell'Anchor.

--------------------------------------------------------------------------------
Structural Change
--------------------------------------------------------------------------------

Modifica del modello dati, dello schema del Repository o di altre strutture
tecniche soggette a versionamento.

Le modifiche strutturali sono versionate separatamente dal contenuto dei
Learning Object.


================================================================================
6. Relationship with CREATE / MERGE / UPDATE
================================================================================

Le operazioni KEP:


CREATE;

MERGE;

UPDATE;


non corrispondono automaticamente a una versione.


Relazione:


CREATE

        |

        v

Nuova identità


MERGE

        |

        v

Nuova versione possibile della stessa identità


UPDATE

        |

        v

Nuova versione della stessa identità


La decisione finale appartiene ai processi di revisione.


================================================================================
7. Version History
================================================================================

Ogni oggetto o struttura soggetto a versionamento deve mantenere informazioni
sulla propria storia secondo il relativo modello di versionamento.

Per il Learning Object la storia può includere:

* identificativo stabile del Learning Object;
* numero versione;
* data modifica;
* motivo modifica;
* origine della modifica;
* riferimento alla Change Proposal.

La storia di una versione del Learning Object include l'evoluzione del suo
contenuto e delle sue relazioni persistenti, compresi eventuali cambiamenti
al Knowledge Statement o all'associazione con un Anchor.

La modifica dell'Anchor come entità condivisa mantiene una storia distinta
quando tale Anchor è soggetto a un proprio modello di evoluzione.

Taxonomy Versioning, Repository Schema Versioning e API Contract Versioning
mantengono storie separate secondo i rispettivi modelli e contratti.

Le storie di questi sistemi non devono essere confuse con la storia delle
versioni del Learning Object.


================================================================================
8. Version Immutability
================================================================================

Una versione approvata non deve essere modificata direttamente.


Una correzione richiede:


Versione precedente

        |

        v

Nuova versione


La storia precedente rimane disponibile.


================================================================================
9. Versioning and Learning State
================================================================================

Il Learning State non segue direttamente le versioni della conoscenza.


La Mastery appartiene all'utente.


Se un Learning Object evolve:


- la storia della conoscenza viene preservata;

- il sistema valuta l'impatto sulla Mastery secondo regole dedicate.


Il Versioning Model non aggiorna la Mastery.


================================================================================
10. Versioning and Evidence
================================================================================

Le Evidence possono riferirsi a una specifica versione di un'entità
versionata.

La Change Evidence può inoltre motivare la creazione di una nuova versione.

La Evidence e la conoscenza versionata rimangono entità distinte.


Esempio:


Change Evidence:


Motiva la creazione della versione 2.0 di un Learning Object.


La Evidence non diventa parte della conoscenza versionata.


================================================================================
11. Version Compatibility
================================================================================

Le versioni devono mantenere compatibilità quando possibile.


Una modifica incompatibile deve essere esplicitamente identificata.


Esempi:


Compatibile:


Correzione di una frase esplicativa.


Non necessariamente compatibile:


Cambio completo della conoscenza rappresentata.


================================================================================
12. Version Retirement
================================================================================

Una versione può essere ritirata quando:


- è stata sostituita;

- contiene informazioni errate;

- non rappresenta più il modello corrente.


Il ritiro non elimina automaticamente la storia.


================================================================================
13. Anti-Patterns
================================================================================


Non validi:


--------------------------------------------------------------------------------
Silent Mutation
--------------------------------------------------------------------------------

Modificare conoscenza senza creare nuova versione.


--------------------------------------------------------------------------------
Identity Fragmentation
--------------------------------------------------------------------------------

Creare nuove identità per semplici variazioni della stessa conoscenza.


--------------------------------------------------------------------------------
History Loss
--------------------------------------------------------------------------------

Eliminare versioni precedenti senza processo autorizzato.


--------------------------------------------------------------------------------
Mastery Coupling
--------------------------------------------------------------------------------

Usare il versioning come misura della conoscenza dell'utente.


================================================================================
14. Relationship with Other Specifications
================================================================================

Learning Object Specification:

definisce il Learning Object come unità di conoscenza e ne definisce
l'identità e il contenuto soggetto a evoluzione.


Domain Model Specification:

definisce i confini dell'aggregate Learning Object e stabilisce che il
Knowledge Statement è membro del Learning Object, mentre l'Anchor è associato
al Learning Object e può essere condiviso da più Learning Object.

Il Versioning Model non ridefinisce tali confini e non attribuisce all'Anchor
un ciclo di vita o un versionamento derivato dal Learning Object.


KEP Specification:

produce proposte di cambiamento.


Learning Review:

approva evoluzioni della conoscenza.


Persistence Model:

definisce come la storia e le rappresentazioni persistenti vengono conservate.


Taxonomy:

definisce la tassonomia e la propria evoluzione indipendentemente dal
versionamento del Learning Object.


Lifecycle Specification:

definisce gli stati di vita delle entità.


API Specification:

definisce i contratti API.

Il versionamento dei contratti API è distinto dal versionamento del contenuto
dei Learning Object.


================================================================================
Principi conclusivi
================================================================================


## VERSION-001 — Knowledge has identity

La conoscenza mantiene continuità durante la propria evoluzione.


## VERSION-002 — Changes are historical events

Ogni cambiamento significativo lascia una traccia.


## VERSION-003 — Version is not mastery

La versione descrive la conoscenza, non l'apprendimento.


## VERSION-004 — Evolution requires control

L'evoluzione del Repository deve essere governata.


================================================================================
Principio conclusivo
================================================================================

La Versioning Model Specification garantisce che il Repository possa
evolvere senza perdere:


- identità;

- storia;

- coerenza;


L'ELR conserva la conoscenza corrente.

Il Versioning Model conserva il percorso attraverso cui quella conoscenza è
evoluta.
