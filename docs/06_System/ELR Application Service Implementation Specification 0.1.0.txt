================================================================================
Scopo
=====

La ELR Application Service Implementation Specification definisce il livello
applicativo dell'English Learning Repository.

L'Application Layer coordina:

* API requests;
* casi d'uso;
* regole dominio;
* persistenza;
* audit.

L'Application Layer NON contiene:

* logica cognitiva;
* schema database;
* dettagli HTTP.

================================================================================
Application Principles
======================

APPLICATION-001 — Use Case Ownership

Ogni operazione applicativa rappresenta un caso d'uso esplicito.

APPLICATION-002 — Domain Authority

Le regole di dominio rimangono nel Domain Layer.

APPLICATION-003 — Transaction Control

Le operazioni applicative definiscono il confine transazionale.

APPLICATION-004 — Process Coordination

L'Application Layer coordina componenti senza sostituirne la responsabilità.

Application Services
====================

================================================================================
Learning Object Service
=======================

Responsabilità:

Gestire i casi d'uso applicativi relativi ai Learning Object e coordinare
l'accesso alla conoscenza persistente secondo i contratti Domain, Lifecycle,
Review e Versioning.

Metodi:

create_candidate()

Crea un nuovo Learning Object con lifecycle_status Candidate.

submit_for_review()

Avvia il processo di revisione della proposta associata al Learning Object.

approve_change_proposal()

Coordina l'approvazione autorizzata di una Change Proposal.

L'Application Service non decide autonomamente l'approvazione.

La decisione di Review e la validazione delle transizioni rimangono affidate
ai componenti proprietari del dominio e del processo di Learning Review.

reject_change_proposal()

Coordina il rifiuto autorizzato di una Change Proposal.

L'Application Service non decide autonomamente il rifiuto.

get_learning_object()

Recupera conoscenza persistente.

get_history()

Recupera la storia evolutiva e le versioni secondo il Versioning Model.

================================================================================
Category Service
================

Responsabilità:

Gestire consultazione della tassonomia.

Metodi:

get_categories()

get_category_tree()

================================================================================
Version Service
===============

Responsabilità:

Gestire accesso alla storia evolutiva.

Metodi:

create_version()

Coordina la richiesta di creazione di una nuova versione
secondo le regole definite dal Versioning Model e dal Domain Layer.

L'Application Layer non decide autonomamente la validità
della creazione della versione.

get_versions()

================================================================================
Audit Service
=============

Responsabilità: 
Registrare e recuperare Audit Record relativi alle operazioni significative dell'Application Layer. 

L'Audit Service non produce, decide o sostituisce gli eventi di dominio definiti dall'Event Model. 

Metodi: 

record_event() 

Registra un Audit Record relativo all'operazione applicativa. 

get_events() 

Recupera gli Audit Record secondo le regole di accesso previste dal Security and Access Model.

Approve Change Proposal
=======================

Request

↓

Authorization Check

↓

Load Change Proposal

↓

Validate Review Decision

↓

Apply Authorized Domain Transition

↓

Apply Approved Change

↓

Create New Version when required by the Versioning Model

↓

Persist Result

↓

Audit Event

La decisione di approvazione appartiene al processo di Learning Review.

L'Application Service coordina il caso d'uso, verifica l'autorizzazione,
invoca le transizioni di dominio appropriate e coordina persistenza e audit.

L'Application Service non decide autonomamente:

* se una Change Proposal è approvabile;
* quale transizione di dominio sia semanticamente valida;
* quale versione debba essere creata.

Tali responsabilità appartengono rispettivamente ai componenti proprietari
di Review, Domain/Lifecycle e Versioning.

================================================================================
Transaction Rules
=================

Ogni use case applicativo di modifica deve essere atomico.

Esempio:

Approve Change Proposal:

BEGIN TRANSACTION

* validate authorization;
* load Change Proposal;
* validate Review decision;
* apply authorized domain transition;
* apply approved change;
* create new version when required by the Versioning Model;
* persistence;
* audit.

COMMIT

In caso di errore:

ROLLBACK

L'Application Service coordina il confine transazionale ma non sostituisce le
responsabilità di Domain, Review o Versioning.

================================================================================
Dependency Rules
================

Application Layer può dipendere da:

* Domain Layer;
* Repository Interface;
* Services tecnici.

Application Layer NON può dipendere da:

* FastAPI;
* SQLAlchemy;
* PostgreSQL;
* framework infrastrutturali.

================================================================================
Prossimo Incremento
===================

Il prossimo incremento implementativo sarà determinato in base alle
dipendenze e alle priorità definite dall'architettura corrente ELR.

Eventuali nuove specifiche implementative dovranno mantenere coerenza con:

* ELR Domain Model;
* ELR Lifecycle Model;
* ELR Versioning Model;
* ELR Security and Access Model;
* ELR Persistence Model;
* ELR API Specification;
* ELR Event Model.

L'Application Service Implementation Specification non introduce nuove
decisioni semantiche nei modelli proprietari, ma ne coordina l'applicazione
a livello di use case.

================================================================================
Principio conclusivo
====================

L'Application Layer è il coordinatore operativo dell'ELR.

Non crea conoscenza e non conserva conoscenza:
orchestra il percorso controllato attraverso cui la conoscenza evolve.
