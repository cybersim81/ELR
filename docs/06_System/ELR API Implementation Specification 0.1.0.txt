================================================================================
Scopo
=====

La ELR API Implementation Specification definisce il primo livello API
implementativo dell'English Learning Repository.

Le API espongono capacità applicative senza esporre direttamente:

* database;
* entità interne;
* dettagli infrastrutturali.

================================================================================
API Principles
==============

API-IMPLEMENTATION-001 — Domain Protection

Le API non modificano direttamente il dominio.

API-IMPLEMENTATION-002 — Explicit Operations

Ogni operazione rappresenta un caso d'uso esplicito.

API-IMPLEMENTATION-003 — Lifecycle Compliance

Ogni modifica deve rispettare il Lifecycle Model.

Le API non implementano direttamente le transizioni di Lifecycle.

L'API invoca il caso d'uso applicativo corrispondente;
la validazione e l'applicazione della transizione sono responsabilità
del livello applicativo e del dominio secondo il Lifecycle Model.

API-IMPLEMENTATION-004 — Traceable Actions

Ogni modifica deve produrre audit.

Learning Object API
===================

================================================================================
POST /api/v1/learning-objects
=============================

Scopo:

Creare un nuovo Learning Object Candidate.

Request:

{
"anchor_id": "uuid",
"statement": "text",
"category_id": "uuid"
}

Response:

{
"id": "uuid",
"lifecycle_status": "Candidate"
}

Regole:

* crea solo Candidate;
* non rende la conoscenza attiva;
* genera AuditRecord.

================================================================================
GET /api/v1/learning-objects/{id}
=================================

Scopo:

Recuperare un Learning Object.

Response:

{
"id": "uuid",
"lifecycle_status": "Active",
"version": 1
}

================================================================================
Write Operations
================

Le operazioni di modifica seguono il modello Change Proposal.

Le principali write operations applicative sono:

POST /change-proposals

Crea una Change Proposal per una modifica proposta alla conoscenza.

POST /change-proposals/{id}/status

Richiede l'aggiornamento dello stato della Change Proposal secondo il processo
di Review e le autorizzazioni applicabili.

Le operazioni di approvazione e rifiuto non modificano direttamente il
Learning Object tramite un endpoint lifecycle generico.

Il passaggio:

API
↓
Application Service
↓
Review / Domain
↓
Lifecycle / Versioning
↓
Repository

deve essere rispettato.

L'API Implementation non contiene logica di dominio e non decide
autonomamente se una Change Proposal possa essere approvata o rifiutata.

================================================================================
Change Proposal Boundary
========================

La Change Proposal costituisce l'unità operativa della write path.

L'API riceve una richiesta di modifica e la inoltra all'Application Layer.

L'Application Layer coordina il caso d'uso.

La Learning Review determina l'esito della Review secondo le regole
autorizzative e di dominio.

Il Domain Layer applica le transizioni consentite.

Il Versioning Model determina la rappresentazione evolutiva risultante.

Il Repository persiste il risultato.

L'API Layer non bypassa questi confini.

================================================================================
Transaction Boundary
====================

Ogni chiamata che modifica conoscenza deve:

1. validare richiesta;

2. eseguire caso d'uso;

3. applicare regole dominio;

4. aggiornare persistenza;

5. generare audit.
