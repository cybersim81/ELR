================================================================================
Scopo
=====

La ELR Implementation Architecture Specification definisce la prima
architettura implementativa dell'English Learning Repository.

Il documento traduce i principi architetturali ELR in una struttura software
concreta mantenendo separazione tra:

* dominio;
* processi;
* persistenza;
* interazione;
* infrastruttura.

Questo documento NON sostituisce la ELR Architecture Specification.

La Architecture Specification definisce cosa deve essere ELR.

Questo documento definisce come il primo sistema software implementa tali
principi.

================================================================================
Implementation Principles
=========================

IMPLEMENTATION-001 — Domain First

Il modello software deve essere guidato dal modello dominio.

IMPLEMENTATION-002 — Separation of Layers

Ogni responsabilità deve appartenere al proprio livello.

IMPLEMENTATION-003 — Replaceable Infrastructure

Le dipendenze infrastrutturali devono poter essere sostituite senza modificare
il dominio.

IMPLEMENTATION-004 — Traceable Evolution

Ogni modifica significativa deve mantenere tracciabilità.

================================================================================
Domain Layer
============

Il Domain Layer contiene i principali concetti e oggetti ELR utilizzati
dall'implementazione:

* Anchor;
* Learning Object;
* Knowledge Category;
* Version;
* Learning State.

Knowledge Statement non è modellato come entità autonoma.

Il contenuto del Knowledge Statement è rappresentato come valore del
Learning Object secondo il modello di dominio corrente.

Mastery State appartiene al Domain Model ELR, ma la sua persistenza è fuori
dal Core Repository v0.1 e non costituisce quindi una persistence responsibility
di questa implementazione.

Il Domain Layer non dipende da:

* database;
* API;
* framework;
* sistemi esterni.

================================================================================
Application Layer
=================

L'Application Layer coordina i casi d'uso:

* creazione Candidate;
* proposta modifica;
* approvazione;
* aggiornamento versione;
* recupero conoscenza.

L'Application Layer applica le regole di processo.

================================================================================
API Layer
=========

L'API Layer espone verso sistemi esterni le capacità definite dal contratto
ELR API.

Il contratto API comprende, tra le altre:

* accesso e ricerca dei Learning Object;
* accesso alla conoscenza tramite Anchor e categorie;
* creazione e gestione delle Change Proposal;
* accesso ai dati di Learning State;
* accesso ai dati relativi alla Mastery;
* gestione delle Evidence secondo i relativi contratti;
* autenticazione, autorizzazione e separazione dei ruoli.

Il Core Repository v0.1 può implementare soltanto il sottoinsieme delle
capacità API incluso nel proprio scope.

Le API non modificano direttamente il dominio.

Ogni modifica passa attraverso Application Layer.

================================================================================
Persistence Layer
=================

Il Persistence Layer gestisce la persistenza dello stato applicativo e dei dati necessari al funzionamento del Repository.

La persistenza della conoscenza comprende:

Learning Object;
Anchor;
Knowledge Category;
Version;
Audit Record.

I Transactional Event Record sono gestiti dal Persistence Layer come infrastructure persistence necessaria al transactional event flow, ma non costituiscono conoscenza persistente del Repository e non ampliano il persistence boundary definito dalla Persistence Model Specification.

Gli eventi operativi non fanno parte della conoscenza conservata dal Repository. Il Transactional Event Record rappresenta esclusivamente il fatto tecnico necessario a garantire la registrazione transazionale e la successiva pubblicazione dell'evento.

Il Persistence Layer non contiene:

logica cognitiva;
logica di estrazione della conoscenza;
calcolo della Mastery;
generazione degli esercizi;
decisioni di Review;
logica di pubblicazione degli eventi.

================================================================================
Event Layer
===========

L'Event Layer implementa il modello di eventi definito dalla ELR Event Model
Specification.

Le categorie principali sono:

* Knowledge Process Events;
* Review Events;
* Mastery Events;
* Learning Activity Events;
* Learning Object Lifecycle Events.

Learning Object Lifecycle Events:

* LearningObjectCreated;
* LearningObjectSubmitted;
* LearningObjectUpdated;
* LearningObjectRetired.

Review Events:

* ChangeProposalApproved;
* ChangeProposalRejected;
* ChangeProposalModified.

Le decisioni della Learning Review sono rappresentate come Review Events
e non costituiscono direttamente eventi del lifecycle del Learning Object.

Il Core Repository v0.1 può implementare un sottoinsieme degli eventi
definiti dal modello corrente in funzione dello scope implementativo.

Gli eventi rappresentano fatti avvenuti e non sostituiscono API, processi,
Evidence o conoscenza persistente.

Gli eventi vengono persistiti tramite il Persistence Layer e possono essere
pubblicati verso consumer esterni.

================================================================================
Specification Ownership and Consistency
========================================

L'Implementation Architecture Specification traduce i contratti architetturali
e di dominio in una struttura software concreta.

Non ridefinisce la semantica proprietaria dei concetti.

Le responsabilità semantiche rimangono nei rispettivi documenti:

* Domain Model e relative specifiche per i concetti di dominio;
* Persistence Model e Persistence Mapping per la persistenza;
* API Specification per il contratto API;
* Event Model Specification per il modello degli eventi.

Questa specifica deve mantenere coerenza con tali documenti senza duplicarne
o modificarne le decisioni.

Quando lo scope implementativo Core Repository v0.1 è più ristretto rispetto
al modello ELR complessivo, la differenza deve essere esplicitamente trattata
come scope boundary e non come modifica del modello architetturale.

================================================================================
Architecture Decision
=====================

ADR-001 — Technology Stack

Decisione:

La prima implementazione ELR utilizza Python, FastAPI e PostgreSQL.

Motivazione:

Lo stack supporta:

* sviluppo rapido;
* separazione dominio/infrastruttura;
* futura integrazione KEP;
* gestione API;
* persistenza strutturata.

Conseguenze:

Positive:

* elevata velocità di prototipazione;
* ecosistema adatto a sistemi AI.

Negative:

* richiede disciplina architetturale per mantenere separazione dei livelli.

================================================================================
Scope v0.1
==========

Incluso:

* dominio core;
* persistenza base;
* lifecycle minimo;
* API fondamentali;
* audit iniziale.

Escluso:

* interfaccia utente;
* KEP completa;
* Mastery Engine completo;
* Exercise System;
* sistemi distribuiti.

================================================================================
Principio conclusivo
====================

L'Implementation Architecture Specification definisce il primo ponte tra il
modello ELR e una realizzazione software concreta.

L'implementazione deve rispettare il modello cognitivo e architetturale ELR,
senza modificarne i principi fondamentali.
