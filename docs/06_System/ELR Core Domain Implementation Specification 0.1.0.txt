Scopo
=====

La ELR Core Domain Implementation Specification definisce la prima
rappresentazione software del dominio cognitivo ELR.

Il documento descrive:

* entità dominio;
* relazioni;
* invarianti;
* responsabilità;
* regole fondamentali.

Il dominio rappresenta la conoscenza ELR senza dipendere da:

* database;
* API;
* framework;
* sistemi esterni.

================================================================================
Domain Principles
=================

DOMAIN-IMPLEMENTATION-001 — Domain Independence

Le entità dominio non devono conoscere dettagli infrastrutturali.

DOMAIN-IMPLEMENTATION-002 — Explicit State

Ogni entità con ciclo di vita deve rappresentare esplicitamente il proprio
stato.

DOMAIN-IMPLEMENTATION-003 — Immutable History

La storia delle modifiche non viene sovrascritta.

DOMAIN-IMPLEMENTATION-004 — Controlled Mutation

Le modifiche alle entità avvengono attraverso operazioni autorizzate.

Entity: Anchor
==============

Responsabilità:

Rappresentare il riferimento linguistico fondamentale.

Attributi concettuali:

id:

Identificativo univoco.

content:

Rappresentazione dell'anchor.

type:

Tipo di anchor.

metadata:

Informazioni descrittive.

Vincoli:

* un Anchor deve avere un identificativo;
* un Anchor non viene modificato distruggendo la storia;
* un Anchor può essere collegato a più Learning Object.

================================================================================
Entity: LearningObject
======================

Responsabilità:

Rappresentare una unità persistente di conoscenza ELR.

Attributi concettuali:

id:

Identificativo univoco.

anchor_id:

Riferimento all'Anchor.

statement:

Knowledge Statement associato.

category:

Categoria cognitiva.

lifecycle_status:

Stato del ciclo di vita del Learning Object.

current_version:

Versione corrente.

created_at:

Data creazione.

updated_at:

Ultimo aggiornamento.

================================================================================
LearningObject Lifecycle Status
==============================

Gli stati consentiti sono:

Candidate

Proposed

Reviewed

Active

Retired

Rejected

Sono vietate transizioni non definite dal Lifecycle Model.

Updated non costituisce uno stato persistente del Learning Object.

L'evoluzione di un Learning Object già Active viene rappresentata attraverso
il Versioning Model mediante la creazione di una nuova Versione.

Il lifecycle state rappresenta lo stato corrente del Learning Object.

La storia evolutiva non viene rappresentata introducendo uno stato Updated,
ma attraverso le Version records immutabili associate al Learning Object.

================================================================================
Entity: KnowledgeStatement
==========================

Responsabilità:

Rappresentare il contenuto cognitivo del Learning Object.

Nel Domain Model corrente il Knowledge Statement non costituisce una Entity
autonoma.

È un valore interno al Learning Object.

Rappresentazione:

LearningObject
    └── statement: str

Vincoli:

* il Knowledge Statement non può essere vuoto;
* il Knowledge Statement appartiene al Learning Object che lo contiene;
* non possiede una identity autonoma;
* non possiede un lifecycle autonomo;
* non possiede un repository autonomo;
* non contiene dati personali;
* non contiene informazioni temporanee di processo.

La rappresentazione implementativa corrente non introduce quindi:

* KnowledgeStatement UUID;
* KnowledgeStatement repository;
* KnowledgeStatement lifecycle;
* relazione autonoma LearningObject → KnowledgeStatement.

Una futura introduzione di un Value Object esplicito richiede una revisione
del Domain Model e della Persistence Mapping Specification.

================================================================================
Entity: KnowledgeCategory
=========================

Responsabilità:

Classificare la conoscenza.

La KnowledgeCategory costituisce un'entità del dominio con propria identity
e propria gerarchia tassonomica.

Attributi:

id:

Identificativo univoco della categoria.

name:

Nome della categoria.

parent_id:

Categoria superiore opzionale.

Vincoli:

* la tassonomia deve mantenere coerenza gerarchica;
* name non può essere vuoto;
* parent_id, quando presente, deve riferirsi a una categoria esistente.

La KnowledgeCategory non introduce un lifecycle autonomo del Learning Object.

Il Learning Object mantiene il riferimento alla categoria attraverso
category_id.

Entity: Version
===============

Responsabilità:

Conservare la storia evolutiva.

Attributi:

id:

Identificativo versione.

learning_object_id:

Learning Object a cui appartiene la versione.

number:

Numero versione.

status:

Stato versione.

created_at:

Data creazione.

content_snapshot:

Rappresentazione storica.

Vincoli:

* una versione attiva è unica per Learning Object;
* una versione precedente non viene eliminata;
* una versione è immutabile dopo la sua stabilizzazione.

================================================================================
Domain Operations
=================

Le operazioni dominio iniziali:

create_learning_object()

Crea un nuovo Learning Object con lifecycle_status Candidate.

submit_learning_object()

Avvia il processo di revisione della modifica proposta.

approve_change_proposal()

Applica una decisione di Review autorizzata a una Change Proposal secondo
le regole del Domain e del Lifecycle Model.

Il dominio non decide autonomamente l'esito della Review.

L'Application Service coordina il caso d'uso.

La Learning Review determina l'esito della proposta secondo le regole
autorizzative applicabili.

reject_change_proposal()

Applica al dominio l'esito di rifiuto di una Change Proposal.

create_new_version()

Genera una nuova versione preservando la precedente secondo il Versioning
Model.

La creazione di una nuova Versione non introduce uno stato Updated nel
Learning Object.

================================================================================
Domain Rules
============

RULE-001

Un Learning Object non può diventare Active senza Review.

RULE-002

Una versione storica non può essere modificata.

RULE-003

Il dominio non accede direttamente alla persistenza.

RULE-004

Ogni modifica significativa genera AuditRecord.

RULE-005

Le transizioni di stato devono rispettare il Lifecycle Model.

================================================================================
Implementation Boundary
=======================

Il dominio espone:

* entità;
* regole;
* comportamenti.

Il dominio NON espone:

* query database;
* endpoint HTTP;
* serializzazione API;
* configurazioni infrastrutturali.

================================================================================
Prossimo Incremento
===================

Il prossimo incremento implementativo sarà determinato in base alle
dipendenze e alle priorità definite dall'architettura corrente ELR.

Il Core Domain Implementation Specification deve rimanere coerente con:

* ELR Domain Model Specification;
* Anchor Specification;
* Learning Object Specification;
* Lifecycle Model;
* Versioning Model;
* Validation Rules;
* Persistence Mapping.

Il Core Domain non introduce responsabilità di:

* persistenza;
* API;
* autorizzazione applicativa;
* orchestrazione dei casi d'uso;
* infrastruttura.

Eventuali modifiche future alle responsabilità o alle aggregate boundaries
devono essere introdotte attraverso una revisione esplicita dei relativi
documenti proprietari.

================================================================================
Principio conclusivo
====================

Il Core Domain rappresenta il nucleo cognitivo dell'ELR.

La tecnologia implementativa deve adattarsi al dominio e non modificare il
significato della conoscenza rappresentata.
