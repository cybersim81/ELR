================================================================================
Scopo
================================================================================

La ELR Lifecycle Specification definisce il ciclo di vita delle entità e dei
processi principali dell'English Learning Repository.


Il documento descrive:


- stati possibili delle entità;

- transizioni consentite;

- eventi che determinano cambiamenti;

- responsabilità dei componenti coinvolti.


Il Lifecycle Model garantisce che l'evoluzione dell'ELR avvenga attraverso
processi controllati.


================================================================================
Responsabilità del documento
================================================================================

Questo documento definisce:


- ciclo di vita dei Learning Object;

- ciclo di vita delle Change Proposal;

- ciclo di vita delle Evidence;

- ciclo di vita delle versioni.


Questo documento NON definisce:


- contenuto linguistico dei Learning Object;

- algoritmi KEP;

- algoritmo Mastery;

- struttura fisica del database.


================================================================================
Principio fondamentale
================================================================================

Ogni entità ELR attraversa stati definiti.


Una transizione di stato deve essere:


- esplicita;

- motivata;

- tracciabile.


Il ciclo di vita risponde alla domanda:


"Qual è lo stato corrente di questa entità e come può evolvere?"


================================================================================
1. Lifecycle Boundary
================================================================================

Il Lifecycle Model opera tra processo applicativo, dominio e persistenza.

Relazione:

Event / Command
        |
        v
Application Service
        |
        v
Process Decision
        |
        v
Entity State Transition
        |
        v
Repository Update

Un Event o un Command non determina autonomamente una transizione di stato.

La transizione deve essere eseguita dal processo competente secondo le regole
del Lifecycle Model.


================================================================================
2. Lifecycle Principles
================================================================================


--------------------------------------------------------------------------------
LIFECYCLE-001 — State Before Action
--------------------------------------------------------------------------------

Ogni azione deve rispettare lo stato corrente dell'entità.


--------------------------------------------------------------------------------
LIFECYCLE-002 — Controlled Transition
--------------------------------------------------------------------------------

Una transizione deve essere autorizzata dal processo competente.


--------------------------------------------------------------------------------
LIFECYCLE-003 — Historical Continuity
--------------------------------------------------------------------------------

I cambiamenti devono mantenere continuità storica.


--------------------------------------------------------------------------------
LIFECYCLE-004 — Process Ownership
--------------------------------------------------------------------------------

Ogni transizione appartiene a un componente responsabile.


================================================================================
3. Learning Object Lifecycle
================================================================================

Il Learning Object rappresenta la conoscenza persistente dell'ELR.

Il suo lifecycle descrive lo stato del Learning Object e non l'esito della
Learning Review di una Change Proposal.

Ciclo principale:

Candidate
|
v
Proposed
|
v
Active
|
v
Retired

Una Change Proposal può essere associata a un Learning Object Proposed o
Active e segue il proprio lifecycle indipendente:

Created
|
v
Under Review
|
+-------------+
|             |
v             v
Approved       Rejected

L'approvazione di una Change Proposal può determinare una nuova Version del
Learning Object.

Il rifiuto di una Change Proposal non costituisce una transizione del
Learning Object verso uno stato di rifiuto.

Una modifica approvata di un Learning Object Active non introduce uno stato
`Updated`.

La modifica viene rappresentata attraverso una nuova Version, mentre il
Learning Object mantiene il proprio lifecycle status coerente con il
Lifecycle Model.

La versione precedente rimane nella storia.

================================================================================
3.3 Review Decision and Learning Object State
=============================================

La decisione di Learning Review appartiene alla Change Proposal e non
costituisce uno stato del Learning Object.

Una Change Proposal può essere:

* Approved;
* Rejected.

`Approved` indica che la modifica proposta può essere applicata secondo le
regole del dominio e del processo applicativo.

`Rejected` indica che la modifica proposta non può essere applicata.

Il Learning Object non assume uno stato `Reviewed`, `Approved` o `Rejected`
come conseguenza della decisione di Review.

La decisione di Review è rappresentata dagli eventi di dominio previsti
dall'Event Model:

* ChangeProposalApproved;
* ChangeProposalRejected;
* ChangeProposalModified.



================================================================================
3.1 Candidate
================================================================================

Uno stato Candidate rappresenta una conoscenza candidata che non è ancora
conoscenza ufficiale del Repository.

Il Candidate può essere rappresentato e persistito nel Repository, ma non è
disponibile come conoscenza ufficiale per recupero, esercizi o apprendimento.

Origine possibile:

* KEP;
* importazione validata;
* creazione controllata.


================================================================================
3.2 Proposed
================================================================================

Una conoscenza Proposed è associata a una proposta di modifica.


Richiede:


- Change Proposal;

- Evidence;

- valutazione.


================================================================================
3.3 Reviewed
================================================================================

Una conoscenza Reviewed ha superato la valutazione del processo di Learning
Review.


Può essere:


- approvata;

- rifiutata.


================================================================================
3.4 Active
================================================================================

Un Learning Object Active rappresenta conoscenza ufficiale del Repository.


È disponibile per:


- recupero;

- esercizi;

- apprendimento.


================================================================================
3.5 Retired
================================================================================

Un Learning Object Retired non è più utilizzato come conoscenza attiva.


La storia rimane conservata.

5. Evidence Lifecycle
================================================================================

Una Evidence segue:


Generated

        |

        v

Available

        |

        v

Consumed

        |

        v

Archived


================================================================================
5.1 Generated
================================================================================

L'Evidence viene prodotta da un processo.


Esempi:


- KEP;

- Mastery Engine.


================================================================================
5.2 Available
================================================================================

L'Evidence è disponibile al componente responsabile.


================================================================================
5.3 Consumed
================================================================================

L'Evidence è stata utilizzata per una decisione o valutazione.


================================================================================
5.4 Archived
================================================================================

L'Evidence non è più operativa ma può essere mantenuta per tracciabilità.

        |

        v

Superseded

        |

================================================================================
6.1 Created
================================================================================

La versione viene generata da una modifica approvata.


================================================================================

================================================================================

================================================================================

================================================================================
7. Lifecycle Ownership
================================================================================


KEP:

produce Candidate e Change Proposal.

Learning Review:

decide l'approvazione o il rifiuto delle Change Proposal.

Application Service:

coordina il caso d'uso e invoca le transizioni di dominio autorizzate.

Lifecycle Model:

definisce e governa le transizioni consentite.

Repository / Persistence:

persiste lo stato risultante dalle transizioni.

Versioning Model:

conserva la storia evolutiva delle versioni.

Mastery Engine:

gestisce l'evoluzione dello stato di apprendimento.

================================================================================
8. Invalid Transitions
================================================================================

Non sono consentite:


--------------------------------------------------------------------------------
Direct Persistence
--------------------------------------------------------------------------------

Inserire un Candidate direttamente come Active.


--------------------------------------------------------------------------------
Silent Update
--------------------------------------------------------------------------------

Modificare un Learning Object senza transizione.


--------------------------------------------------------------------------------
Evidence Mutation
--------------------------------------------------------------------------------

Modificare una Evidence già prodotta.

Una Evidence prodotta è immutabile.

Eventuali nuove informazioni o risultati devono essere rappresentati attraverso
una nuova Evidence, senza modificare la Evidence storica.

--------------------------------------------------------------------------------
Mastery Override
--------------------------------------------------------------------------------

Modificare Learning State attraverso processi non autorizzati.

================================================================================
10. Lifecycle and Repository Integrity
================================================================================

Il Lifecycle impedisce:


- conoscenza non approvata;

- perdita della storia;

- modifiche non tracciate;

- separazione errata delle responsabilità.


================================================================================
11. Lifecycle Anti-Patterns
================================================================================


Non validi:


--------------------------------------------------------------------------------
Uncontrolled Creation
--------------------------------------------------------------------------------

Creare Learning Object senza processo.


--------------------------------------------------------------------------------
State Jumping
--------------------------------------------------------------------------------

Passare da Candidate ad Active senza Review.


--------------------------------------------------------------------------------
History Destruction
--------------------------------------------------------------------------------

Eliminare stati precedenti.


--------------------------------------------------------------------------------
Responsibility Mixing
--------------------------------------------------------------------------------

Un componente modifica stati appartenenti ad altri componenti.

================================================================================
Principi conclusivi
================================================================================


## LIFECYCLE-001 — Entities evolve through states

Le entità ELR cambiano attraverso transizioni definite.


## LIFECYCLE-002 — Transitions require ownership

Ogni cambiamento ha un responsabile.


## LIFECYCLE-003 — History is preserved

L'evoluzione non cancella il passato.


## LIFECYCLE-004 — Process and knowledge remain separate

Il ciclo di vita governa la conoscenza senza diventare conoscenza.


================================================================================
Principio conclusivo
================================================================================

La ELR Lifecycle Specification completa il modello di governance del Repository.


La KEP identifica conoscenza candidata.

La Learning Review controlla le modifiche.

L'ELR conserva conoscenza approvata.

Il Versioning Model conserva la storia.

Il Lifecycle Model definisce il percorso attraverso cui ogni entità evolve.
