# 04_End_to_End_Gap_Map.txt

## End-to-End Gap Map

### Purpose

This document defines the gap between the current implementation baseline and the intended persistent end-to-end ELR flow.

It is a continuity artifact and does not replace the authoritative specifications.

---

## IA-01 Closure Mapping

The following IA-01 findings are reflected in the current E2E baseline:

* IA-001 — KnowledgeStatement is an explicit immutable LearningObject aggregate member.
* IA-002 — KnowledgeStatement has no autonomous identity or lifecycle boundary.
* IA-003 — Version is explicitly owned by LearningObject through `learning_object_id`.
* IA-005 — Version state is no longer mutable state stored directly on LearningObject.
* IA-010 — Version history is LearningObject-centered.
* IA-017 — Version snapshots preserve structured KnowledgeStatement semantics.
* IA-018 — Application and repository Version history boundaries are aligned.
* IA-019 — Version snapshot semantics are covered by application tests.

All eight findings are:

`RESOLVED`

## E2E-08 — Persistent Reload

Status: NEXT

Objective:

Demonstrate that a LearningObject persisted through the production SQLAlchemy repositories can be reconstructed correctly from a newly created database session.

Required boundary:

`Database → New Session → Repository → Reconstructed Aggregate`

The test MUST:

1. create and persist a LearningObject;
2. commit the transaction;
3. close the original session;
4. create a new independent session;
5. reconstruct the LearningObject through the concrete repository;
6. verify identity and aggregate state;
7. verify persisted KnowledgeStatement data;
8. verify Anchor and KnowledgeCategory references.

E2E-08 remains open until the new-session reload behavior is demonstrated by an integration test.

---

## E2E-09 — Version History Recovery

Status: PENDING

Objective:

Demonstrate that immutable Version history survives session reload and can be recovered from persistent storage in the correct order.

Required behavior:

`Persist Versions → Close Session → New Session → Recover Version History`

The recovered history MUST preserve:

* LearningObject ownership;
* Version identity;
* Version numbers;
* snapshot contents;
* ascending Version order;
* immutability of historical snapshots.

E2E-09 starts after E2E-08 is complete.

---

## E2E-10 — Audit History Recovery

Status: PENDING

Objective:

Demonstrate that operational Audit history survives session reload and can be recovered from persistent storage in deterministic order.

Required behavior:

`Persist Audit Records → Close Session → New Session → Recover Audit History`

The recovered audit history MUST preserve:

* entity ownership;
* event type;
* actor;
* metadata;
* chronological ordering.

Audit history remains operational history and MUST remain distinct from immutable Version history.

E2E-10 starts after E2E-09 is complete.
