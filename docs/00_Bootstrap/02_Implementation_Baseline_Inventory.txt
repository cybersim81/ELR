# 02_Implementation_Baseline_Inventory.txt

## Implementation Baseline Inventory

### Purpose

This document records the implementation state discovered during the baseline inventory.

It distinguishes existing implementation from normative conformance.

It is not an implementation specification and does not authorize deviations from the normative baseline.

### Inventory Status

**IMPLEMENTATION BASELINE INVENTORY: COMPLETE**

### Domain Layer

#### LearningObject

Present under:

`app/domain/entities/learning_object.py`

Current implementation includes:

* stable `id`;
* `anchor_id`;
* explicit immutable `KnowledgeStatement` aggregate member;
* `category_id`;
* lifecycle `state`;
* examples;
* notes.

Mutable Version state is no longer stored directly on LearningObject.

Lifecycle transition behavior is implemented.

**Status: IMPLEMENTED / DOMAIN-ALIGNED**

#### KnowledgeStatement

Present under:

`app/domain/entities/knowledge_statement.py`

The object is immutable and represents the semantic value of a KnowledgeStatement.

It has no autonomous:

* identity;
* lifecycle;
* repository;
* versioning boundary.

It is owned by the LearningObject aggregate.

**Status: IMPLEMENTED / DOMAIN-ALIGNED**

#### Version

Present under:

`app/domain/entities/version.py`

The object is immutable and contains:

* `learning_object_id`;
* `number`;
* `snapshot`.

Version identity is explicitly scoped to LearningObject history.

**Status: IMPLEMENTED / DOMAIN-ALIGNED**

#### Anchor

Present under:

`app/domain/entities/anchor.py`

Anchor has its own identity and is represented independently from LearningObject.

**Status: IMPLEMENTED / PRELIMINARILY CONFORMANT**

#### AuditRecord

Present under:

`app/domain/entities/audit_record.py`

Audit records are immutable operational-history records.

**Status: IMPLEMENTED / PRELIMINARILY CONFORMANT**

### IA-01 Implementation Alignment Evidence

#### IA-001 — LearningObject Statement Representation

LearningObject uses an explicit immutable KnowledgeStatement aggregate member.

**Status: RESOLVED**

#### IA-002 — KnowledgeStatement Identity Semantics

KnowledgeStatement is immutable and has no autonomous identity, lifecycle, repository, or versioning boundary.

**Status: RESOLVED**

#### IA-003 — Generic Version Entity

Version uses `learning_object_id` rather than a generic `entity_id`.

**Status: RESOLVED**

#### IA-005 — LearningObject Version Number

LearningObject no longer stores mutable Version state.

**Status: RESOLVED**

#### IA-010 — Generic VersionRepository History

Version history is retrieved using `learning_object_id`.

**Status: RESOLVED**

#### IA-017 — Version Snapshot Representation

Version snapshots contain the structured KnowledgeStatement representation.

**Status: RESOLVED**

#### IA-018 — Application / Repository Version Boundary

Application and repository layers use the same LearningObject-centered Version boundary.

**Status: RESOLVED**

#### IA-019 — Version Snapshot Test Coverage

Tests verify Version creation, Version history, Version numbering, snapshot contents, and preservation of previous Versions.

**Status: RESOLVED**

Present.

**Status: IMPLEMENTED / DELETE SEMANTICS OPEN**

#### VersionRepository

`app/domain/repositories/version_repository.py`

Current contract uses:

`save(version)`

and:

`get_history(learning_object_id)`

The in-memory implementation follows the same LearningObject-centered boundary.

**Status: IMPLEMENTED / DOMAIN-ALIGNED**

#### AnchorRepository

Present as a separate repository.

**Status: IMPLEMENTED / CONFORMANT PRELIMINARILY**

#### KnowledgeStatementRepository

No autonomous repository was found.

This is consistent with KnowledgeStatement not being an autonomous aggregate.

**Status: NO AUTONOMOUS REPOSITORY**

### Application Layer

`app/application/services/learning_object_service.py` is present.

The service implements:

* LearningObject creation;
* lifecycle progression;
* Version creation;
* immutable Version history retrieval;
* Version snapshot creation;
* AuditRecord creation;
* knowledge update through new Version creation.

The application workflow is covered by tests.

**Status: IMPLEMENTED / IA-01 ALIGNED**

### Persistence Layer

The verified persistence tree contains:

`app/persistence/models/base.py`

and:

`app/persistence/models/anchor_model.py`

Anchor persistence is therefore materialized.

No verified persistence models were found for:

* LearningObject;
* KnowledgeStatement;
* Version;
* AuditRecord.

No verified concrete production repository implementations were found under the inspected persistence tree.

**Status: PARTIAL**

### Test Layer

Domain tests cover Anchor and LearningObject lifecycle behavior.

Application tests cover the LearningObject service workflow, including Version creation, Version history, and AuditRecord creation.

Persistence tests cover AnchorModel.

The current application tests use in-memory repositories.

No persistent database round-trip test was identified for LearningObject, Version, KnowledgeStatement, or AuditRecord.

**Status: PARTIAL**

### In-Memory Infrastructure

`tests/fixtures/repositories.py` provides:

* `InMemoryLearningObjectRepository`;
* `InMemoryVersionRepository`;
* `InMemoryAuditRepository`.

The Version repository stores Version objects and retrieves history by `learning_object_id`.

**Status: IMPLEMENTED / IA-01 ALIGNED**

### Current Implementation Boundary

The verified implementation currently reaches:

`Domain → Application → In-Memory Repository → Tests`

The verified production persistence path reaches only the independently persisted Anchor model.

The following persistent path is not yet materialized:

`Application → Concrete Repository → Persistence Model → Database → Reload`
