# 05_Implementation_Alignment_Roadmap.txt

## Implementation Alignment Roadmap

### Purpose

This roadmap converts the Implementation Baseline Inventory and End-to-End Gap Map into an ordered implementation sequence.

It is subordinate to the normative architecture.

### Guiding Rule

Resolve semantic deviations before materializing production persistence.

Do not encode a currently non-conformant domain representation into database schemas and repositories and then attempt to correct it later.

---

## Phase IA-01 — Domain Semantic Alignment

### Objective

Bring the domain representation into explicit agreement with the consolidated normative baseline.

### Scope

Resolve:

* IA-001 — LearningObject statement representation;
* IA-002 — KnowledgeStatement identity/value semantics;
* IA-003 — generic Version entity;
* IA-005 — LearningObject version semantics;
* IA-010 — generic VersionRepository history;
* IA-017 — Version snapshot representation;
* IA-018 — application/repository Version boundary;
* IA-019 — Version snapshot test coverage.

### Completed Result

The domain and repository contracts now express LearningObject-centered knowledge versioning.

KnowledgeStatement is represented as an immutable aggregate member/value and has no autonomous persistence or versioning boundary.

Version history is explicitly scoped to LearningObject.

Version snapshots preserve the structured KnowledgeStatement value.

Application and repository Version history contracts are aligned.

### Gate

`IA-01 DOMAIN ALIGNMENT`

Status: `COMPLETE`

### Closure Evidence

* Domain entities aligned;
* VersionRepository contract aligned;
* Application service aligned;
* in-memory Version repository aligned;
* Version snapshot semantics tested;
* no autonomous KnowledgeStatement repository introduced.

### Remaining Work Outside IA-01

Production persistence and repository integration remain pending and belong to subsequent implementation-alignment phases.

---

## Phase IA-02 — Contract and Lifecycle Alignment

### Objective

Resolve remaining repository and lifecycle ambiguities before persistence.

### Scope

Primarily:

* IA-009 — LearningObject delete capability;
* repository ownership boundaries;
* Version history ownership;
* Audit history boundary;
* lifecycle contract consistency.

### Verified Resolution Progress

The following IA-02 alignment findings have been resolved and verified:

* IA-009 — LearningObject delete capability — `RESOLVED`;
* IA-016 — Lifecycle Application Orchestration — `RESOLVED`.

The LearningObject Repository no longer exposes physical deletion as a Domain Repository capability.

The LearningObject lifecycle orchestration and invalid-transition coverage have been verified against:

`Candidate → Proposed → Active → Retired`

### Required Result

Every repository capability must have an explicit normative purpose.

The LearningObject lifecycle must remain:

`Candidate → Proposed → Active → Retired`

Change Proposal review decisions must remain outside the LearningObject lifecycle state.

Version history must remain LearningObject-centered.

Audit history must remain distinct from immutable Version history.

### Gate

`IA-02 CONTRACT AND LIFECYCLE ALIGNMENT`

Status: `COMPLETE`

Progress: `100%`

### Closure Evidence

* repository capability boundaries verified;
* LearningObject Repository ownership verified;
* Version history ownership verified as LearningObject-centered;
* Audit history boundary verified as distinct from Version history;
* LearningObject delete capability verified as absent from the Domain Repository contract;
* lifecycle orchestration verified against `Candidate → Proposed → Active → Retired`;
* invalid lifecycle transition behavior verified;
* Change Proposal review decisions remain outside LearningObject lifecycle state.

## Phase IA-03 — Persistence Model

### Objective

Materialize the aligned domain model in production persistence.

### Scope

Implement and verify persistence for:

* LearningObject;
* Version;
* AuditRecord;
* required KnowledgeStatement representation;
* Anchor relationships.

### Required Result

Persistence models represent the aligned domain semantics rather than the pre-alignment implementation.

KnowledgeStatement must remain an aggregate member/value representation and must not acquire an autonomous persistence or repository boundary merely as a consequence of persistence implementation.

Version persistence must preserve the LearningObject-centered immutable Version boundary.

### Gate

`IA-03 PERSISTENCE MODEL ALIGNMENT`

Status: `COMPLETE`

Progress: `100%`

### Closure Evidence

* `LearningObjectModel` persistence model verified;
* embedded `KnowledgeStatement` representation verified;
* Anchor relationship verified;
* `VersionModel` and LearningObject foreign key verified;
* `AuditRecordModel` verified, including the SQLAlchemy-safe `metadata` column mapping;
* LearningObject `examples` / `notes` relationships verified;
* owned relationship cascade and `delete-orphan` behavior verified;
* focused persistence-model tests passed.

### Scope Boundary

Concrete repositories belong to IA-04.

Database/session wiring, migrations, transaction handling, and persistent integration belong to IA-05 and later phases.

These concerns must not be counted as IA-03 work.

## Next Action

Verify the existing Domain Repository contracts and repository tree before implementing IA-04.

Then proceed one concrete repository block at a time using:

`inspect → block/sections → verify → test → percentage → next gap`

## Operating Rule

No implementation change is considered complete until its focused test passes.

For an existing file with a small, localized change, identify only the sections that need modification instead of rewriting the whole file.

For a new file, provide one complete block for that file.

If a single-file change is too large for one block, split it into sequential blocks while keeping all blocks scoped to that same file.

Distinct files are always handled as distinct blocks.

If a repository read or search fails, automatically try alternative Git tree, path, or lookup methods before stopping.

After a focused test passes, advance automatically to the next confirmed gap and update the completion percentage.

Do not reopen a completed IA phase unless new authoritative evidence establishes a direct contradiction with the normative architecture or roadmap.

IA-03 is closed. Concrete repository integration belongs to IA-04. Database/session/migration/transaction wiring belongs to IA-05. Persistent integration testing belongs to IA-06.
