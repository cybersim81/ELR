## IA-08-A03 Objective

Determine whether the repository implementation conforms to the authoritative
normative responsibility for Security and Authorization.

The inspection MUST establish:

1. what the authoritative specifications require;
2. what the current repository actually implements;
3. which responsibilities already exist;
4. which responsibilities are incomplete or absent;
5. whether any apparent difference is architectural or merely naming;
6. whether a confirmed implementation gap actually exists.

Do not introduce a new service, entity, repository, boundary, or abstraction
merely because a particular class or filename is absent.

The absence of a named class is NOT sufficient evidence of non-conformance.

Responsibility and behavior are authoritative; naming is secondary.

# Required Working Method

================================================================================

Follow this sequence:

`inspect → compare → responsibility disposition → implement only confirmed gap → test → verify → checkpoint → roadmap/bootstrap update → next finding`

---

## Step 1 — Normative Inspection

Read the authoritative normative specifications relevant to IA-08-A03.

Identify:

* required responsibility;
* required semantics;
* authorization rules;
* security invariants;
* identity and actor requirements;
* permission boundaries;
* persistence expectations where applicable;
* transaction expectations where applicable;
* required integration points;
* explicit negative-path requirements;
* required failure behavior.

Do not infer requirements from filenames alone.

---

## Step 2 — Repository Inspection

Inspect the current repository implementation.

Search for:

* domain entities;
* application services;
* authorization mechanisms;
* authentication / identity boundaries;
* repositories;
* persistence models;
* API boundaries;
* transaction boundaries;
* actor propagation;
* permission checks;
* security-related exceptions;
* existing tests;
* adapters;
* wiring;
* existing integration points.

Prefer existing implementation boundaries when they already satisfy the
normative responsibility.

---

## Step 3 — Responsibility Disposition

Classify the inspected responsibility as one of:

`CONFORMANT`

`IMPLEMENTATION VERIFIED / RESOLVED`

`PARTIAL`

`GAP`

`BLOCKED`

Use the smallest classification supported by evidence.

Do not create implementation work merely to eliminate a naming difference.

Do not classify an absent named abstraction as a GAP unless the authoritative
responsibility itself is demonstrably unfulfilled.

---

## Step 4 — Implementation

If and only if a confirmed implementation gap exists:

* modify only the necessary repository files;
* preserve previously verified behavior;
* preserve A01 closure;
* preserve A02 closure;
* avoid unrelated refactoring;
* avoid speculative architecture;
* maintain existing repository abstractions where sufficient;
* maintain transaction semantics;
* maintain existing domain lifecycle semantics;
* preserve audit and version behavior.

---

## Step 5 — Verification

After implementation:

* run focused tests for the changed responsibility;
* run relevant application-service tests;
* run relevant integration tests;
* run the complete test suite;
* record exact verification results.

A responsibility is not considered complete merely because the code appears
correct.

---

## Step 6 — Documentation

After verification:

* update the relevant IA-08 implementation roadmap;
* update the current implementation checkpoint;
* update the Bootstrap Pack operational state;
* update the session continuity state;
* update this session prompt if the next resume point changes.

Do not modify baseline documents unless the baseline itself has materially
changed.

---

## Step 7 — Checkpoint

A checkpoint MUST be established after a responsibility receives a final
disposition and verification is complete.

The checkpoint MUST identify:

* completed finding;
* responsibility status;
* verification result;
* remaining findings;
* next finding;
* files changed;
* relevant commit/checkpoint reference when available.
