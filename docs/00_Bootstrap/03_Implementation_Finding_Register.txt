# 03_Implementation_Finding_Register.txt

## Implementation Finding Register

### Purpose

This document records the implementation findings established during the Implementation Baseline Inventory.

A finding does not redefine the normative architecture.

Each finding must be resolved against the authoritative normative corpus before the corresponding implementation is considered conformant.

### Status Vocabulary

* `RESOLVED` — the identified implementation alignment issue has been resolved and verified.
* `CONFIRMED DEVIATION` — implementation contradicts an established normative boundary.
* `COVERAGE GAP` — behavior may exist, but the required conformance is not demonstrated by tests.
* `PERSISTENCE GAP` — required persistent implementation is absent.
* `ALIGNMENT REQUIRED` — implementation exists but requires semantic or structural alignment.
* `PRELIMINARILY CONSISTENT` — inspected evidence is currently consistent with the baseline.
* `OPEN` — requires further verification or an explicit implementation decision.

---

## IA-001 — LearningObject Statement Representation

**Area:** Domain Model

**Finding:** LearningObject previously stored `statement` as `str`.

**Normative expectation:** KnowledgeStatement is an aggregate member / knowledge value of LearningObject and does not constitute an autonomous aggregate.

**Required change:** Represent KnowledgeStatement explicitly as an immutable value owned by LearningObject without introducing an autonomous aggregate boundary.

**Resolution:** LearningObject now stores an explicit immutable `KnowledgeStatement` value object. KnowledgeStatement has no autonomous repository, lifecycle, or versioning boundary.

**Evidence:**

* `app/domain/entities/knowledge_statement.py`
* `app/domain/entities/learning_object.py`
* `tests/domain/test_learning_object.py`
* `tests/application/services/test_learning_object_service.py`

**Status:** `RESOLVED`

**Resolution note:** The implementation now explicitly represents the normative KnowledgeStatement semantics without introducing an autonomous KnowledgeStatement aggregate.

---

## IA-002 — KnowledgeStatement Identity Semantics

**Area:** Domain Model

**Finding:** The previous implementation represented KnowledgeStatement with entity-like identity metadata.

**Normative expectation:** KnowledgeStatement is an aggregate member / knowledge value and has no autonomous identity, lifecycle, repository, or versioning boundary.

**Required change:** Remove autonomous identity semantics and represent KnowledgeStatement as an immutable value.

**Resolution:** KnowledgeStatement is now an immutable value object containing only its semantic value fields.

**Evidence:**

* `app/domain/entities/knowledge_statement.py`
* `tests/domain/test_learning_object.py`

**Status:** `RESOLVED`

**Resolution note:** No autonomous KnowledgeStatement repository or lifecycle exists.

## IA-003 — Generic Version Entity

**Area:** Domain Model

**Finding:** Version previously contained a generic `entity_id`.

**Normative expectation:** LearningObject is the primary unit of knowledge versioning.

**Required change:** Version identity must explicitly reference the LearningObject whose history it represents.

**Resolution:** Version now identifies its owning LearningObject explicitly through `learning_object_id`.

**Evidence:**

* `app/domain/entities/version.py`
* `app/domain/repositories/version_repository.py`
* `tests/fixtures/repositories.py`
* `tests/application/services/test_learning_object_service.py`

**Status:** `RESOLVED`

**Resolution note:** The Version boundary is explicitly LearningObject-centered.

## IA-005 — LearningObject Version Number

**Area:** Domain Model

**Finding:** LearningObject previously contained mutable `version: int`.

**Normative expectation:** Stable LearningObject identity and immutable Version history are distinct concepts.

**Required change:** Remove mutable Version state from LearningObject and represent historical versions through immutable Version records.

**Resolution:** The mutable version field has been removed from LearningObject. Version numbering is represented by immutable Version records owned by the LearningObject version history.

**Evidence:**

* `app/domain/entities/learning_object.py`
* `app/domain/entities/version.py`
* `app/application/services/learning_object_service.py`
* `tests/application/services/test_learning_object_service.py`

**Status:** `RESOLVED`

**Resolution note:** LearningObject lifecycle state is no longer conflated with Version history.

## IA-009 — LearningObject Delete Capability

**Area:** Repository / Lifecycle

**Finding:** LearningObjectRepository exposed `delete()`, and the in-memory implementation supported it.

**Impact:** Physical deletion semantics had not yet been reconciled with lifecycle and persistence requirements.

**Status:** `RESOLVED`

**Resolution:** `delete()` has been removed from the effective LearningObjectRepository contract and from the in-memory repository implementation.

**Normative alignment:** LearningObject lifecycle terminates at `Retired`. Retirement does not imply physical deletion, and historical identity/version information must remain available. Physical deletion, if ever required, is outside the Domain Repository contract.

**Evidence:**

* `app/domain/repositories/learning_object_repository.py`
* `tests/fixtures/repositories.py`

**Resolution note:** LearningObject no longer exposes physical deletion as a Domain Repository capability.

---

## IA-010 — Generic VersionRepository History

**Area:** Repository Layer

**Finding:** VersionRepository previously exposed generic `get_history(entity_id)` semantics.

**Normative expectation:** Version history belongs to the LearningObject versioning boundary.

**Required change:** Replace generic entity history semantics with LearningObject-centered history semantics.

**Resolution:** VersionRepository now exposes:

`get_history(learning_object_id)`

and the in-memory implementation filters Version records using `learning_object_id`.

**Evidence:**

* `app/domain/repositories/version_repository.py`
* `tests/fixtures/repositories.py`
* `app/application/services/learning_object_service.py`

**Status:** `RESOLVED`

**Resolution note:** Generic entity version-history semantics have been removed.

## IA-016 — Lifecycle Application Orchestration

**Area:** Application

**Finding:** LearningObjectService implements the lifecycle progression and rejects invalid transitions through the domain model.

**Impact:** The application lifecycle skeleton is operational, but explicit test coverage was initially incomplete for several prohibited transitions.

**Status:** `RESOLVED`

**Resolution:** Lifecycle orchestration and domain transition rules have been verified, including explicit rejection of invalid transitions across Candidate, Proposed, Active, and Retired states.

**Normative lifecycle:**

`Candidate → Proposed → Active → Retired`

**Evidence:**

* `app/domain/entities/learning_object.py`
* `app/application/services/learning_object_service.py`
* `tests/domain/test_learning_object.py`

**Resolution note:** The application lifecycle is aligned with the normative state model. `Reviewed`, `Approved`, `Rejected`, and `Updated` are not LearningObject lifecycle states.

## IA-017 — Version Snapshot Representation

**Area:** Application / Versioning

**Finding:** Version snapshots previously inherited the string-based LearningObject statement representation.

**Normative expectation:** Version snapshots preserve the semantic state of the LearningObject, including its KnowledgeStatement value.

**Required change:** Preserve KnowledgeStatement semantics structurally inside the immutable Version snapshot.

**Resolution:** Version snapshots now represent `statement` structurally with its `text` and `language` values.

**Evidence:**

* `app/application/services/learning_object_service.py`
* `tests/application/services/test_learning_object_service.py`

**Status:** `RESOLVED`

**Resolution note:** Both initial Version creation and subsequent Version creation use the corrected snapshot representation.

## IA-018 — Application Version History Boundary

**Area:** Application / Repository

**Finding:** The application service was LearningObject-centered while the repository abstraction remained generic.

**Normative expectation:** Application and repository layers must express the same LearningObject-centered Version boundary.

**Required change:** Align application and repository Version history operations around `learning_object_id`.

**Resolution:** The application service and VersionRepository now both use `learning_object_id` for Version history.

**Evidence:**

* `app/application/services/learning_object_service.py`
* `app/domain/repositories/version_repository.py`
* `tests/fixtures/repositories.py`

**Status:** `RESOLVED`

## IA-019 — Version Snapshot Test Coverage

**Area:** Tests
